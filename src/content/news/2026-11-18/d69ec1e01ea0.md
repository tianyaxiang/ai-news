OpenAI released GPT-6.2 Sol yesterday at the same price as GPT-6.1 Sol: $2 per million input tokens and $10 per million output. Artificial Analysis puts it at 53 on their Intelligence Index at medium effort, against 46 for 6.1 Sol, using slightly fewer output tokens. Same price, 7 points higher. 6.1 Sol at medium effort is the default coding worker in my setup, so this morning I spent $11 to find out whether I should switch. On my orders the two models tied on quality, and 6.2 Sol cost 25% more. I'm not switching yet.

OpenAI 昨天发布了 GPT-6.2 Sol，价格与 GPT-6.1 Sol 相同：输入代币每百万 2 美元，输出代币每百万 10 美元。Artificial Analysis 在中等难度下将其智能指数定为 53，而 6.1 Sol 为 46，且使用的输出代币略少。价格相同，分数高出 7 分。6.1 Sol 在中等难度下是我设置中的默认编码工作模型，所以今天早上我花了 11 美元来确定是否应该切换。在我的订单中，两个模型的质量持平，但 6.2 Sol 的成本高出 25%。我暂时不会切换。

Setup I plan and review with Claude and hand the implementation to a cheaper model through a small dispatcher I wrote. Each work order runs in its own git worktree inside a macOS sandbox. When the worker says it's done, the dispatcher re-runs the project's test command itself. Then a separate read-only reviewer (Claude Sonnet) reads the diff against the order and returns pass or block. A failed check or a block triggers one automatic retry.

我的设置是使用 Claude 进行规划和审查，并通过我编写的一个小型调度程序将实现工作交给更便宜的模型。每个工作订单都在 macOS 沙盒内的独立 git 工作树中运行。当工作模型表示完成后，调度程序会自行重新运行项目的测试命令。然后，一个独立的只读审查员（Claude Sonnet）会根据订单读取差异并返回通过或拦截结果。检查失败或拦截会触发一次自动重试。

For model comparisons I keep five work orders from October that were hard for the worker I used back then. It needed 3 to 7 attempts on each. Every replay starts from the same base commit as the original. All five are in one Python repo with about 900 tests at those commits. Today both models got the same five orders at the same moment, through the same Codex CLI build (0.169.0-alpha.11.1), at medium reasoning effort, two jobs per model in parallel. Costs are list prices, including $0.10 per million for cached input.

为了进行模型比较，我保留了 10 月份的五个工作订单，这些订单对于我当时使用的模型来说很难处理。每个订单都需要 3 到 7 次尝试。每次重放都从与原始订单相同的基准提交开始。这五个订单都在同一个 Python 仓库中，在这些提交点大约有 900 个测试。今天，两个模型在同一时刻通过相同的 Codex CLI 构建版本（0.169.0-alpha.11.1）接收了相同的五个订单，推理难度均为中等，每个模型并行处理两个作业。成本为标价，包括每百万 0.10 美元的缓存输入费用。

One order makes the whole difference. Without skills-sync, 6.2 Sol is 13% cheaper ($3.44 against $3.97). With five orders, one outlier decides the headline, so read everything below with that in mind. The $2 order: The skills-sync order asks for a new script plus tests. 6.2 Sol wrote it, ran the full suite inside the sandbox and saw 5 failures out of 905 tests. None were in its own code. It re-ran four of them in a clean temp directory and they passed. One old assertion still failed. Then it stopped, left its four new files unstaged, and asked me to decide whether it was allowed to commit. I can defend that call. I also paid for it.

一个订单造成了全部差异。如果不计入 skills-sync，6.2 Sol 反而便宜了 13%（3.44 美元对 3.97 美元）。在五个订单中，一个异常值决定了标题，所以请带着这个前提阅读下文。关于 2 美元的订单：skills-sync 订单要求编写一个新脚本并进行测试。6.2 Sol 编写了它，在沙盒中运行了完整的测试套件，并在 905 个测试中发现了 5 个失败。没有一个是它自己代码的问题。它在一个干净的临时目录中重新运行了其中四个，它们通过了。一个旧的断言仍然失败。然后它停止了，留下了四个未暂存的新文件，并要求我决定是否允许提交。我可以为这个决定辩护。我也为此付了钱。

The dispatcher's own check on that worktree came back green, found uncommitted files, and sent the order back for an automatic retry. The second attempt read everything again, ran the 13-minute suite again and committed. $1.06 for the first attempt, $0.94 for the second. 6.1 Sol finished the same order in one attempt for $0.38. Some early feedback on OpenAI's forum says the new models stop too early. This is what that looks like on a bill.

调度程序对该工作树的检查结果为绿色，发现了未提交的文件，并将订单发回进行自动重试。第二次尝试重新读取了所有内容，再次运行了 13 分钟的测试套件并提交。第一次尝试花费 1.06 美元，第二次花费 0.94 美元。6.1 Sol 在一次尝试中以 0.38 美元完成了同样的订单。OpenAI 论坛上的一些早期反馈称，新模型停止得太早。这就是账单上所体现的情况。

Where 6.2 Sol was better: The codex-adapter order contradicts itself. It says existing tests may only be added to, never changed, but the feature can't go green without changing one old assertion. Both models noticed and said so in their reports. What they did next was different. 6.2 Sol left the old assertion alone and reported the conflict. When the check failed and the order came back, it changed that one assertion, nothing else, and passed review. 6.1 Sol also loosened the timing parameters of three unrelated watchdog tests to get the suite green. The reviewer blocked that. The order went back at xhigh effort and took four attempts in total, $1.14 against $0.88.

6.2 Sol 表现更好的地方：codex-adapter 订单本身存在矛盾。它说现有的测试只能增加，不能修改，但如果不修改一个旧的断言，该功能就无法通过测试。两个模型都注意到了这一点，并在报告中指出了。它们接下来的做法不同。6.2 Sol 没有动那个旧断言，并报告了冲突。当检查失败订单返回时，它修改了那一个断言，没有做其他任何改动，并通过了审查。6.1 Sol 为了让套件通过，还放宽了三个无关的看门狗测试的计时参数。审查员拦截了该操作。订单以超高难度重新处理，总共进行了四次尝试，成本为 1.14 美元，而 6.2 Sol 为 0.88 美元。

The regression I couldn't reproduce: Artificial Analysis reports 6.2 Sol three points below 6.1 Sol on their Coding Agent Index, measured with the Codex CLI at max effort. They trace the drop to a code Q&A test where the new model leaves out key facts more often. That worried me, because I also send read-only research orders. So I wrote two. One: list every failure case of a function, with the exact error strings and line numbers. Two: list every exit code, plus every place one particular code is returned. I built the answer keys from the source before running anything, 20 facts and 25 facts. 6.2 Sol got 20/20 and 23/25. 6.1 Sol got 20/20 and 24/25. Two orders is not a benchmark, but at medium effort I saw no sign of the problem.

我无法复现的回归：Artificial Analysis 报告称，在以最大难度使用 Codex CLI 测量时，6.2 Sol 在其编码代理指数上比 6.1 Sol 低三分。他们将这种下降归因于代码问答测试，新模型在测试中更频繁地遗漏关键事实。这让我很担心，因为我也发送只读的研究订单。所以我写了两个。第一个：列出一个函数的所有失败案例，包括确切的错误字符串和行号。第二个：列出每个退出代码，以及返回特定代码的每个位置。在运行任何东西之前，我从源代码构建了答案键，分别是 20 个事实和 25 个事实。6.2 Sol 得到了 20/20 和 23/25。6.1 Sol 得到了 20/20 和 24/25。两个订单算不上基准测试，但在中等难度下，我没有看到该问题的迹象。

Speed: Artificial Analysis measures 6.2 Sol as faster per task. I couldn't see it. An order took 25 to 36 minutes on either model, and most of that is the test suite, which needs about 13 minutes per run when four jobs share one Mac mini. The model's thinking time is the small part.

速度：Artificial Analysis 测量得出 6.2 Sol 每个任务更快。我没看出来。无论哪个模型，一个订单都需要 25 到 36 分钟，其中大部分时间是测试套件，当四个作业共享一台 Mac mini 时，每次运行大约需要 13 分钟。模型的思考时间只占很小一部分。

Caveats: Five orders, one repo, one language, medium effort, one day after release. The first-pass rate is understated for both models: at least three of the failed first checks came from timing-sensitive tests under load, not from the model's code. The prompts were written for earlier models and I changed nothing for 6.2.

注意事项：五个订单，一个仓库，一种语言，中等难度，发布后一天。两个模型的首次通过率都被低估了：至少有三次首次检查失败是由于负载下对时间敏感的测试引起的，而不是模型代码的问题。提示词是为早期模型编写的，我没有为 6.2 做任何更改。

What I'm doing: 6.1 Sol stays my default. For the next week about half of my real orders go to 6.2 Sol, with one added line in its prompt: if the suite has failures that were there before you started, commit anyway and list them in the report. That should remove the $2 case. In a week I'll have 15 to 20 real orders per model and I'll post the numbers. My advice: before you switch a default model, replay a handful of orders you've already paid for once. Mine cost $11. If you've run the same comparison, I'd like to see your numbers.

我的做法：6.1 Sol 仍然是我的默认模型。在接下来的一周里，我大约一半的真实订单将交给 6.2 Sol 处理，并在其提示词中增加了一行：如果套件中存在你开始之前就有的失败，请照常提交并在报告中列出它们。这应该能消除 2 美元的情况。一周后，我将拥有每个模型 15 到 20 个真实订单，我会公布这些数据。我的建议是：在切换默认模型之前，重放一些你已经付过费的订单。我的花费是 11 美元。如果你也进行了同样的比较，我很想看看你的数据。
