### How One Base64 Bug Can Leak Your Java Heap (Java4Shell)

关于 Java4Shell 的大部分首日报道要么是“你的服务器着火了”，要么是“它只会导致 JVM 崩溃”。这两种说法都忽略了其背后的机制，而机制本身才能告诉你谁处于风险之中。本文将探讨该漏洞存在的原因、各来源实际确定的内容，以及防御者可以关注的重点。我本人并未复现该漏洞。以下所有内容均来自 Upwind、Endor Labs、Equixly、Qualys 和 Calif 的公开报告，并在存在分歧的地方进行了标注。

**TL;DR (摘要)**

| 声明 | 状态 |
| :--- | :--- |
| 在配备 AVX-512 VBMI 的 x86-64 架构上，堆写入越过输出数组边界 | 已由 Endor Labs（在模拟器下）和 Upwind（在真实硬件上）复现 |
| 远程请求导致 JVM 崩溃 | 各来源一致确认 |
| 指定产品中的预认证远程代码执行 (RCE) | 由 Calif 声明，无公开的概念验证 |
| 攻击者可控制写入内容 | 不支持，写入的字节是固定的 |
| 野外利用 | 无报告，截至 11 月 17 日未列入 CISA KEV |

**为什么存在内部函数 (Intrinsic)**

HotSpot 附带了一个纯 Java 实现的 Base64 解码器。当 JIT（即时编译器）观察到该解码器运行频繁时，它会用一个内部函数（针对目标 CPU 手写汇编的存根）来替换 Java 循环。在配备 AVX-512 VBMI 的 x86-64 架构上，该存根可以一次性解码大块数据。Equixly 指出了两个与暴露风险相关的要点：内部函数仅在 JIT 编译解码器后才会替换 Java 代码，这在繁忙的服务器上几秒钟内就会发生；且向量化路径仅在超过长度阈值时才会启用。Endor Labs 指出，Java 21、25 和 27 的阈值为 31 字节，Java 17 为 128 字节。这就是为什么不同版本触发该漏洞的最短长度有所不同：在 21、25 和 27 版本上，65 个字符就足够了，而 17 版本需要 129 个字符。

**尾部漏洞 (The tail bug)**

块循环处理大部分输入。最后一部分字符（包括填充）会通过尾部例程处理。据 Upwind 称，以多余的 `=` 结尾的畸形字符串会导致尾部计算出负的输出长度。一次小规模写入会变成完整的 64 字节写入，超出输出数组末尾 62 字节。Endor Labs 测量得出，单个 `=` 尾部会导致 62 字节溢出，`==` 则会导致 63 字节溢出。根据这些测量结果，可以得出两个结论：首先，溢出的内容是固定的。Endor Labs 表示，无论输入数据如何，这些字节保持不变。攻击者控制的是输入长度和目标数组周围的堆布局，而不是被写入的字节。其次，Java 随后仍会抛出 `IllegalArgumentException` 拒绝该输入。正如后文检测部分所述，该异常是一个有用的信号，但它是在破坏发生后才触发的。Upwind 还运行了 30 万个格式正确的输入，未发现任何溢出，因此普通流量没有风险。触发条件是畸形字符串。

**修复方案**

Endor Labs 将该修复报告为 JDK-8393212，“Base64 优化改进”，这是一个四行代码的更改，在大小计算前添加了保护，并将短填充尾部路由到标量路径。工程师于 2026 年 10 月 14 日在保密状态下提交了该补丁。Endor Labs 还指出，截至 11 月 17 日，公开的 jdk17u、jdk21u 和 jdk25u 仓库尚未包含此修复，而 Oracle 的构建版本已经发布。易受攻击的代码于 2023 年 1 月通过 JDK 18 的反向移植进入 17.0.6 版本，Equixly 标记 17.0.6 为起点，这是其根据反向移植历史推断得出的。

**从崩溃到代码执行**

崩溃路径很简单。据 Endor Labs 称，如果这 62 个多余的字节落在活动对象上，它们会覆盖其头部，通常的结果是垃圾回收期间发生 `SIGSEGV`。Equixly 警告说，崩溃日志不会提到 Base64，因为垃圾回收器是在稍后读取受损对象时才触发错误的。Calif 声称可以实现更多目标，分为五个阶段：

| 阶段 | 声明的步骤 |
| :--- | :--- |
| 1 | 破坏数组长度 |
| 2 | 破坏第二个数组以泄露堆内容（Calif 称之为 JavaBleed） |
| 3 | 修复对象头部以保持 JVM 运行 |
| 4 | 远程整理堆，使溢出落在选定对象上 |
| 5 | 写入 JVM 代码缓存 |

Endor Labs 将上述每一项都标记为 Calif 的声明。Calif 表示不存在通用的利用方式，每个目标都需要特定的解码器路径、可写缓冲区、可读反馈通道和堆布局。我阅读的来源完全没有讨论地址空间随机化 (ASLR)，因此我不会将其称为障碍或绕过手段。这就是为什么你的暴露风险取决于应用程序，而不仅仅是 JVM。一个在热路径上使用 `Base64.getDecoder()` 解码攻击者数据并反射部分结果的服务，具有 Calif 所描述的形态。一个从不解码攻击者输入的服务，最坏的情况也只是崩溃风险。特定产品中的 HTTP Basic 或 JWT 解析是否符合条件在各来源中尚无定论，因此我将其视为未知。

**未触及漏洞的情况**

根据报告，以下情况不会触及该漏洞：MIME 解码器采用标量路径；不调用 `java.util.Base64` 的第三方 Base64 库不会触及内部函数；ARM64 主机（包括 Graviton、Ampere 和 Apple 芯片）没有此类存根。Equixly 在 arm64 架构的 Temurin 17.0.21 上运行了 794 个精心构造的输入，未发现任何多余写入。此外，不具备 AVX-512 VBMI 的 x86-64 架构（如 Skylake-SP、Cascade Lake 和 Zen 4 之前的 AMD）也不受影响。需要注意的一个差异是：Equixly 要求同时具备 AVX-512 BW 和 VBMI，而 Cyber Security News 仅提到了 VBMI。Qualys 列出了四个 CPU 标志（avx512f, avx512bw, avx512vbmi, bmi2），并表示必须同时出现这四个标志。

**检测工程**

你无法通过依赖扫描来检测此漏洞，因为缺陷存在于运行时中。你需要在边缘、日志和主机上进行检测。

**边缘规则**

无需解码即可检查畸形形态。填充后的 Base64 长度必须能被 4 整除，因此以 `=` 或 `==` 结尾且长度不是 4 的倍数的令牌会立即失效。Upwind 的启发式规则增加了 32 个字符的长度下限。Endor Labs 建议在运行混合 Java 版本时将 65 作为下限。Equixly 为 Authorization 标头提供了以下规则：`^Basic\s+(?:\S{4})*\S{0,2}=`。我尚未测试过该规则。请先在生产流量中以仅记录模式运行它，因为错误的规则如果阻止了正常的登录，本身就会导致服务中断。应用层...
