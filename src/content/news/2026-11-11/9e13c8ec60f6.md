If all of my posts were titled “Typst very nice”, we’d be done, but, alas. Luckily, typst accepts inputs to a document with `--input key=value`, which is put in a `sys.inputs` dictionary for the template to read. So the template becomes:
`#let title = sys.inputs.at("title", default: "You forgot the title :(")`
which, when rendered with `typst compile --format png --ppi 144 --input title="Look ma, from the CLI!" fancy-typst-with-input.typ` becomes Perfection. Let’s move on to generating the images at build-time.

### Astro
This site is built with Astro, a static site generator. Articles are written in Markdown, which is then bundled into a Content Collection by Astro. The details are irrelevant, what matters is that this lets me define metadata which I can query through a Javascript API. The source code for the page template is at `src/pages/posts/[id].astro`.

本网站使用静态网站生成器 Astro 构建。文章以 Markdown 编写，然后由 Astro 打包进内容集合（Content Collection）。细节并不重要，重要的是这让我能够定义元数据，并通过 Javascript API 进行查询。页面模板的源代码位于 `src/pages/posts/[id].astro`。

There are a few notable things about this file path: That it is in the `src/pages/` directory tells Astro that this should be rendered as a page. The remainder of the path, `/posts/[id]`, tells Astro where to put the page. `[id]` being in brackets means `id` is a dynamic parameter which must be defined at build time. In other words, Astro needs to know every ID when building the site—it can’t generate infinitely many IDs.

关于这个文件路径有几点值得注意：它位于 `src/pages/` 目录下，告诉 Astro 这应该被渲染为一个页面。路径的其余部分 `/posts/[id]` 告诉 Astro 将页面放置在哪里。`[id]` 放在括号中意味着 `id` 是一个必须在构建时定义的动态参数。换句话说，Astro 在构建网站时需要知道每一个 ID——它无法生成无限多的 ID。

A function called `getStaticPaths` exported from the template defines the set. That is, fetch every article, and use its id as the id parameter. This is the object returned for the current page.

模板中导出的 `getStaticPaths` 函数定义了这个集合。也就是说，获取每一篇文章，并将其 ID 用作 ID 参数。这就是当前页面返回的对象。

And just like that, this blog now has a JSON api. Note that the file extension is included in the path, i.e. `.json.ts`. This is because when the dev server is running it sets the appropriate content-type header to let the browser know what to do with the response, but once the page is built the result is a file with `.ts` stripped off. The browser then interprets the remaining file extension to know what content to expect at the path.
