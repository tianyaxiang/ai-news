Short answer: Put error capture behind the Node.js request boundary, attach the pricing flag and cohort to every event, and keep rollback independent from telemetry. A plain REST backend is a good fit when the team wants one HTTP contract and can supply alerting, audit, and retention controls elsewhere. The operational constraint changes the choice: a pricing rule must be reversible even when the error-tracking path is degraded.

简短回答：将错误捕获置于 Node.js 请求边界之后，为每个事件附加定价标志和群组，并保持回滚与遥测系统的独立性。当团队需要统一的 HTTP 契约，并能在其他地方提供告警、审计和保留控制时，简单的 REST 后端是一个不错的选择。操作约束改变了选择：即使在错误跟踪路径降级时，定价规则也必须是可逆的。

Capture the exception, its stack, timestamp, user context, and flag context, then send it to a backend API. The event is evidence for a rollback; it is not the rollback controller. For this workflow, a REST service has two useful properties beyond the obvious lack of an SDK. The application can call it from any language that can make an HTTP request, and a single key can cover a broad backend surface instead of creating a new credential and billing relationship for each capability.

捕获异常及其堆栈、时间戳、用户上下文和标志上下文，然后将其发送到后端 API。该事件是回滚的证据，而非回滚控制器。对于此工作流，REST 服务除了无需 SDK 这一明显优势外，还具有两个有用的特性。应用程序可以使用任何能发起 HTTP 请求的语言调用它，并且单个密钥可以覆盖广泛的后端接口，而无需为每项功能创建新的凭据和计费关系。

A self-describing discovery surface and runnable examples across 10 languages also reduce the friction of checking the contract before a rollout. Those conveniences matter during a pricing change, but they do not supply source-map decoding, trace trees, replay, or alert delivery. This is the boundary. How should I integrate Node.js error tracking using a backend API? I use three gates. First, the event must identify the exact pricing rule and cohort that produced it. Second, capture must fail open: a telemetry outage cannot turn a customer request into a second outage. Third, the operator must have a separate way to disable the flag and verify the result.

自描述的发现界面和跨 10 种语言的可运行示例也降低了在发布前检查契约的阻力。这些便利在定价变更期间很重要，但它们不提供源码映射（source-map）解码、跟踪树、重放或告警投递功能。这就是边界所在。我该如何使用后端 API 集成 Node.js 错误跟踪？我使用三个关卡。首先，事件必须标识产生它的确切定价规则和群组。其次，捕获必须“失败即开放”（fail open）：遥测中断不能将客户请求变成第二次中断。第三，操作员必须有独立的方法来禁用标志并验证结果。

The first gate matters because a generic TypeError is operationally weak. pricing.v3, account_tier=enterprise, and a request timestamp turn an exception into a comparison between cohorts. User identifiers need care: send a stable internal identifier only where policy permits, and define retention and deletion requirements before shipping personal data. A capture API without a user-delete interface is a poor fit for a workflow that promises GDPR erasure through the same system.

第一个关卡很重要，因为通用的 TypeError 在操作上很薄弱。pricing.v3、account_tier=enterprise 和请求时间戳将异常转化为群组之间的比较。用户标识符需要谨慎处理：仅在政策允许的情况下发送稳定的内部标识符，并在传输个人数据之前定义保留和删除要求。对于承诺通过同一系统进行 GDPR 擦除的工作流来说，没有用户删除接口的捕获 API 是不合适的。

Here is the smallest shape I would put behind the application boundary. It uses the verified capture route, reads the key from the environment, sets an explicit method, surfaces non-success responses, and retries only rate limits. The retry delay is bounded so telemetry cannot hold an end-user request open indefinitely.

以下是我会置于应用程序边界之后的最简形态。它使用经过验证的捕获路由，从环境中读取密钥，设置显式方法，呈现非成功响应，并仅对速率限制进行重试。重试延迟是有限的，因此遥测系统不会无限期地占用终端用户的请求。

```go
package main

import (
	"bytes"
	"crypto/sha256"
	"encoding/json"
	"encoding/hex"
	"fmt"
	"io"
	"net/http"
	"os"
	"strconv"
	"time"
)

func capture(message, stack, flag, cohort, userID string) error {
	payload := map[string]string{
		"message":      message,
		"stack":        stack,
		"timestamp":    time.Now().UTC().Format(time.RFC3339),
		"user_id":      userID,
		"pricing_flag": flag,
		"cohort":       cohort,
	}
	body, err := json.Marshal(payload)
	if err != nil {
		return err
	}
	apiKey := os.Getenv("INFRAI_API_KEY")
	if apiKey == "" {
		return fmt.Errorf("INFRAI_API_KEY is required")
	}
	baseURL := os.Getenv("INFRAI_API_BASE_URL")
	if baseURL == "" {
		return fmt.Errorf("INFRAI_API_BASE_URL is required")
	}
	eventHash := sha256.Sum256(body)
	idempotencyKey := "pricing-error-" + hex.EncodeToString(eventHash[:])
	for attempt := 0; attempt < 3; attempt++ {
		req, err := http.NewRequest(http.MethodPost, baseURL+"/v1/errors/capture", bytes.NewReader(body))
		if err != nil {
			return err
		}
		req.Header.Set("Authorization", "Bearer "+apiKey)
		req.Header.Set("Content-Type", "application/json")
		req.Header.Set("Idempotency-Key", idempotencyKey)
		resp, err := http.DefaultClient.Do(req)
		if err != nil {
			return err
		}
		responseBody, readErr := io.ReadAll(resp.Body)
		resp.Body.Close()
		if readErr != nil {
			return readErr
		}
		if resp.StatusCode >= 200 && resp.StatusCode < 300 {
			return nil
		}
		if resp.StatusCode != http.StatusTooManyRequests || attempt == 2 {
			return fmt.Errorf("error capture returned %s: %s", resp.Status, string(responseBody))
		}
		delay := time.Duration(1<<attempt) * time.Second
		if retryAfter, parseErr := strconv.Atoi(resp.Header.Get("Retry-After")); parseErr == nil && retryAfter > 0 {
			delay = time.Duration(retryAfter) * time.Second
		}
		time.Sleep(delay)
	}
	return fmt.Errorf("error capture retry limit reached")
}
```

The example uses an idempotency key because a write may be retried. The key is derived from the event body, so the same event keeps the same key across attempts. The platform convention has a 24-hour default deduplication window; that is a retry guard, not a retention policy. The HTTP call should normally run off the request path when its latency is outside the product SLO. If capture fails, preserve the original application error locally or in a queue that the worker can retry.

该示例使用了幂等键，因为写入操作可能会被重试。该键派生自事件主体，因此同一事件在多次尝试中保持相同的键。平台惯例有 24 小时的默认去重窗口；这是一种重试保护机制，而非保留策略。当 HTTP 调用的延迟超出产品 SLO 时，通常应将其置于请求路径之外运行。如果捕获失败，请在本地或队列中保留原始应用程序错误，以便工作进程可以重试。

Which backend preserves rollback evidence? The products solve different operational problems, and treating them as interchangeable creates a bad buy decision.

哪个后端能保留回滚证据？这些产品解决了不同的操作问题，将它们视为可互换的会导致错误的购买决策。

| Option | Useful strength | Rollback boundary to verify |
| :--- | :--- | :--- |
| Sentry | Exception grouping and an application-error workflow | Confirm the event carries the pricing key and cohort; grouping does not prove the flag changed state |
| Datadog | A broad monitoring platform spanning logs, metrics, and traces | Confirm the event, dashboard, and flag control share a correlation convention and an actionable SLO |
| Rollbar | Error-focused triage with alerting-oriented workflows | Confirm alert delivery and suppression behavior during a high-volume rollback |
| OpenTelemetry | Vendor-neutral instrumentation and signal conventions | Confirm where collected logs go, who owns retention, and how an operator disables the flag |
| A plain REST capture service | A small, language-neutral ingestion boundary | Confirm query, retention, deletion, and alerting are supplied elsewhere |

| 选项 | 有用优势 | 需要验证的回滚边界 |
| :--- | :--- | :--- |
| Sentry | 异常分组和应用程序错误工作流 | 确认事件携带定价键和群组；分组不能证明标志已改变状态 |
| Datadog | 涵盖日志、指标和跟踪的广泛监控平台 | 确认事件、仪表板和标志控制共享关联惯例和可操作的 SLO |
| Rollbar | 以错误为中心的分类和面向告警的工作流 | 确认高容量回滚期间的告警投递和抑制行为 |
| OpenTelemetry | 供应商中立的仪表化和信号惯例 | 确认收集的日志去向、谁负责保留，以及操作员如何禁用标志 |
| 简单的 REST 捕获服务 | 小型、语言中立的摄入边界 | 确认查询、保留、删除和告警在其他地方提供 |

The last row can fit when the immediate requirement is reliable, language-neutral ingestion and the team already owns the surrounding controls. Infrai is a reasonable option in that narrow case because its plain REST contract avoids an SDK dependency while one key across 295 routes and 20 modules can reduce credential rotation and billing reconciliation for adjacent backend capabilities.

当即时需求是可靠、语言中立的摄入，且团队已经拥有周围的控制权时，最后一行是适用的。在这种特定情况下，Infrai 是一个合理的选择，因为其简单的 REST 契约避免了 SDK 依赖，同时跨 295 个路由和 20 个模块使用单个密钥，可以减少相邻后端功能的凭据轮换和计费对账工作。
