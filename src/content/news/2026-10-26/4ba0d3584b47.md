For some context: futex is a Linux syscall that’s used in various synchronization operations, such as mutexes and condition variables. In this case, when futex is run, an unexpected error code is returned, causing glibc to panic. The chance of the kernel returning a brand-new type of error due to a Flatpak runtime upgrade is…​not very high, to say the least. But, how else would another error code end up being returned here? Well, it turns out, there’s one important thing that stands between glibc and the kernel…​ The BPF Sandbox

背景说明：futex 是一个 Linux 系统调用，用于各种同步操作，例如互斥锁和条件变量。在这种情况下，当运行 futex 时，返回了一个意外的错误代码，导致 glibc 崩溃。由于 Flatpak 运行时升级而导致内核返回一种全新类型错误的可能性……至少可以说，非常低。但是，除此之外，还有什么原因会导致这里返回另一个错误代码呢？好吧，事实证明，在 glibc 和内核之间存在一个重要的东西……BPF 沙盒。

Chromium’s sandboxing architecture on Linux is an impressive, multi-level system, where the first layer restricts the process’s runtime environment, and the second layer restricts the process’s syscall access. That second layer is known as the BPF sandbox: if a syscall is executed that is not explicitly allowed, the BPF sandbox rejects it, returning a custom error code. Syscalls…​syscalls like futex, right? Well, this seems rather interesting!

Chromium 在 Linux 上的沙盒架构是一个令人印象深刻的多层系统，其中第一层限制进程的运行时环境，第二层限制进程的系统调用访问。第二层被称为 BPF 沙盒：如果执行了未明确允许的系统调用，BPF 沙盒会拒绝它，并返回一个自定义错误代码。系统调用……像 futex 这样的系统调用，对吧？嗯，这看起来相当有趣！
