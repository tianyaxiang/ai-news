### 1. Introduction
### 1. 引言

If you’ve watched a coding agent in action, you’ve probably noticed the default workflow: let the AI handle the routine bugs, but step in when the problem gets complicated. One-line fixes go to the agent; deep internals, numerical edge cases, and cross-file invariants stay with the senior engineer. That made me wonder: what kinds of bugs do coding agents actually struggle with?
如果你观察过编码代理（Coding Agent）的工作过程，你可能已经注意到了默认的工作流：让 AI 处理常规 Bug，但在问题变得复杂时介入。单行修复交给代理，而深层内部逻辑、数值边界情况以及跨文件不变量则留给资深工程师。这让我不禁思考：编码代理到底在哪些类型的 Bug 上会感到吃力？

Over the past month, I ran 28 blind-scored debugging experiments on three real, recently fixed bugs from production open-source libraries: ky, immer, and decimal.js. Ironically, the two bugs I expected to be the hardest turned out not to be a problem at all. One was buried deep inside Immer’s internals, and the other was a subtle numerical edge case in decimal.js. Across 16 attempts, the AI fixed both correctly every single time.
在过去的一个月里，我针对来自生产级开源库（ky、immer 和 decimal.js）的三个近期修复的真实 Bug，进行了 28 项盲测调试实验。讽刺的是，我原以为最难的两个 Bug 反而完全不是问题。其中一个深埋在 Immer 的内部逻辑中，另一个则是 decimal.js 中一个微妙的数值边界情况。在 16 次尝试中，AI 每次都正确修复了这两个 Bug。

*Figure 1: AI indeed struggles with an easy bug.*
*图 1：AI 确实会在简单的 Bug 上栽跟头。*

The third bug looked almost trivial: an HTTP client silently dropped a retry option. Yet it defeated every model and workflow I tested. Across all 12 runs, the AI produced a “fix” that actually corrupts user data. By any reasonable standard, none of those runs were successful.
第三个 Bug 看起来微不足道：一个 HTTP 客户端静默丢失了重试选项。然而，它击败了我测试的所有模型和工作流。在全部 12 次运行中，AI 产生的“修复”方案实际上会破坏用户数据。按照任何合理的标准来看，这些运行都没有成功。

What concerns me isn’t just that the fixes were wrong—it’s that every single one passed the entire 84-test retry suite for the code under repair. That’s the real failure mode. If your team merges AI-generated fixes because CI is green, this is exactly the kind of bug that slips through: it looks simple, the tests pass, and the implementation quietly corrupts user data when it collides with Ky’s existing option shape.
让我担心的不仅仅是修复方案错误，而是每一个方案都通过了被修复代码的全部 84 项重试测试套件。这才是真正的故障模式。如果你的团队因为 CI（持续集成）通过就合并 AI 生成的修复代码，那么这正是那种会漏网的 Bug：它看起来很简单，测试也通过了，但当实现逻辑与 Ky 现有的选项结构冲突时，它会悄无声息地破坏用户数据。

Here’s what these 28 runs revealed—and why I think they’re relevant to anyone building or deploying coding agents. If you’re an engineer who relies on AI to write production code, a tech lead deciding where AI can be trusted, or a researcher interested in the real limits of code generation, these results highlight a failure mode that isn’t obvious from benchmark scores.
以下是这 28 次运行所揭示的内容，以及为什么我认为它们与任何构建或部署编码代理的人息息相关。如果你是一位依赖 AI 编写生产代码的工程师，一位决定 AI 在何处可信的技术主管，或者一位对代码生成真实局限性感兴趣的研究人员，这些结果凸显了一种在基准测试分数中并不明显的故障模式。

The question isn’t whether AI can solve hard bugs. It’s whether it knows when it doesn’t have enough information to solve an easy one. Difficulty didn’t predict failure—missing information did.
问题不在于 AI 是否能解决困难的 Bug，而在于它是否知道自己何时因信息不足而无法解决简单的 Bug。难度并不能预测失败，信息缺失才是。

When the correct fix could be inferred from the codebase and the bug report, the AI succeeded in all 16 attempts, including bugs buried in unfamiliar proxy internals and subtle numerical edge cases. But when the correct fix depended on an undocumented API contract, it failed in all 12 attempts—across Claude Haiku 4.5, Sonnet 5, and Opus 4.8, using three different agent workflows.
当正确的修复方案可以从代码库和 Bug 报告中推断出来时，AI 在所有 16 次尝试中都取得了成功，包括那些深埋在不熟悉的代理内部逻辑和微妙数值边界情况中的 Bug。但当正确的修复方案依赖于未记录的 API 契约时，它在所有 12 次尝试中都失败了——涵盖了 Claude Haiku 4.5、Sonnet 5 和 Opus 4.8，并使用了三种不同的代理工作流。

More process didn’t fix the problem. In one experiment, a reviewer agent correctly identified that the proposed patch would corrupt user data and explained exactly why. It then approved the change anyway, reasoning that the issue was unlikely and belonged to a pre-existing class of problems. The failure wasn’t in detection—it was in judgment. Even when the system recognized the risk, it lacked the decision-making needed to stop the bad fix from shipping.
增加流程并不能解决问题。在一次实验中，一个审查代理正确地识别出提议的补丁会破坏用户数据，并准确解释了原因。然而，它最终还是批准了该变更，理由是该问题发生的可能性较低，且属于预先存在的问题类别。失败不在于检测，而在于判断。即使系统识别出了风险，它也缺乏阻止错误修复方案发布所需的决策能力。

### 2. Let’s start with the bugs that I tested
### 2. 从我测试的 Bug 开始

To perform this test, I select real bugs from real codebases, with real ground truth: the maintainer’s merged fix and the regression tests that shipped with it. Three selection rules did the heavy lifting.
为了进行这项测试，我从真实的开源代码库中选择了真实的 Bug，并拥有真实的“基准真理”（Ground Truth）：即维护者合并的修复方案以及随之发布的回归测试。三条选择规则起到了关键作用。

First, every bug was fixed upstream in July 2026, and it’s highly probable that the training cutoff for the latest Claude models (the 5 family) is before this period, so no model has seen the fix. Second, each fix shipped with regression tests, held out as a hidden grader the agent never sees. Third, I chose the three bugs to span difficulty, from a one-line fix to a two-file invariant repair.
首先，每个 Bug 都是在 2026 年 7 月在上游修复的，最新的 Claude 模型（5 系列）的训练截止日期很可能在此之前，因此没有任何模型见过该修复方案。其次，每个修复方案都附带了回归测试，作为代理永远无法看到的隐藏评分标准。第三，我选择了三个难度跨度较大的 Bug，从单行修复到涉及两个文件的不变量修复。

### 2.1 The easy one: ky, PR #867
### 2.1 简单的那个：ky, PR #867

ky is a small HTTP client built by Sindre Sorhus. It wraps the browser’s fetch and adds the things every app ends up needing anyway: retries, timeouts, JSON handling. The normal way to use it is to build one base client with your shared settings, then specialize it per feature.
ky 是由 Sindre Sorhus 构建的一个小型 HTTP 客户端。它封装了浏览器的 fetch API，并添加了每个应用程序最终都会用到的功能：重试、超时、JSON 处理。通常的使用方式是先用共享设置构建一个基础客户端，然后针对每个功能进行定制。

The bug: when the base client sets retry as a number, and the extension sets it as an object, the number silently vanishes. The extended client quietly falls back to the default of 2 retries. Nothing crashes. No warning. Your requests just retry fewer times than you configured, which is exactly the kind of bug nobody notices until a bad network day in production.
该 Bug 为：当基础客户端将重试次数设置为数字，而扩展客户端将其设置为对象时，该数字会静默消失。扩展后的客户端会悄悄回退到默认的 2 次重试。程序不会崩溃，也没有警告。你的请求只是比你配置的重试次数少，这正是那种在生产环境网络状况不佳之前没人会注意到的 Bug。
