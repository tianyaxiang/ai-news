C++ Index…?
C++ 索引……？

Apart from fixing bugs and minor improvements, I’ve been experimenting with migrating the index code off Java to C++. I’ve still not fully decided whether this is the direction we want to go, in general rewrites especially across language boundaries just aren’t worth it and it kinda goes against my better judgement, but we’re currently CPU bottlenecked and there might be some juice left to squeeze by skipping the JVM tax, and additionally Java really chafes for this sort of use case. Don’t get me wrong, the new Java FFM API is miles better than anything we had before, but handling off-heap memory is still awkward and leads to a bunch of duplicated implementations or reimplementations of stuff like sorting and searching algorithms that already exists for on-heap structures but not off; bobbing in and out of native code is awkward and makes the logic difficult to follow, it just chafes.
除了修复漏洞和进行小幅改进外，我一直在尝试将索引代码从 Java 迁移到 C++。我还没有完全决定这是否是我们想要的方向，通常情况下，尤其是跨语言边界的重写是不值得的，这在某种程度上违背了我的判断，但我们目前受到 CPU 的限制，跳过 JVM 的开销或许还能榨出一些性能，此外，Java 在这种用例下确实让人感到别扭。别误会，新的 Java FFM API 比我们以前拥有的任何东西都要好得多，但处理堆外内存仍然很尴尬，并导致了大量重复实现，例如那些已经存在于堆内结构但不存在于堆外的排序和搜索算法；在原生代码之间进进出出很尴尬，使得逻辑难以追踪，这确实让人不舒服。

Should be noted the reason I’m even chasing optimizations in the index boils down to the fact that for an internet search engine, performance is recall. The search engine is only as good as the number of results it can rank within the query’s execution budget. To be honest I’m not 100% convinced we’ll see that much performance impact, and if we do I doubt it will be massive, as the Java implementation is already very optimized, and what we’re mostly bottlenecked on isn’t the sort of places where you see big differences between the languages.
值得注意的是，我之所以追求索引优化，归根结底是因为对于互联网搜索引擎来说，性能就是召回率。搜索引擎的好坏取决于它在查询执行预算内能排名的结果数量。老实说，我并不百分之百确信我们会看到那么大的性能影响，即使有，我也怀疑它是否会非常巨大，因为 Java 的实现已经非常优化了，而且我们主要受限的地方并不是那种能看到两种语言之间巨大差异的地方。

Thus far the buffer pool has been translated, and part of the main inverse index structure. These are some of the most finnicky parts of the index, and a reasonable canary for whether it’s plausible. Based on what I’ve accomplished it’s encouraging to see how much more expressive C++ is for this type of work. The vastly improved ergonomics may be a motivating factor for continuing this even if the performance doesn’t materialize.
到目前为止，缓冲池和部分主倒排索引结构已经完成转换。这些是索引中最棘手的部分，也是判断其是否可行的合理试金石。基于我所取得的成果，看到 C++ 在这类工作中表现出的更强表达能力令人鼓舞。即使性能提升没有实现，大幅改善的人机工程学也可能成为继续这项工作的动力。

I’m doing this quite slowly one component at a time, measuring twice and cutting once, finding good abstractions that lean into C++’s strengths rather than doing a straight translation. In part because this is supremely fiddly and technical work, and in part because there genuinely isn’t any rush and if there is much performance to gain it’s probably in staring at the problem long enough I find better alternative approaches. I did manage to lean more into lock-free algorithms in the buffer pool for example. Translation probably won’t be finished this year at this pace.
我正在非常缓慢地一次处理一个组件，三思而后行，寻找能够发挥 C++ 优势的良好抽象，而不是进行直接翻译。部分原因是这项工作极其繁琐且技术性强，部分原因是因为确实没有任何紧迫性，如果能获得很大的性能提升，那可能在于长时间盯着问题直到找到更好的替代方案。例如，我确实在缓冲池中更多地使用了无锁算法。照此速度，翻译工作今年可能无法完成。

Many things are undecided: Haven’t decided on where to draw the interface boundary yet. Neither do I have a public git repo for this. May still scrap the entire idea as a silly boondoggle. We’ll just have to see where it goes.
许多事情尚未决定：还没有决定在哪里划分接口边界。我也没有为此建立公共 git 仓库。可能最终还是会放弃整个想法，将其视为愚蠢的浪费。我们只能走着瞧。
