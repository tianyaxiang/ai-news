Hello, Lately, I'm observing that Ubuntu's response to severe security flaws is concerning. On November 16th, details about a remote memory corruption called NoisyTCP (CVE-2026-99288) in the Linux kernel's TCP stack were published: https://www.openwall.com/lists/oss-security/2026/11/15/2 Today, nine days later, Ubuntu still has not published a fix yet: https://ubuntu.com/security/CVE-2026-99288 Other distros had a fix already available when the details were published. Likewise, a KVM host escape (CVE-2026-99312) affecting AMD virtualization published on Nov 18th has no fix yet either [3]: https://ubuntu.com/security/CVE-2026-99312

你好，最近我观察到 Ubuntu 对严重安全漏洞的响应令人担忧。11 月 16 日，关于 Linux 内核 TCP 栈中名为 NoisyTCP (CVE-2026-99288) 的远程内存损坏漏洞的详细信息被发布：https://www.openwall.com/lists/oss-security/2026/11/15/2 今天，九天过去了，Ubuntu 仍未发布修复程序：https://ubuntu.com/security/CVE-2026-99288。其他发行版在详细信息发布时就已经提供了修复程序。同样，11 月 18 日发布的、影响 AMD 虚拟化的 KVM 主机逃逸漏洞 (CVE-2026-99312) 也尚未有修复程序 [3]：https://ubuntu.com/security/CVE-2026-99312。

Ubuntu has been slow in patching another remote TCP corruption (CVE-2026-98432) lately, where it took multiple weeks until a fix was available. See also: https://chalmovsky.com/posts/wtf-ubuntu Recent news indicates that this is might be exploited in the wild: https://www.greynoise.io/blog/check-point-security-management-servers-intrusion-campaign I think everyone understands that these times aren't easy for security teams. Nevertheless, remote corruption vulnerabilities in the Linux kernel are the kind of thing where I expect updates to be available within hours, not days or weeks.

Ubuntu 最近在修补另一个远程 TCP 损坏漏洞 (CVE-2026-98432) 时也很缓慢，花费了数周时间才提供修复。另请参阅：https://chalmovsky.com/posts/wtf-ubuntu。最近的新闻表明该漏洞可能正在被野外利用：https://www.greynoise.io/blog/check-point-security-management-servers-intrusion-campaign。我想大家都明白，对于安全团队来说，现在这段时间并不容易。尽管如此，Linux 内核中的远程损坏漏洞是我期望在几小时内（而不是几天或几周内）就能获得更新的那类问题。

On a recent Ubuntu LTS system, the kernel version is 7.0.0-44. This seems to indicate that Ubuntu is not relying on longterm supported kernels from kernel.org, but is instead backporting patches to an old kernel version. On a Debian stable system, the kernel version is 6.12.118+deb13, indicating that it's based on a very recent longterm kernel from kernel.org. I would consider the backporting strategy for the kernel to be hardly viable and probably everyone should base their Linux kernels on longterm releases supported by the Linux kernel developers. -- Hanno Böck - Independent security researcher https://itsec.hboeck.de/ https://badkeys.info/ Powered by blists - more mailing lists Please check out the Open Source Software Security Wiki, which is counterpart to this mailing list.
