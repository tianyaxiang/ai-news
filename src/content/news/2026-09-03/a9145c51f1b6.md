# I got tired of paying for invoicing software, so I built my own (and open-sourced it)
# 我厌倦了为发票软件付费，于是自己开发了一个（并将其开源）

I run a small one-person software consultancy, and for the last year I've been paying a monthly SaaS fee to send maybe 8-10 invoices a month. Every renewal I'd think "this is a CRUD app with a PDF exporter, why am I paying for this" — so I finally built my own and called it Kite. It's now open source: github.com/Skye-Technology/Kite-Invoice-App

我经营着一家一人制的软件咨询公司。过去一年里，我每个月都要支付 SaaS 订阅费，而我每月可能只需要发送 8 到 10 张发票。每次续费时我都会想：“这不就是一个带 PDF 导出功能的 CRUD（增删改查）应用吗？我为什么要为它付费？”于是，我最终自己开发了一个工具，并将其命名为 Kite。现在它已经开源了：github.com/Skye-Technology/Kite-Invoice-App

### What it actually does
### 它具体能做什么

Kite is a self-hosted invoice and expense tracker for freelancers and small businesses. Nothing exotic — invoices, quotations, expenses, contacts, PDF export — but built around a few things I actually needed and kept not finding together in one tool:
* Multi-currency, with the invoice currency following the contact's default currency
* Dutch-style VAT handling — 0% / 9% / 21% / exempt per line item, plus a reverse-charge flag for cross-border invoices
* PDF generation that actually paginates correctly on long invoices (more on this below)
* A timesheet importer — upload an .xlsx export, get invoice line items back with hours converted to quantity and descriptions built from configurable project-name rules
* Expense categories with icon, balance-sheet, and VAT-deductibility flags, and gross-amount entry (type what the receipt says, the app back-calculates the net)

Kite 是一款面向自由职业者和小企业的自托管发票与费用追踪工具。功能并不花哨——涵盖发票、报价单、费用、联系人管理和 PDF 导出——但它围绕着我真正需要且一直无法在同一个工具中找到的几个核心需求构建：
* 多币种支持：发票币种自动跟随联系人的默认币种。
* 荷兰式增值税处理：支持按行项目设置 0% / 9% / 21% 或免税，并带有跨境发票的反向征税标记。
* PDF 生成：在长发票上能实现真正的正确分页（下文会详细说明）。
* 工时表导入器：上传 .xlsx 文件，即可获得转换后的发票行项目，工时自动转换为数量，描述则根据可配置的项目名称规则生成。
* 费用类别：支持图标、资产负债表标记、增值税抵扣标记，以及总额录入（只需输入收据上的金额，应用会自动反向计算净额）。

### Stack
### 技术栈

Next.js (App Router) + Prisma/PostgreSQL + S3-compatible storage (MinIO locally, R2/S3 in prod) + @react-pdf/renderer for the PDFs. Single-operator auth, no roles or permissions to manage — it's built for one person or a tiny team, not a multi-tenant SaaS.

Next.js (App Router) + Prisma/PostgreSQL + S3 兼容存储（本地使用 MinIO，生产环境使用 R2/S3）+ @react-pdf/renderer（用于生成 PDF）。采用单用户认证，无需管理角色或权限——它是为个人或小型团队打造的，而非多租户 SaaS。

### The pagination problem nobody warns you about
### 没人提醒过你的分页难题

The part I underestimated most was PDF pagination. @react-pdf/renderer has no equivalent of CSS's table-header-group, so there's no built-in way to say "repeat this header row on every page." You build pages by hand. My first attempt just packed a fixed number of rows per page. That worked fine on every invoice I tested with short, one-line descriptions. Then I imported a real 41-line invoice built from timesheet data, where some descriptions wrapped to two or three lines, and got a genuinely blank page in the middle of the PDF with a duplicated page-number label. The fix was switching from row-count budgets to estimated-height budgets: measure each row's likely rendered height and pack rows into a page until the next one would overflow an estimated available-height budget. Boring to write up, but the kind of thing that only breaks on real data, not synthetic test cases.

我最低估的部分是 PDF 分页。@react-pdf/renderer 没有 CSS 中 `table-header-group` 的等效功能，因此没有内置方法来设置“在每一页重复表头行”。你必须手动构建页面。我最初的尝试是每页填充固定行数，这在我测试的所有短描述发票上运行良好。但后来我导入了一张真实的、由工时数据生成的 41 行发票，其中一些描述换行成了两三行，结果导致 PDF 中间出现了一个完全空白的页面，且页码标签重复。解决方法是将“行数预算”改为“预估高度预算”：测量每一行可能的渲染高度，并将行填充到页面中，直到下一行会超出预估的可用高度预算为止。这写起来很枯燥，但这类问题往往只会在真实数据中暴露，而不是在合成测试用例中。

### Importing history without lying about it
### 如何在不弄虚作假的情况下导入历史数据

I had old invoices in a previous tool I was migrating away from, and wanted them in Kite for record-keeping without manually re-entering every line item — but they shouldn't look like real, editable invoices in the new system. No PDF export, no "Duplicate" action, and critically, importing them shouldn't consume the app's own next-invoice-number sequence. That turned into an `isHistorical` flag: it still counts toward dashboard totals and shows up in the invoice list (with a badge), but the UI hides actions that don't make sense for a record you're not going to re-send.

我之前使用的工具里存有旧发票，在迁移时，我希望将它们保留在 Kite 中以便记录，但又不想手动重新输入每一行项目——而且它们不应该在新系统中看起来像可编辑的真实发票。它们不应支持 PDF 导出或“复制”操作，最关键的是，导入它们时不应占用应用自身的下一个发票编号序列。于是我引入了一个 `isHistorical`（历史记录）标记：它仍然计入仪表板总额并显示在发票列表中（带有徽章），但 UI 会隐藏那些对于无需再次发送的记录来说不合理的操作。

### Why open source it
### 为什么要开源

Genuinely just: it's a solved problem for me now, and gatekeeping a CRUD app behind "buy my SaaS" felt silly. MIT licensed, Docker Compose for local dev, works against local Postgres or hosted Supabase without code changes. Issues and PRs welcome — I'm using this myself day to day.

原因很简单：对我来说，这个问题已经解决了，把一个 CRUD 应用锁在“购买我的 SaaS”门后感觉很傻。项目采用 MIT 协议，支持 Docker Compose 本地开发，无需修改代码即可连接本地 Postgres 或托管的 Supabase。欢迎提交 Issues 和 PR——我每天都在使用它。
