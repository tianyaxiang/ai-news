# Your JSON Is Valid but Your Data Is Wrong: Five Failure Modes LLM Structured Outputs Won't Catch
# 你的 JSON 格式正确但数据是错的：LLM 结构化输出无法规避的五种失效模式

Constrained decoding solved a real problem. Before grammar-based methods like Outlines and SGLang, getting valid JSON from a language model was a retry loop. You prompted, parsed, caught the trailing comma, reprompted. Constrained decoding ended that: force token selection through a finite-state machine, and every output parses. Teams adopted it fast. Schema compliance hit near 100%. And then a quiet assumption crept into production codebases: if the JSON validates against the schema, the data is correct.

约束解码（Constrained decoding）解决了一个实际问题。在出现 Outlines 和 SGLang 等基于语法的方案之前，从语言模型中获取有效的 JSON 往往是一个不断重试的循环：你编写提示词、解析、捕获末尾多余的逗号、重新提示。约束解码终结了这一切：通过有限状态机强制选择 Token，确保每一个输出都能被解析。团队迅速采用了这种技术，模式合规率接近 100%。随后，一个潜移默化的假设悄然进入了生产代码库：只要 JSON 通过了模式验证，数据就是正确的。

BAML's benchmarks say otherwise. On function-calling tasks, unconstrained generation with post-hoc parsing reached 93.63% accuracy; constrained decoding on the same model scored 91.37%. The always-valid JSON was less accurate than the sometimes-broken JSON.

BAML 的基准测试结果却并非如此。在函数调用任务中，采用事后解析的非约束生成准确率为 93.63%；而同一模型在约束解码下的准确率仅为 91.37%。这意味着“总是有效”的 JSON 反而比“偶尔出错”的 JSON 准确度更低。

I started tracking this after a classification pipeline I built began returning plausible but fabricated values on roughly one in twelve runs. The JSON always parsed. Pydantic never complained. It took weeks to notice, because every downstream check was structural.

我是在我构建的一个分类流水线开始出现问题后注意到这一点的：大约每 12 次运行中就有一次会返回看似合理但实则虚构的值。JSON 总是能解析成功，Pydantic 也从未报错。我花了数周时间才发现，因为所有的下游检查都仅限于结构层面。

Five failure modes keep showing up. They all produce schema-valid output that breaks your pipeline silently:
* Enum hallucination: valid enum, wrong meaning
* Confident fabrication: plausible values in free-text fields
* Cross-field contradiction: fields valid individually, impossible together
* Distributional collapse: convergence on safe defaults
* Array hallucination: fabricated entries instead of empty arrays

有五种失效模式反复出现。它们产生的输出虽然符合模式规范，却会悄无声息地破坏你的流水线：
* 枚举幻觉（Enum hallucination）：枚举值有效，但含义错误。
* 自信的捏造（Confident fabrication）：在自由文本字段中填入看似合理但虚构的值。
* 跨字段矛盾（Cross-field contradiction）：字段单独看有效，但组合在一起逻辑不通。
* 分布坍缩（Distributional collapse）：模型倾向于输出“安全”的默认值。
* 数组幻觉（Array hallucination）：本应返回空数组时，却捏造了条目。

### Constrained Decoding: The Problem It Actually Solved
### 约束解码：它真正解决的问题

Structured output used to mean hoping the model behaved. Constrained decoding was built to fix that, and it did, just not the whole problem. The progression was real. Prompt-and-pray JSON, where you appended "respond in JSON format" and crossed your fingers, gave way to regex-guided generation (LMQL), then to grammar-based constrained decoding.

过去，结构化输出意味着祈祷模型能按规矩行事。约束解码的出现就是为了解决这个问题，它确实做到了，但并没有解决所有问题。这一演进过程是真实的：从“提示并祈祷”（Prompt-and-pray）式 JSON（即在提示词后加上“以 JSON 格式回复”并祈祷成功），演变为基于正则表达式的生成（LMQL），再到如今基于语法的约束解码。

XGrammar, now the default backend for vLLM and TensorRT-LLM, adds near-zero overhead per token. The syntax problem is solved. But solving syntax created a blind spot. Schema validation checks whether a field is typed correctly: a string is a string, a number is a number. It says nothing about whether that string or number is correct.

XGrammar 现在是 vLLM 和 TensorRT-LLM 的默认后端，它几乎不会增加每个 Token 的开销。语法问题解决了，但解决语法问题却产生了一个盲点。模式验证只检查字段类型是否正确：字符串是否为字符串，数字是否为数字。它无法判断该字符串或数字的内容是否正确。

A lock on a filing cabinet keeps the drawers organized. It says nothing about whether the papers inside are accurate. Schema validation works the same way.

文件柜上的锁能让抽屉保持整齐，但它无法保证里面的文件内容是否准确。模式验证的作用也是如此。

The reason this matters: forcing a model into a strict output format costs it something. It has to spend part of its attention on staying inside the format, instead of spending all of it on getting the actual answer right.

这之所以重要，是因为强迫模型遵循严格的输出格式是有代价的。模型必须分出一部分“注意力”来维持格式，而不是将全部精力用于得出正确的答案。

Lee et al. measured that cost directly. Across open-weight models, forcing structured output formats produced a 3-to-9 percentage point accuracy drop. On math reasoning tasks specifically, where getting the reasoning right matters more than the format, the gap exceeded 15 percentage points.

Lee 等人直接测量了这一代价。在开源模型中，强制执行结构化输出格式会导致准确率下降 3 到 9 个百分点。特别是在数学推理任务中，由于推理过程比格式更重要，准确率差距甚至超过了 15 个百分点。

Tam et al. found the same pattern from a different angle: the stricter the formatting rules, the worse the reasoning got. The format is not free, and most teams aren't accounting for that cost.

Tam 等人从另一个角度发现了同样的规律：格式规则越严格，推理能力就越差。格式并非免费的，而大多数团队并没有考虑到这一成本。

### Five Failure Modes: What Survives Your Schema
### 五种失效模式：那些逃过模式验证的问题

Schema validation catches type errors. It does not catch these five failure modes, because each one produces output that is structurally valid and substantively wrong.

模式验证可以捕获类型错误，但无法捕获以下五种失效模式，因为它们产生的输出在结构上是有效的，但在实质上是错误的。

**Enum hallucination.** The model picks a valid enum value that is semantically wrong for the input. Consider a priority enum of ["low", "normal", "high", "urgent"]: the grammar guarantees one of those four values, but it does not weight them by input context. The model can return "urgent" on a routine request or "low" on a critical one, and the schema will accept both.

**枚举幻觉。** 模型选择了一个有效的枚举值，但从语义上讲对输入而言是错误的。以优先级枚举 ["low", "normal", "high", "urgent"] 为例：语法保证了输出必为这四个值之一，但它不会根据输入上下文进行加权。模型可能会对常规请求返回“紧急”，或对关键请求返回“低”，而模式验证会照单全收。

**Confident fabrication.** Free-text fields return plausible but invented data. BAML demonstrated this by submitting a photo of an elephant as a receipt: constrained decoding returned a complete, schema-valid expense report instead of refusing. Constrained decoding eliminates the model's ability to refuse or express uncertainty. The schema requires a value; the model provides one, whether or not the input supports it.

**自信的捏造。** 自由文本字段返回看似合理但虚构的数据。BAML 曾演示过：提交一张大象的照片作为收据，约束解码返回了一份完整且符合模式的费用报销单，而不是拒绝。约束解码剥夺了模型拒绝或表达不确定性的能力。模式要求提供值，模型就会提供，无论输入内容是否支持。

**Cross-field contradiction.** Schema validation checks each field in isolation. It never checks whether the fields agree with each other. A sentiment extractor can return {"sentiment": "positive", "score": 0.1}, a positive label with a score close to zero, which should mean negative. A date parser can return {"start": "2026-03-15", "end": "2026-03-10"}, an end date before the start date. Both outputs pass every individual field's validation. Neither makes sense once you look at the record as a whole, and no single-field validator is built to catch that, because the constraint lives between fields, not inside any one of them.

**跨字段矛盾。** 模式验证是孤立地检查每个字段的，它从不检查字段之间是否一致。情感提取器可能返回 {"sentiment": "positive", "score": 0.1}，即标签为“正面”但分数接近零（这本应代表负面）。日期解析器可能返回 {"start": "2026-03-15", "end": "2026-03-10"}，即结束日期早于开始日期。这两个输出都能通过单个字段的验证，但从整体记录来看都不合理。没有任何单字段验证器能捕获此类错误，因为约束存在于字段之间，而非字段内部。

**Distributional collapse.** The model converges on safe, generic values across different inputs. Constrained decoding biases toward high-probability tokens within the valid set, and "safe" defaults (0.95, "medium", "general") carry higher base probability than context-specific values. I caught this when confidence scores in a classification pipeline flatlined at 0.98 for three weeks. Collin Wilkins documents a similar case where confidence was 0.99 on every output, including gibberish. Every record had valid types, correct enums, reasonable numbers. The distribution had stopped moving, and nothing alarmed because each individual output was structurally correct.

**分布坍缩。** 模型在面对不同输入时，趋向于输出安全、通用的值。约束解码偏向于选择有效集合内高概率的 Token，而“安全”的默认值（如 0.95、“中等”、“通用”）通常比特定于上下文的值具有更高的基础概率。我是在分类流水线的置信度分数连续三周平稳在 0.98 时发现这一点的。Collin Wilkins 记录过类似案例：即使是乱码，输出的置信度也是 0.99。每条记录的类型、枚举和数字看起来都合理，但分布已经停止变化，且由于每个输出在结构上都是正确的，因此没有任何警报触发。

**Array hallucination.** Models resist returning empty arrays. Under constrained decoding, [] is a low-probability token sequence because the grammar weights object-producing paths more heavily than the empty-array path. When a schema requires an items field of type array, the model fabricates entries rather than returning nothing. In extraction tasks, this produces phantom results: your pipeline reports "found 3 matches" when the correct answer is zero.

**数组幻觉。** 模型倾向于不返回空数组。在约束解码下，[] 是一个低概率的 Token 序列，因为语法对生成对象的路径加权远高于空数组路径。当模式要求一个数组类型的字段时，模型会捏造条目而不是返回空值。在提取任务中，这会导致虚假结果：你的流水线报告“找到 3 个匹配项”，而正确答案其实是零。
