# Stop counting tokens, start counting what ships

SponsoredProvided byHPE When a developer gives an AI agent a coding task, the agent does more than answer once. It plans, generates code, runs tests, and repeats the process to correct errors. A single task can use 10 to 50 times more tokens than a basic chat prompt. The more useful the agent becomes, the more calls it makes. With per-token pricing, the workflows creating the most value can also become the most expensive.

由 HPE 赞助提供。当开发人员向 AI 智能体下达编码任务时，智能体所做的不仅仅是回答一次。它会进行规划、生成代码、运行测试，并重复该过程以纠正错误。单个任务使用的 Token 数量可能是基础聊天提示词的 10 到 50 倍。智能体越有用，它调用的次数就越多。在按 Token 定价的模式下，创造价值最高的工作流往往也可能变得最昂贵。

The financial pressure is already visible. Uber reportedly exhausted its entire 2026 AI budget by April after expanding its use of Claude Code. GitHub Copilot moved from flat-rate pricing to metered credits. Gartner predicts that AI coding token costs will surpass average developer salaries by 2028. The natural response is rationing usage caps, seat limits, and approvals before developers launch agents. But blanket limits can restrict the workflows delivering value. They also optimize the wrong number. Cost per token measures consumption, not results. Some spending reflects waste, including retries and runaway loops. Some represents the work of shipping software. A meter cannot distinguish them, and neither can a spending cap.

财务压力已经显现。据报道，Uber 在扩大使用 Claude Code 后，到 4 月份就耗尽了其 2026 年全年的 AI 预算。GitHub Copilot 已从固定费率定价转向计量积分制。Gartner 预测，到 2028 年，AI 编码的 Token 成本将超过开发人员的平均工资。自然的反应是进行配给，即在开发人员启动智能体之前设置使用上限、席位限制和审批流程。但一刀切的限制可能会阻碍那些能够创造价值的工作流。它们优化的指标也是错误的。单位 Token 成本衡量的是消耗，而非结果。部分支出反映的是浪费，包括重试和失控的循环；而另一部分则代表了交付软件的工作量。计量器无法区分两者，支出上限也做不到。

Measure the software that ships A better measure is cost per merged pull request: total AI-assisted development cost divided by the number of changes that pass review and are merged. Track rework and defects alongside it so cheaper changes do not conceal lower quality. If that cost falls as AI usage rises, without compromising quality, developers are converting more consumption into useful software. The question is not how many tokens they use, but how much finished work the investment produces. Improving that equation requires two changes: reserve expensive inference for tasks that need it, and lower the cost of routine work.

衡量交付的软件。一个更好的衡量指标是“每个合并拉取请求（PR）的成本”：即 AI 辅助开发的总成本除以通过审查并合并的变更数量。同时跟踪返工和缺陷，以确保更便宜的变更不会掩盖较低的质量。如果该成本随着 AI 使用量的增加而下降，且不影响质量，那么开发人员就是在将更多的消耗转化为有用的软件。问题不在于他们使用了多少 Token，而在于这项投资产生了多少成品工作。改善这一等式需要两个改变：将昂贵的推理留给真正需要的任务，并降低日常工作的成本。

Match the model to the task Agentic coding does not require the most powerful model at every step. Use a frontier model, or an on-premises flagship when policy requires it, for difficult planning and novel reasoning. Route suitable work, including code generation, test creation, and repeated refactoring, to open-weight models you operate yourself. A gateway can route requests according to task complexity, data sensitivity, cost, and latency. This reserves premium inference for the moments that justify it rather than applying premium pricing to an entire workflow. Meter the exception, not the workload. Open-weight models make this division increasingly practical.

将模型与任务匹配。智能体编码并不需要在每一步都使用最强大的模型。对于困难的规划和新颖的推理，请使用前沿模型，或者在政策要求时使用本地部署的旗舰模型。将合适的工作（包括代码生成、测试创建和重复重构）路由到您自己运营的开放权重模型。网关可以根据任务复杂度、数据敏感性、成本和延迟来路由请求。这使得高级推理仅在必要时使用，而不是将高昂的定价应用于整个工作流。要计量的是例外情况，而不是工作负载。开放权重模型使得这种划分变得越来越可行。

Software-engineering benchmarks show that leading open-weight models can approach frontier performance on some tasks. That does not establish equivalence across every repository or workflow. Evaluate candidates against your own code, tests, and acceptance criteria before assigning production work. Change the economics of repeated use Next, decide who owns the capacity. With rented inference, every call adds to the bill. With owned capacity, most of the cost is committed upfront, so each additional call gets cheaper as usage grows. The economics are simple: per-token pricing makes heavy use more expensive, while owned capacity becomes more efficient as teams use it more.

软件工程基准测试表明，领先的开放权重模型在某些任务上可以接近前沿模型的性能。但这并不意味着它们在每个代码库或工作流中都等同。在分配生产任务之前，请根据您自己的代码、测试和验收标准来评估候选模型。改变重复使用的经济性。接下来，决定由谁拥有算力。使用租赁的推理服务，每次调用都会增加账单。而拥有算力意味着大部分成本是预先投入的，因此随着使用量的增加，每次调用的成本会变得更低。经济账很简单：按 Token 定价使得高频使用变得更贵，而拥有算力则随着团队使用量的增加而变得更高效。

Ownership is not free, though. Power, operations, maintenance, and depreciation all must be considered. The number that matters is the fully loaded cost per merged pull request. Owned capacity also delivers a type of value that never appears on an invoice: control over sensitive code. When code generation and testing run on-premises, proprietary code stays inside the enterprise. Only approved planning prompts and governed exceptions go to external models, through a gateway the organization controls. That opens the sensitive repositories where security usually stalls adoption, and where the biggest gains are waiting.

不过，拥有算力并非没有成本。电力、运营、维护和折旧都必须考虑在内。真正重要的数字是“每个合并拉取请求的完全分摊成本”。拥有算力还提供了一种永远不会出现在发票上的价值：对敏感代码的控制。当代码生成和测试在本地运行时，专有代码会保留在企业内部。只有经过批准的规划提示词和受控的例外情况才会通过组织控制的网关发送到外部模型。这解锁了那些通常因安全问题而阻碍采用的敏感代码库，而那里正是最大收益所在。
