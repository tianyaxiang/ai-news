# How to Work with AI Coding Agents
# 如何使用 AI 编程代理

Let me start this by saying I am a big fan of coding agents; they help streamline code production. But based on the questions I get asked and the experiences people share with me, they are not used in the best way. That being said, let's talk about coding agents. The main premise of a coding agent is that it is a tool that helps you write better code. You can do that by providing coding agents with context, breaking down problems, reviewing their work, and keeping yourself in control. That last part is the most important!

首先，我想说我非常推崇编程代理（coding agents）；它们有助于简化代码生产流程。但根据我收到的提问以及人们分享的经验来看，大家并没有以最佳方式使用它们。话虽如此，让我们来聊聊编程代理。编程代理的核心前提是：它是一个能帮你写出更好代码的工具。你可以通过为代理提供上下文、拆解问题、审查其工作成果以及保持自身掌控力来实现这一目标。最后一点最为重要！

Not that long ago, when you were able to use AI to generate code, you would get only a few lines of autocomplete. Then came AI coding assistants capable of producing entire functions or explaining errors. Fast forward a couple of years and many technological advances, and we now have a different situation. Coding agents. Rather than just proposing code, an agent can examine a repository, create and modify files, run tests, read error messages, make further changes, and repeat the process until the desired goal is achieved. You, as a developer, are no longer asking the AI, "Could you write that function?" Instead, you are now asking: "Can you take on this problem, go through the codebase, and put in a solution?"

不久前，当你使用 AI 生成代码时，通常只能得到几行自动补全的内容。随后出现了能够生成完整函数或解释错误的 AI 编程助手。快进几年，随着技术的飞速进步，我们现在面临的情况已大不相同——那就是编程代理。代理不仅仅是提出代码建议，它还可以检查代码库、创建和修改文件、运行测试、读取错误信息、进行后续更改，并重复这一过程，直到实现预定目标。作为开发者，你不再是问 AI：“你能写那个函数吗？”相反，你现在问的是：“你能处理这个问题，通读代码库，并给出一个解决方案吗？”

Some may now argue that if AI takes on more of the programming work, then what should the programmer actually be doing? I like to think about it as the programmer still doing the heavy thinking and planning, and using AI as a tool to make the process more efficient (for the most part)!

有些人可能会争论说，如果 AI 承担了更多的编程工作，那么程序员到底应该做什么？我倾向于认为，程序员依然负责深度思考和规划，并将 AI 作为一种工具，使整个过程变得更加高效（在大多数情况下）！

### What makes coding agents different?
### 编程代理有何不同？

Before we go any deeper, we need to distinguish the different forms of AI-assisted programming available and how they progressed over time. Let’s start with autocomplete tools. An autocomplete tool can predict the next line of code. These tools are available in most code editors and on online platforms like Google Colab. Their whole job is to try to predict what you will type next.

在深入探讨之前，我们需要区分目前可用的不同形式的 AI 辅助编程，以及它们是如何随时间演进的。让我们从自动补全工具开始。自动补全工具可以预测下一行代码。这些工具在大多数代码编辑器和 Google Colab 等在线平台上都有提供。它们的全部工作就是尝试预测你接下来要输入的内容。

Then, we have AI assistants, which can respond to simple requests such as: "Write a Python function to parse this file." Finally, we have coding agents that can turn a high-level goal into reality. "Add support for parsing CSV input. Use the existing parser architecture, add tests, and make sure the current test suite still passes."

接下来是 AI 助手，它们可以响应简单的请求，例如：“写一个 Python 函数来解析这个文件。”最后是编程代理，它们可以将高层目标变为现实，例如：“添加对解析 CSV 输入的支持。使用现有的解析器架构，添加测试，并确保当前的测试套件依然通过。”

The difference is the loop. So, instead of just generating text, the agent can interact with its environment. Which is precisely what gives it its power and which makes working with it different.

区别在于“循环”。因此，代理不仅仅是生成文本，它还能与环境进行交互。这正是它强大之处，也是它与众不同的工作方式。

You have probably come across this scenario if you've used a coding agent. You give it a seemingly straightforward instruction: "Build authentication for my application." The agent begins enthusiastically to change your files; it creates new classes, adds dependencies, and maybe even alters the database. In the end, you end up with a great deal of code, code that may not be the code you actually wanted. This is the point where people start giving up on coding agents, and blaming the model. But the issue here wasn’t the model; rather, the instructions specify too little.

如果你使用过编程代理，可能遇到过这种情况：你给它一个看似简单的指令：“为我的应用程序构建身份验证。”代理会热情地开始修改你的文件；它创建新类、添加依赖项，甚至可能修改数据库。最终，你得到了一大堆代码，但这些代码可能并不是你真正想要的。这时，人们开始放弃使用编程代理，并责怪模型。但问题不在于模型，而在于指令过于简单。

A better request might be: "Add email/password authentication. First inspect the existing user and authentication code. Do not modify the database yet. Follow the existing error-handling pattern. Add tests for: valid login, invalid password, unknown user. Before making changes, explain your plan." The second request gives the agent something much more valuable than additional words; it gives it constraints.

一个更好的请求应该是：“添加邮箱/密码身份验证。首先检查现有的用户和身份验证代码。暂时不要修改数据库。遵循现有的错误处理模式。为以下情况添加测试：有效登录、无效密码、未知用户。在进行更改之前，先解释你的计划。”第二个请求赋予了代理比单纯的文字描述更有价值的东西：它赋予了代理约束条件。

### Context Matters More than Prompts
### 上下文比提示词更重要

The prompt you use is very important, but without context, it can only do so much. If you are asking an agent to modify a repo, the repo itself contains a lot of context, such as existing architecture, naming conventions, dependencies, tests, configuration, and documentation. Giving an agent a prompt without context is like driving a car without a GPS in a new country! Both will get you somewhere, but not where you want to go.

你使用的提示词非常重要，但如果没有上下文，它的作用有限。如果你要求代理修改一个代码库，代码库本身就包含了大量的上下文，例如现有的架构、命名规范、依赖项、测试、配置和文档。给代理一个没有上下文的提示词，就像在陌生的国家开车却不使用 GPS！两者都能让你到达某个地方，但未必是你想要去的地方。

For example, a prompt like: "Fix the bug in the parser." will not get you the same results as this one: "Fix the bug in src/parser.py. Before changing anything, read: README.md, src/parser.py, tests/test_parser.py. Follow the existing error-handling pattern. Run the parser tests after making the change." The second prompt provides the model with an improved environment for reasoning. That is why project-level instructions and documentation are becoming increasingly important when working with coding agents.

例如，像“修复解析器中的错误”这样的提示词，其结果远不如这一条：“修复 src/parser.py 中的错误。在进行任何更改之前，请阅读：README.md, src/parser.py, tests/test_parser.py。遵循现有的错误处理模式。更改后运行解析器测试。”第二个提示词为模型提供了更好的推理环境。这就是为什么在使用编程代理时，项目级的说明和文档变得越来越重要。

It is worth pausing here and emphasizing that longer prompts aren't necessarily better. In most cases, a good prompt is the one that shows the agent where to look. Another important thing to pay attention to is: don’t ask the agent to change code right away, instead follow this loop: Ask → Inspect → Plan → Implement → Test → Review.

这里值得停下来强调一下：更长的提示词并不一定更好。在大多数情况下，好的提示词是那些能告诉代理“去哪里看”的提示词。另一个需要注意的重要事项是：不要让代理立即修改代码，而是遵循这个循环：询问 → 检查 → 规划 → 执行 → 测试 → 审查。

Start by asking the agent to inspect the repository without making changes. For example: "First inspect the repository. Do not modify any files. Identify: Where this functionality currently lives. Which files are likely to change. Existing tests related to it. Any architectural constraints. Then propose an implementation plan." This step will save you a lot of time (and potential mistakes), as it gives you a chance to spot a misunderstanding before the agent acts on it by modifying 15 files. Once you can see the agent’s logic, you can start prompting precise changes.

首先要求代理检查代码库而不进行任何更改。例如：“首先检查代码库。不要修改任何文件。识别：此功能目前位于何处。哪些文件可能会被更改。与此相关的现有测试。任何架构约束。然后提出实施计划。”这一步将为你节省大量时间（并避免潜在错误），因为它让你有机会在代理修改 15 个文件之前发现误解。一旦你能看到代理的逻辑，就可以开始提示精确的更改了。

### Focus on Small, Testable Problems
### 专注于小而可测试的问题

One thing I see a lot of people do is give the agent a massive task, like: "Rewrite this entire application." It will be difficult to review the agent's ability to make large changes, because you will have a lot of code to go through! Instead, break the work into small tasks and, ideally, test after each addition: "Task 1: Add the parser class. Task 2: Add unit tests. Task 3: Integrate it with the existing pipeline. Task 4: Refactor duplicated code." In this case, if there's a problem, you'll have a good idea of the location where it happened! Which is a skill that is useful beyond AI; it is good software engineering.

我看到很多人做的一件事是给代理一个巨大的任务，比如：“重写整个应用程序。”审查代理进行大规模更改的能力将非常困难，因为你需要检查大量的代码！相反，应将工作拆分为小任务，理想情况下，在每次添加后进行测试：“任务 1：添加解析器类。任务 2：添加单元测试。任务 3：将其集成到现有流水线中。任务 4：重构重复代码。”在这种情况下，如果出现问题，你就能清楚地知道问题发生的位置！这是一种超越 AI 的技能；这是优秀的软件工程实践。
