# Someone reported java4shell bug in September 2026

In StubGenerator::generate_base64_decodeBlock() (x86_64 AVX-512 VBMI path), L_finalBit handles 1-63 leftover bytes with a masked vector sequence that computes output_size = (len/4)*3. Valid inputs always have a length multiple of 4, so this bug triggers only on invalid inputs: with length < 4 (e.g. "A".repeat(64)+"=" leaves 1 byte after L_process64Loop), output_size starts at 0 and the padding path decrements it below zero, producing a wrong output_mask. The stub stores past the logical output length before returning to Java, corrupting the heap.

在 StubGenerator::generate_base64_decodeBlock()（x86_64 AVX-512 VBMI 路径）中，L_finalBit 使用掩码向量序列处理 1-63 个剩余字节，该序列计算 output_size = (len/4)*3。有效输入的长度始终是 4 的倍数，因此该错误仅在无效输入时触发：当长度 < 4 时（例如 "A".repeat(64)+"=" 在 L_process64Loop 后留下 1 个字节），output_size 从 0 开始，填充路径将其减至零以下，从而产生错误的 output_mask。存根在返回 Java 之前越过逻辑输出长度进行存储，导致堆损坏。

The suggested fix is to early-return to Java if length < 4.

建议的修复方法是如果长度 < 4，则提前返回 Java。
