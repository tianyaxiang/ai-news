# Logfire Data Model
OpenTelemetry data (the data that Logfire ingests) is semi-structured data. It contains a mix of: Fixed schema fields (timestamp, span name, etc.) Semi-structured attributes (HTTP status codes, user IDs, regions, etc.) Semi-structured data is sent via attributes (per-span key-value pairs) or resource attributes (otel_resource_attributes in Logfire; these are per-resource key-value pairs where a resource is a service/k8s pod/etc, essentially an instance of your application or service).

# Logfire 数据模型
OpenTelemetry 数据（即 Logfire 摄取的数据）属于半结构化数据。它包含以下混合内容：固定模式字段（时间戳、跨度名称等）以及半结构化属性（HTTP 状态码、用户 ID、区域等）。半结构化数据通过属性（每个跨度的键值对）或资源属性（Logfire 中的 otel_resource_attributes；这些是每个资源的键值对，其中资源指服务/k8s pod 等，本质上是应用程序或服务的一个实例）进行发送。

# How we started: fast JSON parsing
Pydantic started as a library to validate and parse JSON data efficiently. When we built Logfire, we initially stored all attributes as JSON blobs in a single column and relied on Jiter (one of the fastest JSON parsers out there in any language) to rip through the JSON data as quickly as possible. This is the layout detailed above (attributes: Utf8View (JSON)). This approach was simple but made a fundamental mistake: we were optimizing to do work faster, but we couldn't really avoid doing the work. Compression is also suboptimal since a single varying attribute makes Parquet level dictionary compression ineffective and even zstd struggles with highly variable data, all the JSON syntax overhead, etc. The biggest problem really ends up being extra IO: since most of our data is stored on object storage, extra IO from downloading large JSON blobs, and especially the latency of starting these downloads, ends up dominating query runtimes much more so than any CPU work.

# 我们最初的做法：快速 JSON 解析
Pydantic 最初是一个用于高效验证和解析 JSON 数据的库。在构建 Logfire 时，我们最初将所有属性作为 JSON 二进制大对象（blob）存储在单个列中，并依赖 Jiter（目前各语言中最快的 JSON 解析器之一）尽可能快地处理 JSON 数据。这就是上述布局（attributes: Utf8View (JSON)）。这种方法很简单，但犯了一个根本性的错误：我们是在优化工作速度，却无法真正避免这些工作。压缩效果也不理想，因为单个变化的属性会使 Parquet 级别的字典压缩失效，即使是 zstd 在处理高度可变的数据、所有 JSON 语法开销等问题时也很吃力。最大的问题实际上是额外的 IO：由于我们的大部分数据存储在对象存储上，下载大型 JSON 二进制大对象带来的额外 IO，尤其是启动这些下载的延迟，最终对查询运行时间的影响远超任何 CPU 工作。

# Shredding columns to save IO and compute
To make queries fast, we need to avoid unnecessary work. For normal columns DataFusion / Parquet avoid unnecessary work by using columnar storage (allowing reading only the columns you need) and zone maps / min-max statistics (allowing skipping entire row groups or pages that don't match your filter predicates). So when you write a query like:
SELECT count(*) FROM records WHERE duration < 0;
The system can efficiently read just the duration column and skip row groups where the max duration is < 0 based on the stored statistics. In this case this is a valid query, duration is a f64 so in theory it could have values <0. In practice though duration is always >= 0 so this query will be very fast: based on statistics we know no rows match and we can return 0 immediately.

# 通过切片列来节省 IO 和计算资源
为了加快查询速度，我们需要避免不必要的工作。对于普通列，DataFusion / Parquet 通过使用列式存储（允许仅读取所需的列）和区域映射/最小-最大统计信息（允许跳过不符合过滤条件的整个行组或页面）来避免不必要的工作。因此，当你编写如下查询时：
SELECT count(*) FROM records WHERE duration < 0;
系统可以高效地仅读取 duration 列，并根据存储的统计信息跳过最大持续时间小于 0 的行组。在这种情况下，这是一个有效的查询，duration 是 f64 类型，理论上可以有小于 0 的值。但在实践中，持续时间总是大于等于 0，因此该查询会非常快：根据统计信息，我们知道没有行匹配，因此可以立即返回 0。

So how can we enable this for semi-structured data like attributes stored as JSON? Our initial solution was static shredding: we manually picked a small set of commonly queried attributes (like http.status_code, http.method, etc.) and extracted these into their own strongly typed columns during ingestion. So when we receive:
attributes {'http.response.status_code': 200, 'url.full': 'https:‎//example.com?foo=bar'} {'my_llm_response': 'large text'} {'user_id': '123'}
Assuming our hardcoded shredding configuration extracts http.response.status_code, url
