TL;DR: Retry a failed email API call only when the response is plausibly transient, use capped exponential backoff with jitter, and write an immutable attempt record before each sleep. For a B2B marketplace order, the useful artifact is not merely sent=true; it is a chain showing which order was notified, which policy decision was made, what the transport returned, and when the next attempt became eligible. The decision rule is deliberately boring: classify first, schedule second, send third, and record every transition. A 429 or a temporary 5xx can justify a later attempt. A malformed request, an authentication failure, or a permanent recipient rejection should go to review or a dead-letter path instead. Replaying every error at increasing intervals creates duplicate messages, obscures the real failure, and makes compliance evidence harder to defend. That is the failure boundary.

简而言之：仅在响应被视为暂时性故障时才重试失败的电子邮件 API 调用，使用带有抖动（jitter）的上限指数退避算法，并在每次休眠前写入不可变的尝试记录。对于 B2B 市场订单，有用的凭证不仅仅是“已发送=真”；它应该是一个完整的链条，显示通知了哪个订单、做出了什么策略决策、传输层返回了什么，以及下一次尝试何时生效。决策规则应当刻意保持简单：先分类，再调度，后发送，并记录每一次转换。429 或临时的 5xx 错误可以作为后续重试的理由。而格式错误的请求、身份验证失败或永久性的收件人拒绝则应进入审核或死信队列。盲目地以递增间隔重试每一个错误会导致重复消息，掩盖真实故障，并使合规性证据难以辩护。这就是故障边界。

What evidence does a seller notification actually need? The scenario is a marketplace seller receiving notice of a new order. The notification service owns delivery attempts; the order service owns the order itself. Keep those responsibilities separate. The attempt record should contain an order identifier, notification identifier, recipient address or a privacy-preserving reference to it, policy version, attempt number, decision, response class, and UTC timestamps. Store the provider response body only under a retention rule reviewed for personal data. A useful record distinguishes accepted, retry_scheduled, permanent_failure, and cancelled. It should preserve the idempotency key used for the request. That key does not make an arbitrary remote API idempotent by magic, but it gives a compatible transport a way to suppress an accidental replay and gives an investigator something concrete to correlate. Record it.

卖家通知实际上需要什么证据？场景是市场卖家收到新订单通知。通知服务负责处理投递尝试，而订单服务负责管理订单本身。请保持这些职责分离。尝试记录应包含订单标识符、通知标识符、收件人地址或其隐私保护引用、策略版本、尝试次数、决策、响应类别以及 UTC 时间戳。仅在经过个人数据审查的保留规则下存储提供商的响应正文。一份有用的记录应区分“已接受”、“已调度重试”、“永久失败”和“已取消”状态。它还应保留请求中使用的幂等键。该键并不能神奇地使任意远程 API 具备幂等性，但它为兼容的传输方式提供了一种抑制意外重放的方法，并为调查人员提供了可关联的具体依据。请务必记录它。

Email has several layers. An HTTP API may accept a submission while later mail processing produces a bounce or delivery event. SPF is an authorization mechanism for hosts sending mail for a domain; it is not proof that a mailbox accepted a message. Record API acceptance as one fact, and downstream delivery or bounce evidence as another. What are sound practices for retrying failed email API calls? Start with the response class, not the number of attempts. A 429 Too Many Requests response is a rate signal; honor Retry-After when present and parseable, while still applying an operational maximum. A 5xx response generally indicates a server-side problem, but the remote contract is the authority. Transport timeouts and connection resets are ambiguous: the request may have reached the remote system before the client lost the response, so retry them only with an idempotency strategy and a bounded budget. Do not retry a 400 caused by invalid payload data, a 401 or 403 caused by credentials or policy, or a confirmed permanent recipient rejection. A retry loop cannot repair bad data. It can multiply traffic and delay the queue behind a message that should have been quarantined. Bound it.

电子邮件包含多个层级。HTTP API 可能接受了提交，但后续的邮件处理可能会产生退信或投递事件。SPF 是用于验证主机发送域邮件的授权机制，它并非邮箱已接收消息的证明。应将 API 接受视为一个事实，将下游的投递或退信证据视为另一个事实。重试失败的电子邮件 API 调用有哪些稳妥的做法？应从响应类别入手，而非重试次数。429（请求过多）响应是一个速率信号；在存在且可解析的情况下，应遵守 Retry-After 头部，同时应用操作上限。5xx 响应通常表示服务器端问题，但应以远程协议约定为准。传输超时和连接重置具有歧义：请求可能在客户端丢失响应前已到达远程系统，因此仅在具备幂等策略和有限预算的情况下重试。不要重试由无效负载数据导致的 400 错误、由凭据或策略导致的 401 或 403 错误，以及已确认的永久性收件人拒绝。重试循环无法修复错误数据。它只会成倍增加流量，并阻塞本应被隔离的消息队列。请务必设置边界。

For attempt n, a common schedule is base * 2^n, capped at a maximum, then randomized with jitter so a fleet does not wake every worker on the same boundary. The base and cap belong in capacity planning: model worst-case retry volume against API quota, queue depth, worker concurrency, and the notification SLO. As concrete policy inputs, a 30-second request deadline and a 15-minute retry horizon can be useful starting values for review, but they are not universal constants; measure queue age and dependency behavior before adopting them. The queue math is easy to underestimate. Suppose 500 workers each hold one retryable job and the dependency returns 429 for two minutes. If every worker wakes at the same second, the second wave recreates the rate-limit event, and a queue that looked healthy before the incident can become a second source of load. Full jitter turns that synchronized wave into a distribution, while a cap prevents a single seller notification from consuming capacity indefinitely. Capacity planning should include the initial send plus every eligible retry, the number of workers that can become runnable during the same interval, the API quota's refill behavior, and the delay introduced by a database lease. The operational record should show the chosen delay, the cap, and the policy version so an auditor can reproduce the decision without guessing what the worker knew at the time.

对于第 n 次尝试，常见的调度方式是 base * 2^n，并设置最大上限，然后加入随机抖动，以防止整个集群在同一时间唤醒所有工作进程。基数和上限属于容量规划范畴：需根据 API 配额、队列深度、工作进程并发数和通知 SLO 来建模最坏情况下的重试量。作为具体的策略输入，30 秒的请求截止时间和 15 分钟的重试期限是可供审查的有用初始值，但它们并非通用常量；在采用前请先测量队列时效和依赖项行为。队列计算很容易被低估。假设 500 个工作进程各持有一个可重试任务，而依赖项在两分钟内返回 429。如果每个工作进程都在同一秒唤醒，第二波请求会再次触发限流事件，原本健康的队列可能因此成为二次负载源。完全抖动（Full jitter）将这种同步波转化为分布，而上限则防止单个卖家通知无限期占用容量。容量规划应包括初始发送及所有符合条件的重试、同一时间间隔内可运行的工作进程数量、API 配额的补充行为以及数据库租约引入的延迟。操作记录应显示所选延迟、上限和策略版本，以便审计人员无需猜测工作进程当时的状态即可重现决策。

Here is the policy boundary in Go. It has no vendor-specific endpoint, so the decision can be tested without network I/O.

以下是 Go 语言中的策略边界实现。它不包含任何特定于供应商的端点，因此可以在无需网络 I/O 的情况下测试决策逻辑。

```go
package retry
import (
	"math/rand"
	"strconv"
	"strings"
	"time"
)

type Decision struct {
	Retry bool
	Delay time.Duration
	Reason string
}

func Next(status int, retryAfter string, attempt int, base, cap time.Duration, r *rand.Rand) Decision {
	if attempt < 0 || base <= 0 || cap < base {
		return Decision{Reason: "invalid retry policy"}
	}
	if status != 429 && status < 500 {
		return Decision{Reason: "non-retryable response"}
	}
	delay := base
	for i := 0; i < attempt && delay < cap; i++ {
		if delay > cap/2 {
			delay = cap
			break
		}
		delay *= 2
	}
	if parsed, ok := parseRetryAfter(retryAfter); ok && parsed < cap {
		delay = parsed
	}
	if r != nil && delay > 0 {
		delay = time.Duration(r.Int63n(int64(delay) + 1))
	}
	return Decision{Retry: true, Delay: delay, Reason: "transient response"}
}

func parseRetryAfter(value string) (time.Duration, bool) {
	seconds, err := strconv.Atoi(strings.TrimSpace(value))
	if err != nil || seconds < 0 {
		return 0, false
	}
	return time.Duration(seconds) * time.Second, true
}
```

This treats Retry-After as a scheduling input, not permission to wait forever. A production implementation should accept an HTTP-date if its contract requires it, reject values above the policy cap, and record that a malformed header was ignored. The policy is only one part of the design; the evidence model and queue transaction matter just as much. Where should the attempt record sit in the send path? Persist the notification job before a worker can claim it.

此代码将 Retry-After 视为调度输入，而非无限期等待的许可。生产环境的实现应在协议要求时接受 HTTP 日期格式，拒绝超过策略上限的值，并记录下对格式错误头部的忽略。策略只是设计的一部分；证据模型和队列事务同样重要。尝试记录应位于发送路径的何处？请在工作进程获取任务之前持久化通知作业。
