A hidden defect in Microsoft’s cloud gateway, dormant since July, was to blame for one of the largest outages in the company’s history last week. A preliminary Post-Incident Report (PIR) released by the company outlines how the latent bug, changes in traffic, and reduced server capacity combined to knock much of Microsoft 365 and Exchange infrastructure offline at the end of last week.

上周，微软云网关中一个自七月以来一直处于休眠状态的隐藏缺陷，导致了该公司历史上规模最大的宕机事件之一。微软发布的初步事故报告（PIR）概述了该潜在漏洞、流量变化以及服务器容量减少是如何共同作用，导致微软 365 和 Exchange 基础设施在上周末大面积瘫痪的。

Microsoft’s report lists the incident’s final status as “a technical issue not related to cyber or AI/agents.” Microsoft’s preliminary report places the outage between November 12 at 16:20 UTC and November 13 at 16:10 UTC, just under 24 hours total, and additional monitoring remained in place for any affected systems through November 14.

微软的报告将此次事件的最终状态列为“与网络攻击或人工智能/智能体无关的技术问题”。微软的初步报告显示，宕机时间发生在协调世界时（UTC）11月12日16:20至11月13日16:10之间，总时长略低于24小时，且受影响系统在11月14日之前一直处于额外监控状态。

A perfect storm: Microsoft attributes the outage to three factors. A change deployed to Microsoft’s cloud gateway starting in July created a bug where, under certain conditions, CPU and memory resources could become exhausted and unresponsive. Microsoft contends that the defect was never discovered in pre-release testing because the hardware used was less powerful than some systems already deployed in production, where higher CPU core counts on newer machines apparently contributed to the lockout.

完美风暴：微软将此次宕机归因于三个因素。七月份部署到微软云网关的一项变更产生了一个漏洞，在特定条件下，该漏洞会导致 CPU 和内存资源耗尽并失去响应。微软声称，该缺陷在发布前测试中从未被发现，因为所使用的硬件性能低于生产环境中已部署的部分系统，而新机器上更高的 CPU 核心数显然加剧了锁定问题。

The second factor was server load. Microsoft said that “Traffic shifts during standard network maintenance and upgrades exposed a latent bug.” The company keeps two independent gateway systems in place to access Microsoft 365 for resilience. If one system encounters trouble and users can’t get through the front door, the other is opened to keep traffic flowing.

第二个因素是服务器负载。微软表示，“在标准网络维护和升级期间的流量转移暴露了一个潜在漏洞。”该公司维护着两个独立的网关系统以访问微软 365，从而确保弹性。如果一个系统遇到故障导致用户无法正常访问，另一个系统就会开启以保持流量畅通。

The traffic shift exposed a third factor: infrastructure capacity. An existing fault meant that Microsoft’s gateway server fleet was operating at 14 percent below optimal conditions. That missing headroom could have normally absorbed the demand, but when combined with the changed traffic patterns and underlying defect, it left the gateways with lock contention as requests kept piling up.

流量转移暴露了第三个因素：基础设施容量。一个现有的故障意味着微软的网关服务器集群运行在低于最佳状态 14% 的水平。这种缺失的冗余空间本可以吸收正常需求，但当它与变化的流量模式和潜在缺陷相结合时，随着请求不断堆积，网关出现了锁竞争问题。

Recovery took longer than normal because the fix required a targeted system update from Microsoft engineers. Attempts to restart the gateway servers were ineffective; when the servers came back online, large request queues were still waiting for access, immediately triggering the same resource exhaustion that contributed to the outage in the first place.

恢复过程比平时更长，因为修复工作需要微软工程师进行针对性的系统更新。重启网关服务器的尝试均告无效；当服务器重新上线时，大量的请求队列仍在等待访问，这立即触发了导致最初宕机的资源耗尽问题。

Microsoft expects to publish its full final incident report on November 20. This final report may provide additional clarification on why the regional isolation systems failed and what corrective actions will be taken to ensure this type of outage can be avoided in the future. All of Microsoft’s cloud services appeared online and operational as of Monday morning.

微软预计将于 11 月 20 日发布完整的最终事故报告。这份最终报告可能会进一步说明区域隔离系统为何失效，以及将采取哪些纠正措施以确保未来能够避免此类宕机。截至周一上午，微软的所有云服务似乎均已上线并恢复正常运行。
