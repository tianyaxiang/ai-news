Tuesday AI Deep Dive. When you call a model through an API, you get tokens back and a model name in the response. That name is a claim, not evidence. A router could quietly swap in a cheaper model, a compromised server could tamper with the stream, and judging from output quality alone is unreliable.

周二 AI 深度解析。当你通过 API 调用模型时，你会收到返回的 Token 和响应中的模型名称。该名称只是一个声明，而非证据。路由器可能会悄悄替换成更便宜的模型，受损的服务器可能会篡改数据流，且仅凭输出质量进行判断是不可靠的。

On Nov 2, 2026, Anthropic's Frontier Red Team (with researchers from EPFL, StarkWare, MIT and others) published FlashProve, an open-source prototype for provable inference: the provider commits to a set of weights, then attaches a cryptographic proof to each response showing that those committed weights produced those exact tokens. The verifier needs no GPU and learns nothing about the weights.

2026 年 11 月 2 日，Anthropic 的前沿红队（联合来自 EPFL、StarkWare、MIT 等机构的研究人员）发布了 FlashProve，这是一个用于可证明推理的开源原型：提供商提交一组权重，然后为每个响应附加一个加密证明，证明这些已提交的权重生成了这些确切的 Token。验证者无需 GPU，也不会获知关于权重的任何信息。

The headline: for Llama 4 Maverick (a 400B-parameter mixture of experts, 4-bit weights), one H100 generates proofs at about 110 tokens/second, each proof is about 19 MB per 1,024-token request, and checking a proof takes about 17 seconds on a 24-thread CPU. The cost is roughly 70-95x the GPU time of serving the same requests with vLLM. Here is what that means, how it works at a high level, and where it stops.

核心要点：对于 Llama 4 Maverick（一个 4000 亿参数的混合专家模型，4-bit 权重），单张 H100 生成证明的速度约为每秒 110 个 Token，每个 1024 个 Token 的请求对应的证明大小约为 19 MB，在 24 线程 CPU 上验证一个证明大约需要 17 秒。其成本大约是使用 vLLM 处理相同请求所需 GPU 时间的 70 到 95 倍。以下是其含义、基本工作原理以及局限性。

The problem: "which model answered me?" Anthropic lists cases where you'd want more than trust: Third-party routing. Clients using a model through a router want assurance the tokens came from the model they paid for. Evaluations. Independent evaluators testing a model before and after release need to know the model they evaluated is the one being served. Tamper detection. An attacker on an inference server (or a more capable model substituting itself for an approved one) could serve malicious responses hidden among genuine ones. Text provenance. Claims like "our library was scanned by a frontier security model" are hard to check; even published chat logs could have been generated by a cheaper model. Pacing and model approval. Regulators could require proof that hardware is serving the claimed, approved model. The naive fix, re-running the model yourself, needs the private weights and far more compute than a typical user or auditor has.

问题在于：“是哪个模型回答了我？”Anthropic 列举了需要超越信任的场景：第三方路由。通过路由器使用模型的客户希望确保 Token 来自他们付费购买的模型。评估。在发布前后测试模型的独立评估人员需要知道他们评估的模型正是正在提供服务的模型。篡改检测。推理服务器上的攻击者（或用自身替代获批模型的更强模型）可能会在真实响应中隐藏恶意响应。文本溯源。诸如“我们的库已由前沿安全模型扫描”之类的声明很难核实；即使是已发布的聊天记录也可能是由更便宜的模型生成的。节奏控制与模型审批。监管机构可能要求证明硬件正在运行所声明的、已获批的模型。天真的解决方法——自己重新运行模型——需要私有权重，且所需的计算量远超普通用户或审计员的能力。

How it works: commit, then prove. FlashProve uses a zkSNARK (zero-knowledge succinct argument of knowledge): a short certificate that a computation was executed correctly, which reveals nothing beyond that fact and is far cheaper to verify than to recompute. It runs in two phases: Offline: commit to the weights. The provider publishes a short fingerprint that pins down one exact set of weights while keeping them hidden. On one H100 this takes about 39 minutes per model, and the commitment is good for about 16 million requests before the provider must commit again. The client downloads about 6.5 MB of commitment data. Online: prove each response. Given a prompt and output tokens, the prover produces a proof file for the statement "the committed model produces these output tokens when evaluated." Anyone holding the commitment, the prompt and the reply can check it.

工作原理：先提交，后证明。FlashProve 使用了 zkSNARK（零知识简洁非交互式知识论证）：这是一种简短的证书，证明计算已正确执行，除了这一事实外不泄露任何信息，且验证成本远低于重新计算。它分为两个阶段运行：离线阶段：提交权重。提供商发布一个简短的指纹，锁定一组确切的权重，同时保持其隐藏。在单张 H100 上，每个模型大约需要 39 分钟，该提交在提供商必须再次提交之前可用于约 1600 万次请求。客户端下载约 6.5 MB 的提交数据。在线阶段：证明每个响应。给定提示词和输出 Token，证明者为“已提交的模型在评估时生成了这些输出 Token”这一陈述生成一个证明文件。任何持有提交数据、提示词和回复的人都可以进行验证。

The four properties that matter: Property What it gives you. Completeness: An honest proof is accepted. Soundness: A proof of a false statement can't be forged (short of breaking widely believed cryptographic assumptions). Zero-knowledge: The verifier learns nothing about the weights, intermediate values, or which experts ran. The architecture is not hidden. Succinctness: ~19 MB proof, seconds to check on a CPU, for a run of a ~232 GB quantized model. Under the hood, it follows a well-established recipe: an interactive oracle proof (IOP) compiled into a cryptographic proof using hash functions, built from code proximity tests and lookup arguments. Anthropic notes the construction also offers post-quantum security.

四个关键属性：属性及其含义。完备性：诚实的证明会被接受。可靠性：虚假陈述的证明无法被伪造（除非打破被广泛认可的加密假设）。零知识：验证者不会获知关于权重、中间值或哪些专家被调用的信息。架构本身并不隐藏。简洁性：对于约 232 GB 的量化模型运行，证明大小约为 19 MB，在 CPU 上仅需几秒即可完成验证。在底层，它遵循一套成熟的方案：通过哈希函数将交互式预言机证明（IOP）编译为加密证明，并基于代码邻近性测试和查找参数构建。Anthropic 指出，该结构还提供了抗量子安全性。

Three engineering choices that made it fast: Prove only the experts that ran. In a MoE model each token uses about 17B of the 400B parameters, so prover work per token scales with those ~17B, while the proof still hides which experts were chosen. Prove in batches, after the fact. The prover reads finished text in one parallel pass (like prefill) and opens the weight commitment once per batch instead of once per request. A batch of 24 requests took about 223 seconds. Fit on one GPU. Weights are split into segments and proven one segment of layers at a time, streamed from host memory: one 80 GB GPU with about 290 GB of host memory suffices. FlashProve proves post-hoc (after inference, possibly for a subset of tokens) rather than in-line. That allows a slower but more secure design, at the cost of recomputation complexity, delayed guarantees, and floating-point non-determinism issues.

使其实现高速的三项工程选择：仅证明已运行的专家。在混合专家（MoE）模型中，每个 Token 仅使用 4000 亿参数中的约 170 亿，因此每个 Token 的证明工作量与这 170 亿参数成比例，同时证明过程仍隐藏了具体选择了哪些专家。事后批量证明。证明者以并行方式读取已完成的文本（类似于预填充），并按批次而非按请求打开权重提交。24 个请求的批次大约耗时 223 秒。适配单张 GPU。权重被拆分为多个片段，每次证明一层片段，并从主机内存流式传输：一张 80 GB 的 GPU 配合约 290 GB 的主机内存即可满足需求。FlashProve 采用事后证明（推理完成后，可能针对部分 Token），而非在线证明。这允许采用更慢但更安全的设计，代价是增加了重新计算的复杂性、延迟了保证时间，并带来了浮点数非确定性问题。

Why the numbers are a big deal: The prior-work section is a useful reality check on how fast zkML has moved: ZKML's GPT-2 (117M parameters): about 159 s per token. zkLLM (2024): LLaMA-2-13B at about 2.5 tok/s in a batch. VerInf: the same Llama 4 Maverick at about 0.02 tok/s, with a 93.6 GB proof that took almost a day to verify. Attestable (commercial, not open source at the time of writing): Gemma 4 31B at 53-77 tok/s on one H100. FlashProve: 110 tok/s on Maverick, 19 MB proofs, verified in seconds. Anthropic's takeaway is that the overhead over native computation is roughly two orders of magnitude, "much less than previously expected."

这些数据为何意义重大：前人工作部分是对 zkML 发展速度的一个有用的现实检验：ZKML 的 GPT-2（1.17 亿参数）：每个 Token 约 159 秒。zkLLM（2024）：LLaMA-2-13B 在批处理中约为每秒 2.5 个 Token。VerInf：同样的 Llama 4 Maverick 约为每秒 0.02 个 Token，且证明文件高达 93.6 GB，验证耗时近一天。Attestable（商业软件，撰写时未开源）：Gemma 4 31B 在单张 H100 上为每秒 53-77 个 Token。FlashProve：在 Maverick 上达到每秒 110 个 Token，证明文件仅 19 MB，几秒内即可完成验证。Anthropic 的结论是，相比原生计算的开销大约是两个数量级，“远低于此前的预期”。

Trusting the code: Lean proofs. Cryptographic code is brittle, so the team states completeness, soundness and zero-knowledge in the Lean proof assistant and proves them (in the random oracle model). They ship a fast C++ verifier for daily use and a slower Lean verifier that provably accepts only what the soundness theorem accepts. Two trust gaps remain, and they say so: humans still have to audit that the formal statements match the intent (an interactive visualizer helps), and the fast code isn't formally guaranteed to match the Lean protocol. Soundness depends only on the verifier being correct, which is why a verified verifier is the key piece.

信任代码：Lean 证明。加密代码非常脆弱，因此团队在 Lean 证明助手（Proof Assistant）中陈述了完备性、可靠性和零知识属性，并对其进行了证明（在随机预言机模型下）。他们提供了一个用于日常使用的快速 C++ 验证器，以及一个较慢的 Lean 验证器，后者可证明仅接受可靠性定理所允许的内容。他们也承认仍存在两个信任缺口：人类仍需审计形式化陈述是否符合意图（交互式可视化工具对此有帮助），且快速代码并未在形式上保证与 Lean 协议完全一致。可靠性仅取决于验证器是否正确，这就是为什么经过验证的验证器是关键所在。

Limitations (read these before getting excited): Greedy decoding on an integer model. The proof covers an exact integer version of the weights under greed.

局限性（在兴奋之前请阅读）：整数模型上的贪婪解码。该证明涵盖了贪婪解码下权重的精确整数版本。
