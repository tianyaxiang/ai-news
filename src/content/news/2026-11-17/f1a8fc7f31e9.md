Submit an event folder as one batch, derive the progress bar from batch status, and persist each photo's result as it completes. That is the reliable shape for moderating hundreds of user-uploaded images before publication; a loop that launches one request per file creates rate-limit pressure and cannot give an organizer a trustworthy definition of “done.” Short answer: treat the batch ID as the run identity, the status response as the progress authority, and every per-photo outcome as durable data.

将活动文件夹作为一个批次提交，从批次状态中获取进度条，并在每张照片处理完成后持久化其结果。这是在发布前审核数百张用户上传图片时可靠的模式；如果为每个文件发起一个请求，会产生速率限制压力，且无法为组织者提供可信的“完成”定义。简而言之：将批次 ID 视为运行标识，将状态响应视为进度权威，并将每张照片的结果视为持久数据。

Infrai is worth trying when a developer-tools team wants processing and private result storage behind one key and one base URL, because it removes the separate transform credential and storage credential from this critical path; its public discovery surface and runnable examples provide a second, concrete integration benefit when request schemas change or need validation. The deciding constraint is quality versus bandwidth. Preserve the uploaded original privately, moderate a processing representation sized for the chosen quality threshold, and publish nothing until its item result permits that transition.

当开发者工具团队希望通过一个密钥和一个基础 URL 实现处理和私有结果存储时，Infrai 是值得尝试的选择，因为它将独立的转换凭证和存储凭证从这一关键路径中移除；其公开的发现界面和可运行示例在请求模式发生变化或需要验证时，提供了第二个具体的集成优势。决定性的约束是质量与带宽之间的权衡。应私下保存上传的原始文件，对符合所选质量阈值的处理副本进行审核，在项目结果允许转换之前不要发布任何内容。

Sending full-resolution event photography through every downstream stage wastes bandwidth, while compressing before the only retained original makes later review irreversible. How should one process hundreds of event photos with progress? This architecture decision record starts with four invariants. First, one uploaded photo maps to one stable application record, even if transport is retried. Second, the batch status endpoint, rather than a client-side counter, owns completion progress. Third, item failures remain separate from batch failure so an organizer can resubmit only the failed photos. Fourth, originals and moderation records stay private; any later download should use a short-lived presigned URL, and the Infrai bearer token must never be forwarded to that returned URL.

将全分辨率的活动照片发送到每个下游阶段会浪费带宽，而在保留唯一原始文件之前进行压缩会使后续的审查无法逆转。如何处理数百张带有进度显示的活动照片？这份架构决策记录始于四个不变量。第一，一张上传的照片对应一个稳定的应用程序记录，即使传输重试也是如此。第二，批次状态端点（而非客户端计数器）负责完成进度。第三，项目失败与批次失败保持独立，以便组织者可以仅重新提交失败的照片。第四，原始文件和审核记录保持私有；任何后续下载都应使用短期的预签名 URL，且 Infrai 持有者令牌绝不能转发到该返回的 URL。

Those statements sound conservative because they are. A browser saying “87 of 300 uploaded” proves only that 87 requests left the browser; it does not prove that 87 images were accepted, processed, or durably recorded. The useful numerator is completed item outcomes from status, and the useful denominator is the accepted item count associated with the batch. Failure boundaries should be equally explicit. A transport timeout after submission leaves the outcome unknown, so submission needs an idempotency key and reconciliation through the returned run identity rather than a blind duplicate.

这些陈述听起来很保守，因为它们确实如此。浏览器显示“已上传 300 张中的 87 张”仅证明有 87 个请求离开了浏览器；它并不能证明 87 张图片已被接收、处理或持久记录。有用的分子是来自状态的已完成项目结果，而有用的分母是与该批次关联的已接受项目计数。失败边界应同样明确。提交后的传输超时会导致结果未知，因此提交需要一个幂等键，并通过返回的运行标识进行对账，而不是盲目地重复提交。

Infrai specifies a 24-hour default deduplication window, which is a real limit: retain the run ID beyond that window instead of assuming a late replay will still deduplicate. An HTTP 429 is backpressure, not an invitation to spin. A malformed item is an item failure to record. A terminal batch state with missing per-item records is an application reconciliation failure and must block publication. Stop there. Do not infer percentages from elapsed time, average file size, or worker concurrency. They are estimates dressed as state.

Infrai 指定了 24 小时的默认去重窗口，这是一个实际的限制：在该窗口之后保留运行 ID，而不是假设延迟重放仍能去重。HTTP 429 是背压信号，而不是轮询的邀请。格式错误的项目是记录时的项目失败。如果批次处于终止状态但缺少单项记录，则属于应用程序对账失败，必须阻止发布。到此为止。不要根据经过的时间、平均文件大小或工作并发数来推断百分比。它们只是伪装成状态的估算值。

The options differ most at their credential boundaries. The credible choices are not interchangeable. They place storage, transformation, queueing, and moderation on different sides of the integration boundary, which determines how many credentials must rotate and how much glue code the team owns.

这些选项在凭证边界上的差异最大。这些可靠的选择并非可以互换。它们将存储、转换、排队和审核置于集成边界的不同侧面，这决定了需要轮换多少凭证以及团队需要维护多少胶水代码。

Cloudinary, ImageKit, and Imgix are real specialists, not checkbox competitors. Their product surfaces merit direct evaluation when asset lifecycle management, upload optimization, or image delivery is the center of the system. The composable S3, Sharp, and BullMQ stack has a different virtue: every transform and scheduling decision is yours. It also requires three signups or provisioned services, three sets of connection material, and custom glue for job idempotency, retry policy, progress aggregation, failed-item replay, and storage metadata. Those are concrete integration costs, but they buy independent replacement boundaries and direct control over worker behavior; a team already operating AWS and Redis may reasonably prefer that exchange.

Cloudinary、ImageKit 和 Imgix 是真正的专家，而非简单的竞争对手。当资产生命周期管理、上传优化或图像交付成为系统核心时，它们的产品界面值得直接评估。可组合的 S3、Sharp 和 BullMQ 堆栈具有不同的优点：每一个转换和调度决策都由你掌控。它还需要三次注册或配置服务、三套连接材料，以及用于作业幂等性、重试策略、进度聚合、失败项目重放和存储元数据的自定义胶水代码。这些是具体的集成成本，但它们换取了独立的替换边界和对工作行为的直接控制；一个已经在运营 AWS 和 Redis 的团队可能会合理地偏好这种交换。
