# Your LLM Can Return Perfect JSON and Still Be Wrong
# 你的大模型可以返回完美的 JSON，但结果依然可能是错的

Three weeks after I turned on Structured Outputs for a pipeline that parsed payment confirmation messages into transaction records, I noticed that our reconciliation job started flagging a small, steady stream of mismatches. They were not crashes, and not malformed rows either. Just transactions where the amount and sender matched perfectly but the date was off. Something like 2 to 3% of a given week's volume, enough to notice, not enough to be obvious right away.

在我为一个将支付确认信息解析为交易记录的流水线开启“结构化输出”（Structured Outputs）功能三周后，我注意到我们的对账任务开始标记出一小部分持续存在的不匹配数据。这些既不是程序崩溃，也不是格式错误的行。仅仅是那些金额和发送者完全匹配，但日期不对的交易。大约占每周数据量的 2% 到 3%，足以引起注意，但又不至于一眼就能看出来。

At first I assumed that it was a timezone bug. But it wasn't. When I pulled the raw source messages next to the extracted records, a pattern showed up: every mismatched transaction came from a message that never mentioned a date at all. Something like "Payment received from Chinedu, ₦45,000, ref TXN-82K91." No date anywhere in the text. And the model had filled `transaction_date` in anyway, almost always the date the extraction job ran, off by less than an hour.

起初我以为是时区错误，但并不是。当我把原始消息与提取出的记录放在一起对比时，一种模式出现了：每一笔不匹配的交易都来自一条从未提及日期的消息。比如：“收到来自 Chinedu 的付款，45,000 奈拉，参考号 TXN-82K91。”文中没有任何日期。而模型却自作主张填入了 `transaction_date`，几乎总是提取任务运行当天的日期，误差不到一小时。

The schema said `transaction_date: date, required`. The model couldn't return nothing. So it didn't. I'd been treating "the JSON is valid" as the finish line for this pipeline, and for weeks it looked like one. It isn't. It's the point where a quieter kind of failure becomes possible, one that never throws an error or fails a type check, and doesn't show up until something downstream depends on the value being real. Most of what gets written about Structured Outputs stops at "it can't return broken JSON anymore," as if that settles the reliability question. It settles one version of it.

模式定义中写着 `transaction_date: date, required`（必填）。模型不能返回空值，所以它就没返回空值。我一直把“JSON 格式有效”当作流水线的终点，几周以来它看起来确实像终点。但事实并非如此。这其实是一个更隐蔽的故障点，它不会抛出错误，也不会导致类型检查失败，直到下游某个环节依赖于该值的真实性时，问题才会显现。关于结构化输出的大多数文章都止步于“它不会再返回损坏的 JSON 了”，仿佛这就解决了可靠性问题。这确实解决了一种可靠性问题，但仅此而已。

### The trap of the perfect schema
### 完美模式的陷阱

Structured Outputs solve a real problem. Before native schema enforcement, getting reliable JSON out of an LLM meant regex parsers, retry loops, and prompts that basically begged the model: "ONLY output JSON, no markdown, no preamble." With the modern OpenAI Python SDK and a Pydantic model, most of that category of pain just goes away:

结构化输出解决了一个实际问题。在原生模式强制执行之前，要从大模型中获得可靠的 JSON，意味着需要正则表达式解析器、重试循环，以及基本上是在乞求模型的提示词：“只输出 JSON，不要 Markdown，不要前言。”有了现代的 OpenAI Python SDK 和 Pydantic 模型，大部分这类痛苦都消失了：

```python
import logging
from datetime import date
from pydantic import BaseModel
from openai import OpenAI

logger = logging.getLogger(__name__)
client = OpenAI()

class Transaction(BaseModel):
    sender: str
    amount: float
    transaction_id: str
    transaction_date: date

document = """Payment received from Chinedu.
Amount: ₦45,000
Reference: TXN-82K91
Date: 11 August 2026"""

# gpt-4o-mini kept merging the amount and reference into one field on
# messages with unusual formatting, so this stays on the full model
# despite the cost. Worth revisiting once mini catches up.
completion = client.beta.chat.completions.parse(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": "Extract the transaction details."},
        {"role": "user", "content": document},
    ],
    response_format=Transaction,
)

txn = completion.choices[0].message.parsed
logger.info("parsed txn %s", txn.transaction_id)
```

Run it against a clean message and it works exactly as advertised. Every key present, every type correct, no try/except needed just to catch a stray markdown fence around the JSON.

用一条干净的消息运行它，效果完全如预期。每个键都存在，每个类型都正确，不需要为了捕获 JSON 周围多余的 Markdown 标记而编写 try/except。

Then someone forwards you a message like this one:
然后有人转发给你这样一条消息：

```python
document = """Payment received from Chinedu.
Amount: ₦45,000
Reference: TXN-82K91"""
# No date in this one.
```

But the schema doesn't care that the date isn't there. It's still marked required, so something has to fill that slot, and it's never going to be the schema that bends. The model reaches for whatever gets it to a valid value instead: the current date, the training cutoff, a plausible-looking guess. What comes back type-checks perfectly. It's also completely made up, and there's nothing in the response itself that tells you which fields are which.

但模式并不关心日期是否存在。它仍然被标记为必填，所以必须有东西填补那个空位，而模式本身是不会妥协的。模型会抓取任何能让它凑出一个有效值的东西：当前日期、训练截止日期，或者一个看起来合理的猜测。返回的结果通过了类型检查，但它是完全编造的，而且响应本身没有任何信息告诉你哪些字段是真实的，哪些是编造的。

### Designing schemas for uncertainty
### 为不确定性设计模式

The fix is a mental shift more than a code change. An empty field isn't an error in extraction, it's often just the truth. Making fields nullable takes the pressure off the model to invent something:

修复这个问题更多是思维方式的转变，而非代码的修改。字段为空在提取过程中并不是错误，它往往只是事实。将字段设为可空（nullable）可以减轻模型编造数据的压力：

```python
class Transaction(BaseModel):
    sender: str | None
    amount: float | None
    transaction_id: str | None
    transaction_date: date | None
```

Now if the date's missing, the model can just say so. This also brings a distinction that's easy to blur, which is extraction versus inference. Extraction is "tell me exactly what's in the text." While inference is "tell me what it implies." A message that says "paid on Tuesday" and a schema demanding an ISO date, that's inference, whether you meant to ask for it or not. Sometimes inference is exactly what you want, but the decision should be yours, not something the model makes for you by default. A nullable field hands that decision back to your own code:

现在如果日期缺失，模型可以直接说明。这也带来了一个容易混淆的区别：提取与推理。提取是“告诉我文本中确切的内容”，而推理是“告诉我它暗示了什么”。如果消息说“周二支付”，而模式要求 ISO 日期，这就是推理，无论你是否有意要求。有时推理正是你想要的，但这个决定权应该在你手中，而不是由模型默认替你做出。可空字段将决定权交还给了你的代码：

```python
if transaction.transaction_date is None:
    request_missing_info(transaction_id=transaction.transaction_id)
```

### Evidence and provenance
### 证据与溯源

Nullable fields fix the "inventing values from nothing" problem. They don't fix the other one, which is honestly worse: the model gives you a value, and you have no way to tell if it actually read that value off the page or pattern-matched its way there.

可空字段解决了“无中生有”的问题，但它们无法解决另一个更糟糕的问题：模型给了你一个值，你却无法判断它是真的从页面上读取的，还是通过模式匹配“猜”出来的。

With a normal chat response you can at least watch it reason its way to an answer. Structured Outputs skip straight to the final form. So I started asking for a second field alongside every value, the exact chunk of source text that supposedly backs it up.

在普通的聊天响应中，你至少可以观察它的推理过程。而结构化输出直接跳到了最终结果。所以我开始要求在每个值旁边增加第二个字段，即支持该值的原始文本片段。

```python
from pydantic import Field

class Extracted(BaseModel):
    """Generic wrapper so I'm not writing a near-identical class per field type."""
    value: float | date | str | None
    evidence: str | None = Field(description="exact quote backing this value, empty if not found")

class Transaction(BaseModel):
    sender: str | None
    amount: Extracted
    transaction_id: str | None
    transaction_date: Extracted
```

The generic `Extracted` wrapper is a shortcut, not a best practice. `value` is now a union type instead of a clean float, which costs some of the type safety the original schema had. That trade is worth it once a schema has more than a couple of field types, writing `ExtractedFloat`, `ExtractedDate`, `ExtractedString` separately is just busywork at that point. For one or two fields, keep the specific classes, they're usually cleaner.

通用的 `Extracted` 包装器是一种捷径，而非最佳实践。`value` 现在是一个联合类型，而不是纯粹的浮点数，这牺牲了一些原始模式的类型安全性。但当模式包含多个字段类型时，这种权衡是值得的，因为单独编写 `ExtractedFloat`、`ExtractedDate` 等纯属繁琐工作。如果只有一两个字段，保留特定的类通常更简洁。
