# Why RAG Complexity Should Be Earned
# 为什么 RAG 的复杂性应当是“挣来”的

Retrieval-Augmented Generation (RAG) architectures have expanded considerably beyond the original retrieve-and-generate pattern over the last few years. Contemporary systems increasingly incorporate dense and lexical retrieval, query rewriting, rank fusion, neural reranking, question decomposition, corrective retrieval, reflection, and agent-based orchestration. These techniques can materially improve performance on complex information-seeking tasks. However, they are also frequently introduced before the underlying retrieval subsystem has been independently evaluated.

在过去几年中，检索增强生成（RAG）架构已经远远超出了最初的“检索-生成”模式。现代系统越来越多地集成了稠密检索与词法检索、查询重写、排名融合、神经重排序、问题分解、纠错检索、反思机制以及基于智能体的编排。这些技术确实能显著提升复杂信息检索任务的性能。然而，人们往往在尚未对底层检索子系统进行独立评估之前，就引入了这些复杂技术。

This article looks at how RAG complexity should be introduced in response to measured retrieval failure modes rather than adopted as an architectural default. Recent studies show that comparatively conventional retrieval methods remain highly competitive: lexical retrieval performs well in specialized domains, hybrid retrieval with reranking provides solid baselines, and even agentic systems perform better when they are built on top of stronger retrieval.

本文探讨了 RAG 的复杂性应如何作为对已测得的检索失败模式的响应而引入，而非将其作为架构的默认配置。近期研究表明，相对传统的检索方法依然极具竞争力：词法检索在专业领域表现优异，带有重排序的混合检索提供了稳健的基准，即便是智能体系统，在构建于更强大的检索基础之上时，其表现也会更好。

The implication is not that agentic RAG is unnecessary. Rather, retrieval quality and agentic reasoning address different parts of the problem: when evidence can be recovered through a well-defined retrieval step, the main concern is usually search quality; when retrieval is iterative, multi-hop, or depends on intermediate evidence, agentic retrieval becomes much more useful.

这并不是说智能体 RAG 是多余的。相反，检索质量和智能体推理解决的是问题的不同侧面：当证据可以通过定义明确的检索步骤获取时，主要关注点通常是搜索质量；而当检索是迭代式的、多跳的，或依赖于中间证据时，智能体检索的作用就会大得多。

### Increasing Complexity in RAG Architectures
### RAG 架构中日益增加的复杂性

The following is an increasingly common pattern in modern RAG systems: A retrieval problem appears. Before it has been established whether retrieval itself is functioning correctly, the architecture accumulates query rewriting, routing, multiple retrieval passes, reflection, corrective retrieval, an agent deciding whether additional evidence is required, a reranking model, and sometimes another model tasked with verifying the final answer.

以下是现代 RAG 系统中一种日益普遍的模式：当出现检索问题时，在尚未确定检索本身是否正常工作之前，架构就开始堆砌查询重写、路由、多次检索、反思、纠错检索、决定是否需要额外证据的智能体、重排序模型，有时甚至还会加入另一个负责验证最终答案的模型。

The resulting architecture appears sophisticated. However, the system may still fail for a much simpler reason: the relevant evidence was ranked outside the candidate set and never entered the model’s context. This distinction is important because retrieval and reasoning represent separate system capabilities.

最终的架构看起来非常复杂。然而，系统仍可能因为一个更简单的原因而失败：相关证据在候选集之外，从未进入模型的上下文。这种区分至关重要，因为检索和推理代表了系统两种独立的能力。

If the dominant failure is: The required evidence was not retrieved, then additional reasoning after retrieval is unlikely to fix the root cause. It may instead increase latency, token consumption, nondeterminism, and the number of components requiring evaluation.

如果主要的失败原因是：未检索到所需证据，那么在检索之后增加推理不太可能解决根本问题。相反，它可能会增加延迟、Token 消耗、不确定性以及需要评估的组件数量。

This is not an argument against agentic RAG. There are information-seeking tasks for which planning, decomposition, heterogeneous source selection, and iterative retrieval are necessary. The argument is narrower: Architectural complexity should correspond to a demonstrated failure mode. Agency makes sense when conventional retrieval is structurally insufficient. However, when the evidence already exists in a retrievable unit but fails to enter the context window, there is a higher probability that the dominant problem lies within the search and retrieval subsystem.

这并非反对智能体 RAG。在某些信息检索任务中，规划、分解、异构源选择和迭代检索是必要的。本文的观点更为具体：架构的复杂性应对应于已证实的失败模式。当传统检索在结构上不足以应对时，引入智能体才有意义。然而，当证据已经存在于可检索单元中，却未能进入上下文窗口时，更有可能的问题在于搜索和检索子系统。

### Retrieval and Generation as Distinct System Components
### 作为独立系统组件的检索与生成

A RAG system performs two conceptually separate operations:
1. **Retrieval:** identifying information likely to contain the information necessary to answer a query.
2. **Generation:** interpreting the retrieved information and constructing an appropriate response.

RAG 系统执行两个概念上独立的任务：
1. **检索：** 识别可能包含回答查询所需信息的内容。
2. **生成：** 解读检索到的信息并构建适当的响应。

These operations are often evaluated together because the generated answer is the user-visible output. From a system-design perspective, however, their failure modes should be separated.

这些操作通常被放在一起评估，因为生成的答案是用户可见的输出。然而，从系统设计的角度来看，它们的失败模式应当被区分开来。

Consider a query against a collection of commercial agreements: "What termination provisions apply if the supplier repeatedly fails its SLA?" Assume that the retriever returns: a paragraph describing general supplier obligations, a payment clause, several passages containing the phrase "service level," and a definition of contractual breach. The actual termination clause though, is ranked outside the retrieved top-k set.

以针对一系列商业协议的查询为例：“如果供应商多次违反 SLA，适用哪些终止条款？”假设检索器返回了：一段描述一般供应商义务的段落、一个付款条款、几段包含“服务水平”短语的段落，以及一个合同违约的定义。然而，真正的终止条款却排在检索到的 Top-k 集合之外。

A sufficiently capable language model may still produce a plausible answer based on general contractual patterns. It may even sound correct. The system has nevertheless failed at retrieval. No change to the generation prompt can recover evidence that never entered the model’s context.

一个足够强大的语言模型可能仍然会基于通用的合同模式给出一个看似合理的答案。它甚至听起来是正确的。但系统在检索环节已经失败了。任何对生成提示词（Prompt）的修改都无法找回那些从未进入模型上下文的证据。

This leads to a fundamental diagnostic question for RAG systems: "Was the evidence required to answer the query present within the retrieved candidate set?" That question should generally be answered before modifying the reasoning or generation layer.

这引出了 RAG 系统的一个基本诊断问题：“回答查询所需的证据是否在检索到的候选集中？”在修改推理或生成层之前，通常应该先回答这个问题。

### Lexical Retrieval Remains a Competitive Baseline
### 词法检索依然是极具竞争力的基准

The widespread adoption of embedding-based retrieval has sometimes produced an implicit assumption that semantic similarity is a strict successor to lexical search. Empirical evidence does not really support that interpretation. BM25 remains a highly competitive retrieval mechanism, particularly in domains where exact lexical matches carry significant information.

基于嵌入（Embedding）的检索的广泛采用，有时会产生一种隐含的假设，即语义相似度是词法搜索的必然继任者。但实证证据并不支持这种解读。BM25 依然是一种极具竞争力的检索机制，特别是在精确词法匹配包含重要信息的领域。

The exact formulation is less important here than the distinction between lexical and semantic retrieval. Lexical search is especially effective when queries contain identifiers or terminology where exact matching matters, such as error codes, contractual identifiers, legal citations, product numbers, function names, ticker symbols, acronyms, medical terminology, database fields, or precise.

在此，具体的公式并不重要，重要的是词法检索与语义检索之间的区别。当查询包含需要精确匹配的标识符或术语时，词法搜索尤为有效，例如错误代码、合同标识符、法律引文、产品编号、函数名、股票代码、缩写、医学术语、数据库字段或精确术语。
