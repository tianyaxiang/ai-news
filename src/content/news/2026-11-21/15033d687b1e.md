### Budgeting 3 Recovery Boundaries for Shared Chat Viewers (Subscribe-Only Token Scope)

Node.js 聊天室在重新连接时可能会成功，但共享频道上的查看者看到的对话却是不完整的。只读令牌必须在恢复期间保留其订阅权限。操作上的约束是在不授予写入权限的情况下恢复丢失的消息，然后证明恢复工作有效，且无需在遥测中保留对话的第二个副本。简短的回答是：发放仅限于一个共享频道的“仅订阅”查看者令牌。将发布权限保留在受信任的后端。将重新连接和回填视为具有三个可观察边界的应用程序契约：令牌授权、持久消息移交和恢复完成。发布权限属于令牌；隐藏发送按钮无法强制执行这些权限。

The useful optimization is bounded evidence. A delivery system needs enough information to distinguish an authorization failure from unfinished backfill, but it does not need every viewer identifier attached to every metric. Start there before choosing a transport. A stable capability interface also fixes the integration boundary: vendor switching should leave the application's calls unchanged. Unified credentials reduce administration across backend services; they don't prove that a disconnected viewer recovered the conversation. Keep that distinction explicit when evaluating a unified API.

有用的优化是“有界证据”。交付系统需要足够的信息来区分授权失败和未完成的回填，但它不需要将每个查看者标识符附加到每个指标上。在选择传输方式之前，先从这里开始。稳定的能力接口也固定了集成边界：供应商切换应该保持应用程序的调用不变。统一凭据减少了跨后端服务的管理；它们并不能证明断开连接的查看者恢复了对话。在评估统一 API 时，请明确这一区别。

How should a read-only token scope viewers on a shared channel? Consider a proposed developer-tools room carrying release discussion alongside live build scores. Contributors publish updates; viewers watch the shared feed. A viewer reconnecting after an interruption needs the missing conversation and current score, with the original permission boundary intact. These are design requirements, not claims that a subscription token supplies storage or replay. Separate the room's durable identity from its event channel. An application might associate a release discussion with one event-specific channel and retain its conversation independently. Rotating that channel for the next event limits the usefulness of an old token: it grants access to the old channel rather than the new event. It does not retroactively erase information a viewer already received. Scope matters first.

只读令牌应如何限定共享频道上的查看者？考虑一个提议的开发工具聊天室，其中包含发布讨论以及实时构建分数。贡献者发布更新；查看者观看共享订阅源。在中断后重新连接的查看者需要丢失的对话和当前分数，同时保持原始权限边界不变。这些是设计要求，而不是声称订阅令牌提供存储或重放。将聊天室的持久身份与其事件频道分开。应用程序可能会将发布讨论与一个特定于事件的频道相关联，并独立保留其对话。为下一个事件轮换该频道会限制旧令牌的用处：它授予对旧频道的访问权限，而不是新事件的访问权限。它不会追溯性地擦除查看者已经收到的信息。范围（Scope）最重要。

In an Express application, the backend should authorize the viewer before issuing a token and grant subscription rights only for the intended shared channel. Publishers need their own trusted authorization path. On reconnect, recheck the viewer's entitlement before restoring access; possessing a recovery cursor should never grant permission to read another room. An application-level message identifier and cursor are proposed contract fields here, not vendor API parameter names. A score can often be represented by its latest state, while a conversation contains distinct messages that a viewer may need to read in order. A recovery policy must say which records it preserves. Otherwise, a dashboard can report a healthy connection while the application silently substitutes a current snapshot for missing discussion.

在 Express 应用程序中，后端应在发放令牌之前授权查看者，并仅为预期的共享频道授予订阅权限。发布者需要自己的受信任授权路径。重新连接时，在恢复访问之前重新检查查看者的权利；拥有恢复游标绝不应授予读取另一个聊天室的权限。此处提议的契约字段是应用程序级的消息标识符和游标，而不是供应商 API 参数名称。分数通常可以用其最新状态来表示，而对话包含查看者可能需要按顺序阅读的不同消息。恢复策略必须说明它保留哪些记录。否则，仪表板可能会报告连接健康，而应用程序却在后台静默地用当前快照替换丢失的讨论。

Count evidence at 3 boundaries. At the authorization boundary, record the outcome and intended scope class: viewer or publisher. Never retain the token itself. A successful token request alone does not demonstrate that attempted publication is denied. That needs a separate acceptance check. At the durable handoff boundary, distinguish a record accepted for later delivery from a socket publish accepted now. These receipts represent different events. Preserve a stable message identity across the handoff so a retry can be recognized, and define when a worker may acknowledge queued work. For standard queues, assume at-least-once delivery and require consumer idempotency. A duplicate delivery must not create a duplicate chat message.

在三个边界处计算证据。在授权边界，记录结果和预期的范围类别：查看者或发布者。切勿保留令牌本身。仅凭成功的令牌请求并不能证明尝试发布被拒绝。这需要单独的接受检查。在持久移交边界，区分“为稍后交付而接受的记录”和“现在接受的套接字发布”。这些收据代表不同的事件。在移交过程中保持稳定的消息标识，以便可以识别重试，并定义工作进程何时可以确认排队的工作。对于标准队列，假设至少一次交付并要求消费者幂等性。重复交付不得创建重复的聊天消息。

Recovery completion is the third boundary. Define completion against the application's expected position in the conversation, rather than merely against a connected socket. Useful aggregate outcomes include caught up, authorization denied, and recovery window exceeded. Keep the categories small and explicit. Here is an illustrative cardinality budget, not a benchmark: 4 outcome classes multiplied by 3 deployment environments gives 12 possible label combinations before other dimensions. Adding 10,000 room identifiers expands that upper bound to 120,000. Adding viewer identifiers expands it again. The arithmetic explains why room and viewer identity belong in a deliberately limited diagnostic record rather than in every time series. Count before collecting.

恢复完成是第三个边界。根据应用程序在对话中的预期位置来定义完成，而不是仅仅根据连接的套接字。有用的汇总结果包括“已追上”、“授权被拒绝”和“超过恢复窗口”。保持类别小而明确。这是一个说明性的基数预算，而不是基准：4 个结果类别乘以 3 个部署环境，在考虑其他维度之前就有 12 种可能的标签组合。增加 10,000 个聊天室标识符将上限扩大到 120,000。增加查看者标识符会再次扩大它。这种算术解释了为什么聊天室和查看者身份应该属于刻意限制的诊断记录，而不是每个时间序列。在收集之前先计算。

Retention deserves the same treatment. Assume, solely for planning, 100,000 diagnostic events per day at 300 bytes each. Seven days retains 210,000,000 raw bytes; 30 days retains 900,000,000. Neither figure includes indexes, replication, compression, or storage overhead. Replace those assumptions with measured event sizes before procurement. The multiplication already exposes the consequence of retaining every successful reconnect. The trade-off is explicit: choose complete aggregate counts over exhaustive successful-session traces because the operating question is how often recovery fails, while a full trace archive multiplies retained records by viewer activity. Sampling ordinary successes reduces retained evidence, but it also reduces detail available for reconstructing a particular viewer's session.

保留策略也应受到同等对待。仅为规划起见，假设每天有 100,000 个诊断事件，每个事件 300 字节。七天保留 210,000,000 原始字节；30 天保留 900,000,000 字节。这两个数字都不包括索引、复制、压缩或存储开销。在采购前，用测量的事件大小替换这些假设。乘法运算已经暴露了保留每次成功重新连接的后果。权衡是明确的：选择完整的汇总计数而不是详尽的成功会话跟踪，因为操作问题是恢复失败的频率，而完整的跟踪存档会根据查看者活动成倍增加保留的记录。对普通成功进行采样会减少保留的证据，但也会减少用于重建特定查看者会话的可用细节。

Preserve aggregate counts independently of sampled diagnostic records. Record permission denials and recovery-window failures through a bounded diagnostic policy, and avoid copying message bodies into those records. The resulting telemetry can explain recovery without becoming an unplanned archive of the room. Make this choice explicit in the support policy: an operator may be able to count successful recovery without reconstructing every successful session. Put the durable handoff inside the recovery contract. A queue and a socket solve different parts of this workflow. Persist the notification for later processing.

将汇总计数与采样的诊断记录分开保存。通过有界的诊断策略记录权限拒绝和恢复窗口失败，并避免将消息正文复制到这些记录中。由此产生的遥测数据可以解释恢复过程，而不会成为聊天室的非计划存档。在支持策略中明确这一选择：操作员可能能够在不重建每个成功会话的情况下计算成功恢复的次数。将持久移交放入恢复契约中。队列和套接字解决了此工作流的不同部分。持久化通知以供稍后处理。
