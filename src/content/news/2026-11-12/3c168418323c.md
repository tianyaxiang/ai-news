# Publish a Chrome Extension: 6 Steps and a Review Checklist

Originally published on ExtensionLaunch. To publish a Chrome extension, you need more than working code: the Chrome Web Store reviews your manifest, your permissions and your privacy answers before anyone can install it. Most first submissions that stall do so for avoidable reasons. Below are the six steps from developer account to first update, plus the checklist I'd run before pressing Submit.

本文最初发布于 ExtensionLaunch。要发布 Chrome 扩展程序，仅有可运行的代码是不够的：在任何人安装之前，Chrome 应用商店会审核你的清单文件（manifest）、权限设置以及隐私声明。大多数首次提交被搁置的原因都是可以避免的。以下是从开发者账号到首次更新的六个步骤，以及我在点击“提交”前会执行的检查清单。

### What to have ready before you open the dashboard
Gather these first so you aren't hunting for assets mid-form:
* A Google account (for anything beyond a hobby project, use a dedicated or Google Workspace account)
* An extension built on Manifest V3 (new Manifest V2 submissions are no longer accepted)
* A 128x128 PNG icon
* At least one screenshot at 1280x800 or 640x400
* A one-line summary, a longer description and a category
* A privacy policy URL if you handle user data (most extensions do)
* $5 for the one-time registration fee

### 在打开仪表板之前需要准备什么
请先收集好这些资料，以免在填写表单时手忙脚乱：
* 一个 Google 账号（如果是业余项目之外的用途，请使用专用账号或 Google Workspace 账号）
* 基于 Manifest V3 构建的扩展程序（不再接受新的 Manifest V2 提交）
* 一个 128x128 的 PNG 图标
* 至少一张 1280x800 或 640x400 的截图
* 一句简短的摘要、一段详细描述以及所属类别
* 如果你处理用户数据（大多数扩展程序都会），则需要一个隐私政策 URL
* 5 美元的一次性注册费

### Steps 1 to 3: account, manifest, package
1. Register as a developer. Sign in to the Chrome Web Store Developer Dashboard, pay the one-time $5 USD fee and verify your contact email. If you publish under a brand, set up a group publisher. You'll also have to declare whether you're a trader or a non-trader.
2. Tighten your manifest. Reviewers check your package against manifest.json, and two fields matter most: version and permissions. Over-broad permissions are the most common reason a first submission stalls. Request only the permissions your code actually calls. Scope host permissions to specific domains instead of `<all_urls>`. Use activeTab when you only need page access after the user clicks.

### 第 1 至 3 步：账号、清单与打包
1. 注册成为开发者。登录 Chrome 应用商店开发者仪表板，支付 5 美元的一次性费用并验证你的联系邮箱。如果你以品牌名义发布，请设置群组发布者。你还需要声明自己是贸易商还是非贸易商。
2. 精简你的清单文件。审核人员会根据 manifest.json 检查你的安装包，其中最重要的两个字段是版本号和权限。权限范围过大是首次提交被搁置的最常见原因。仅请求代码实际调用的权限。将主机权限限制在特定域名，而不是使用 `<all_urls>`。当你只需要在用户点击后获取页面访问权限时，请使用 activeTab。

3. Zip the right folder. manifest.json must sit at the root of the ZIP, not inside a parent folder. If you use a bundler, zip the build output, not your source. From inside the output directory: `zip -r ../my-extension.zip . -x "*.git*" "node_modules/*"`

3. 压缩正确的文件夹。manifest.json 必须位于 ZIP 文件的根目录，而不是父文件夹内。如果你使用打包工具，请压缩构建输出目录，而不是源代码。在输出目录内执行：`zip -r ../my-extension.zip . -x "*.git*" "node_modules/*"`

### Steps 4 and 5: listing, privacy and visibility
4. Fill in all three tabs. After uploading the ZIP, the dashboard asks for:
* Store listing: Name, summary, detailed description, category, language, icon, screenshots
* Privacy: Single purpose, a justification per permission, data-use disclosures, privacy policy URL
* Distribution: Visibility, regions, pricing
The Privacy tab is where vague answers hurt. State one clear purpose, explain each permission in plain language and make your data disclosures match what the code and the privacy policy say. If your extension needs a login, fill in the Test instructions tab so the reviewer can actually use it.

### 第 4 至 5 步：列表、隐私与可见性
4. 填写所有三个选项卡。上传 ZIP 文件后，仪表板会要求填写：
* 商店列表：名称、摘要、详细描述、类别、语言、图标、截图
* 隐私：单一用途、每个权限的理由、数据使用披露、隐私政策 URL
* 分发：可见性、地区、定价
“隐私”选项卡是容易因回答模糊而受阻的地方。请陈述一个明确的用途，用通俗易懂的语言解释每个权限，并确保你的数据披露与代码及隐私政策的内容一致。如果你的扩展程序需要登录，请填写“测试说明”选项卡，以便审核人员能够实际使用它。

5. Pick visibility, then submit.
* Public: shows up in search and category pages
* Unlisted: only reachable by direct link, good for a soft launch or beta
* Private: limited to named testers or your Workspace organization
A new extension usually clears review in a few hours to a few days. Sensitive permissions or a large codebase can stretch that, and there's no way to speed it up, so submit well before any announced launch date.

5. 选择可见性，然后提交。
* 公开：显示在搜索和类别页面中
* 不公开：仅可通过直接链接访问，适用于软发布或测试版
* 私有：仅限指定的测试人员或你的 Workspace 组织
一个新的扩展程序通常在几小时到几天内通过审核。敏感权限或庞大的代码库可能会延长审核时间，且无法加速，因此请务必在预定的发布日期前尽早提交。

### Step 6: ship updates without new trouble
The update loop is simple: bump version, re-zip, upload the new package and submit. Users get the update automatically over the following hours. Three rules keep it painless:
* Never reuse a version number. Chrome rejects any package whose version isn't higher than the published one.
* Keep permissions stable. Adding a sensitive one can trigger a fresh, slower review and re-prompt existing users.
* Write real release notes. They build trust with users and show reviewers what changed.

### 第 6 步：发布更新，避免麻烦
更新流程很简单：提升版本号、重新压缩、上传新包并提交。用户会在接下来的几小时内自动收到更新。遵循三条规则可确保过程顺利：
* 永远不要重复使用版本号。Chrome 会拒绝任何版本号不高于已发布版本的安装包。
* 保持权限稳定。添加敏感权限可能会触发新的、更缓慢的审核，并重新提示现有用户。
* 编写真实的发布说明。它们能建立用户信任，并向审核人员展示变更内容。

### The pre-submit checklist
* [ ] Manifest V3 with an accurate name and description, and a version higher than the last one
* [ ] Only permissions you use, each justified in plain language
* [ ] 128x128 icon and at least one correctly sized screenshot
* [ ] Privacy policy URL is live and matches your data disclosures
* [ ] ZIP built from compiled output, with manifest.json at the root

### 提交前检查清单
* [ ] Manifest V3，名称和描述准确，版本号高于上一个版本
* [ ] 仅包含你使用的权限，且每个权限都有通俗易懂的理由
* [ ] 128x128 图标和至少一张尺寸正确的截图
* [ ] 隐私政策 URL 可访问且与你的数据披露内容一致
* [ ] ZIP 包由编译后的输出构建，且 manifest.json 位于根目录

### Key takeaways
Narrow permissions are the biggest lever for a smooth first review. Zip the build output with manifest.json at the root. Your Privacy tab answers, your code and your privacy policy must agree. Budget hours to days for review and never schedule a launch the same day you submit. Every update needs a higher version number; avoid adding sensitive permissions casually. Approval is only the starting line.

### 关键要点
缩小权限范围是顺利通过首次审核的最大助力。请压缩构建输出目录，并确保 manifest.json 位于根目录。你在“隐私”选项卡中的回答、代码以及隐私政策必须保持一致。预留数小时到数天的审核时间，切勿将发布日期定在提交当天。每次更新都需要更高的版本号；避免随意添加敏感权限。获批仅仅是起点。
