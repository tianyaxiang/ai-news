# shadcn / improve

improve 是一项代理技能，用于审计任何代码库并编写供其他代理执行的实施计划。其核心理念是：将最强大的模型用于智能发挥作用的关键环节——理解代码库、判断工作的价值、编写规范——然后将执行工作交给成本更低的模型。该技能本身从不执行任何修改，计划即产品。

you → /improve (expensive model, advises) plans/ → 001-fix-n-plus-one.md (self-contained specs) other agent → implements, tests, ships (cheap model, executes)

安装方式：`npx skills add shadcn/improve`。它适用于任何支持 Agent Skills 格式的代理。它编写的计划是纯 Markdown 格式，因此任何代理（或人类）都可以直接使用。

### Usage
/improve full audit → prioritized findings → plans
/improve quick cheap pass: hotspots, top findings only
/improve deep exhaustive: every package, every category
/improve security focused audit (also: perf, tests, bugs, ...)
/improve branch audit only what the current branch changes
/improve next feature suggestions — where to take the project
/improve plan <description> skip the audit, spec one thing
/improve review-plan <file> critique and tighten an existing plan
/improve execute <plan> dispatch a cheaper executor, review its work
/improve reconcile refresh the backlog: verify, unblock, retire
/improve ... --issues also publish plans as GitHub issues

### How to use
典型的首次运行流程如下：在仓库中打开代理并运行 `/improve`（或使用 `/improve quick` 以节省成本）。它会映射仓库、进行审计，并返回一个发现列表。回复你想要规划的项目，例如“plan 1, 3 and 5”。计划将存放在 `plans/` 目录下——每个计划一个文件，并附带一个推荐顺序的索引。请阅读它们，因为它们旨在被审查。你可以将计划交给任何代理（“implement plans/001-*.md”），或者让该技能直接运行：`/improve execute 001`。它会在一个隔离的工作树中调度一个更便宜的模型，根据计划审查差异，并报告结果。合并操作仍由你决定。在下一次会话中，运行 `/improve reconcile` 来清理积压工作：验证已完成的内容，刷新已偏离的内容，解除被阻塞的内容。在提交 PR 之前，`/improve branch` 可以执行同样的操作，但仅限于当前分支所更改的范围。

### Example
针对 shadcn/ui 的一次运行返回了如下发现：
| # | Finding | Category | Effort | Confidence |
|---|------------------------------------------------|-----------|--------|------------|
| 1 | shadow-config duplicated in search.ts/view.ts, | tech-debt | M | HIGH |
| | copies already drifted (TODO at search.ts:31) | | | |
| 2 | O(n²) icon migration (migrate-icons.ts:168) | perf | S | HIGH |

……并拒绝了一些发现，同时记录了拒绝原因，以便在下次运行时不再出现：
- [SEC-01] https_proxy env var "SSRF": by-design — standard proxy convention, every CLI honors it. Not a finding.

选择 #1 后生成了此计划——包含当前代码摘录、确切步骤、作为验证门禁的仓库自身测试/lint 命令，以及当现实与预期不符时的停止条件。

### How it works
**侦察 (Recon)**：映射仓库：技术栈、约定以及确切的构建/测试/lint 命令——这些在每个计划中都成为验证门禁。它还会摄取现有的意图和设计文档（如 docs/adr/、PRDs、CONTEXT.md、DESIGN.md、PRODUCT.md），确保已决定的权衡不会被重新标记为发现，方向建议保持在既定的产品意图内，且计划使用仓库自身的术语。它适用于任何已经维护这些文档的仓库。

**审计 (Audit)**：在九个类别中并行分发子代理：正确性、安全性、性能、测试覆盖率、技术债务、依赖项与迁移、开发者体验 (DX)、文档和方向（功能建议——每一项都必须引用仓库本身的证据，拒绝通用的空洞想法）。每个发现都带有文件:行号证据、影响、工作量和置信度。

**审查 (Vet)**：由于子代理倾向于过度报告，顾问模型会在向你展示任何内容之前亲自重新阅读每个引用的位置——误报会被剔除，错误的归因会被纠正，拒绝记录会被保存。

**优先级排序 (Prioritize)**：发现结果会进入一个按杠杆率（影响 ÷ 工作量，并按置信度加权）排序的表格。你选择哪些内容成为计划。

**规划 (Plan)**：每个选定的发现对应一个文件，写入 `plans/` 目录，并附带索引、优先级顺序和依赖图。

### What makes the plans executable
计划是为最弱的可行执行者编写的——即一个从未见过顾问会话且可能规模小得多的模型。以下三个属性实现了这一点：

**自包含 (Self-contained)**：所有上下文均已内联：确切的文件路径、当前状态的代码摘录、带有示例文件的仓库约定、已验证的命令。没有“如上所述”之类的模糊表述。

**验证门禁 (Verification gates)**：每一步都以一个命令及其预期输出结束。完成标准是机器可检查的。执行者无需判断自己是否成功。

**硬边界 (Hard boundaries)**：明确的范围外列表和停止条件——“如果出现 X，停止并报告”——而不是让小模型在现实与计划不符时进行即兴发挥。每个计划还标记了编写时所依据的 git 提交记录，因此执行者在触碰任何内容之前会运行机械化的偏离检查。

### Closing the loop
计划并非“一发即忘”：`execute <plan>` 会在隔离的 git 工作树中生成一个更便宜的执行子代理，将计划交给它，然后像技术主管一样审查结果——重新运行每个完成标准，检查范围合规性，并根据意图读取差异。结论：批准（合并仍由你决定）、发回修改（最多 2 轮），或阻塞并细化计划。

`reconcile` 会处理自上次运行以来发生的情况：验证已完成 (DONE) 的计划是否仍然有效，调查被阻塞 (BLOCKED) 的计划并绕过障碍重写，刷新已偏离的计划，并撤销已独立修复的发现。

`--issues` 将计划发布为 GitHub Issues——保持相同的自包含主体，以便任何代理或人类可以在工作所在的地方接手。

### Hard rules
从不自行修改源代码。唯一的写入操作仅限于 `plans/` 目录；执行者仅在一次性工作树中进行编辑，合并操作始终由你掌控。从不运行会改变你工作目录的命令。
