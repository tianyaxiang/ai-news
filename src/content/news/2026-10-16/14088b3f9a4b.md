# Kubernetes CI: Lease Test Mailboxes, Don't Retry Blindly

Email verification tests become unreliable when the mailbox is treated like an ordinary HTTP dependency. A pipeline sends a message, waits a few seconds, sees nothing, and retries. The retry may create a duplicate message, race the first delivery, or consume a mailbox that another test owns. In Kubernetes CI, the cleaner model is an inbox lease: one test run reserves one isolated mailbox for a bounded period, records that ownership, and releases it whether the test passes or fails. This turns a vague polling problem into a resource-lifecycle problem that can be operated.

当将邮箱视为普通的 HTTP 依赖项时，电子邮件验证测试会变得不可靠。流水线发送一条消息，等待几秒钟，如果没有看到结果，就会重试。重试可能会创建重复的消息、与第一次投递产生竞争，或者占用另一个测试所拥有的邮箱。在 Kubernetes CI 中，更简洁的模型是收件箱租约：一次测试运行在有限的时间内预留一个隔离的邮箱，记录该所有权，并在测试通过或失败时释放它。这会将一个模糊的轮询问题转化为一个可操作的资源生命周期问题。

The failure mode: a mailbox is not a retryable dependency. Most email assertions have at least four separate steps: Create or reserve a test mailbox. Trigger the application event. Wait for the message to arrive and identify the right message. Release the mailbox and retain enough evidence to debug the run. If step three is implemented as “retry the whole test,” the pipeline can repeat step two as well. That creates false positives and makes delivery latency look like application flakiness. It also makes parallel Kubernetes Jobs collide when they use a shared address.

故障模式：邮箱不是可重试的依赖项。大多数电子邮件断言至少包含四个独立步骤：创建或预留测试邮箱；触发应用程序事件；等待消息到达并识别正确的消息；释放邮箱并保留足够的证据以调试运行。如果第三步被实现为“重试整个测试”，流水线也可能会重复第二步。这会产生误报，并使投递延迟看起来像是应用程序的不稳定性。当并行运行的 Kubernetes Job 使用共享地址时，也会导致冲突。

The phrases temp mail so and temp mail com sometimes appear in old test names or search logs. The label does not matter as much as the contract behind the mailbox: ownership, expiration, message identity, and cleanup must be explicit. Model the inbox as a leased resource. A useful lease record needs a small amount of state: { "run_id": "orders-pr-1842-7f3a", "mailbox_id": "mbx-91c2", "owner": "orders-e2e", "created_at": "2026-10-16T04:00:12Z", "expires_at": "2026-10-16T04:10:12Z", "expected_recipient": "mbx-91c2@example.test" }.

“temp mail so”和“temp mail com”等短语有时会出现在旧的测试名称或搜索日志中。标签本身并不重要，重要的是邮箱背后的契约：所有权、过期时间、消息标识和清理必须是明确的。将收件箱建模为租用资源。一个有用的租约记录需要少量的状态信息：{ "run_id": "orders-pr-1842-7f3a", "mailbox_id": "mbx-91c2", "owner": "orders-e2e", "created_at": "2026-10-16T04:00:12Z", "expires_at": "2026-10-16T04:10:12Z", "expected_recipient": "mbx-91c2@example.test" }。

The run_id is the correlation key. The expiration is the safety valve. If a worker disappears, a janitor can reclaim the mailbox after expires_at without guessing whether a test is still active. The lease should be created before the application event is triggered. Pass the mailbox address and run ID into the test as injected configuration, not as a hard-coded environment-wide value. In practice, this one detail prevents a surprising number of cross-run email assertions. For a concrete contract-test shape, see contract-test API emails in GitHub Actions. The same separation between triggering an event and proving delivery works well inside a Kubernetes Job.

run_id 是关联键。过期时间是安全阀。如果工作节点消失，清理程序可以在 expires_at 之后回收邮箱，而无需猜测测试是否仍在运行。租约应在触发应用程序事件之前创建。将邮箱地址和运行 ID 作为注入配置传递给测试，而不是作为硬编码的环境范围值。在实践中，这一个细节可以防止大量意外的跨运行电子邮件断言。关于具体的契约测试形式，请参阅 GitHub Actions 中的契约测试 API 电子邮件。触发事件与证明投递之间的这种分离在 Kubernetes Job 中同样适用。

A Kubernetes implementation: Keep the test Job short-lived and give it a deadline. A simplified manifest looks like this: apiVersion: batch/v1 kind: Job metadata: generateName: checkout-email- spec: backoffLimit: 0 activeDeadlineSeconds: 900 ttlSecondsAfterFinished: 3600 template: spec: restartPolicy: Never containers: - name: e2e image: registry.example.test/checkout-e2e:sha-abc123 env: - name: MAILBOX_LEASE_ID valueFrom: secretKeyRef: name: checkout-mailbox-lease key: lease_id - name: TEST_RUN_ID value: "orders-pr-1842-7f3a".

Kubernetes 实现：保持测试 Job 短期运行并设置截止日期。一个简化的清单如下所示：apiVersion: batch/v1 kind: Job metadata: generateName: checkout-email- spec: backoffLimit: 0 activeDeadlineSeconds: 900 ttlSecondsAfterFinished: 3600 template: spec: restartPolicy: Never containers: - name: e2e image: registry.example.test/checkout-e2e:sha-abc123 env: - name: MAILBOX_LEASE_ID valueFrom: secretKeyRef: name: checkout-mailbox-lease key: lease_id - name: TEST_RUN_ID value: "orders-pr-1842-7f3a"。

backoffLimit: 0 is intentional here. A Kubernetes-level restart can rerun the side effects that send email, while the lease and application test may not be idempotent. If the container needs a retry, make that retry narrow: poll for the expected message, do not submit the order again. The Job deadline is not a replacement for the mailbox expiration. They should be related but independent. A stuck pod should not keep a mailbox alive forever, and a mailbox service outage should not cause an unbounded CI wait.

此处设置 backoffLimit: 0 是故意的。Kubernetes 级别的重启可能会重新运行发送电子邮件的副作用，而租约和应用程序测试可能不是幂等的。如果容器需要重试，请缩小重试范围：轮询预期的消息，不要再次提交订单。Job 的截止日期不能替代邮箱的过期时间。它们应该是相关但独立的。卡住的 Pod 不应让邮箱永久保持活动状态，邮箱服务中断也不应导致 CI 无限期等待。

Correlate messages before asserting them: Never assert only on recipient and subject when parallel runs are possible. Use a unique run token in a header, URL parameter, or test-specific payload field. Then make the assertion sequence explicit: lease mailbox, trigger event once, poll for run_id until deadline, assert exactly one matching message, assert token and destination, write run receipt, release lease. A matching message should be claimed atomically if the mailbox API supports claiming. Otherwise, two test workers can both read the same message and report success.

在断言消息之前先进行关联：当可能存在并行运行时，切勿仅根据收件人和主题进行断言。在标头、URL 参数或特定于测试的有效负载字段中使用唯一的运行令牌。然后明确断言顺序：租用邮箱、触发一次事件、轮询 run_id 直到截止日期、断言恰好有一条匹配消息、断言令牌和目标、写入运行回执、释放租约。如果邮箱 API 支持声明，则应以原子方式声明匹配的消息。否则，两个测试工作节点可能会同时读取同一条消息并报告成功。

A receipt should include the message ID, delivery timestamp, run ID, and sanitized assertion result. Avoid storing full message bodies when a token or header is sufficient. This is the same operational idea as API smoke tests with explicit receipts: a green check is more useful when it carries proof that can be connected to one run.

回执应包含消息 ID、投递时间戳、运行 ID 和脱敏后的断言结果。当令牌或标头已足够时，避免存储完整的消息正文。这与带有明确回执的 API 冒烟测试具有相同的操作理念：当绿色勾选标记携带可关联到单次运行的证据时，它才更有用。

Retry policy and cleanup: Separate retries into three budgets: Provisioning retry: retry lease creation only when the service reports a transient failure, and use an idempotency key based on run_id. Delivery polling: poll with a capped interval, such as 2, 4, 8, and 10 seconds, until the test deadline. Assertion retry: do not retry a failed token or recipient assertion. That is an application failure, not eventual consistency. Always release the lease in a cleanup path. If the test process is killed, the expiration and a periodic janitor are the fallback.

重试策略和清理：将重试分为三个预算：配置重试：仅在服务报告瞬时故障时重试租约创建，并使用基于 run_id 的幂等键。投递轮询：以受限的时间间隔（例如 2、4、8 和 10 秒）轮询，直到测试截止日期。断言重试：不要重试失败的令牌或收件人断言。那是应用程序故障，而不是最终一致性。始终在清理路径中释放租约。如果测试进程被杀死，过期时间和定期清理程序将作为后备方案。

Alert on leases that are reclaimed by expiry; they usually indicate a dead worker, a missing cleanup hook, or a timeout that is too short. Be careful with logs. A typo like tempail or tamp mail com can be useful when tracing legacy configuration, but it should not become a mailbox identity or a routing rule. Store the canonical lease ID and run ID alongside any human-readable labels.

对因过期而被回收的租约发出警报；它们通常表示工作节点已死、缺少清理钩子或超时设置过短。小心处理日志。像 tempail 或 tamp mail com 这样的拼写错误在追踪遗留配置时可能有用，但它们不应成为邮箱标识或路由规则。将规范的租约 ID 和运行 ID 与任何人类可读的标签一起存储。

Operational checklist: Before relying on this pattern, verify: Every parallel Job receives a unique mailbox lease. The application event is triggered once per run. Polling filters on a run-specific identifier. Kubernetes retries cannot repeat an email-producing side effect. Lease expiration is shorter than the overall cleanup window. Receipts contain message ID, run ID, and sanitized outcomes. A janitor reclaims abandoned leases and emits a useful metric. CI fails on assertion mismatch instead of hiding it in another retry. The main payoff is boring, predictable email testing. Kubernetes can schedule the work, but it should not be responsible for understanding mailbox ownership. Put that contract in the test workflow, give every lease a deadline.

操作检查清单：在依赖此模式之前，请验证：每个并行 Job 是否接收到唯一的邮箱租约；应用程序事件是否在每次运行中仅触发一次；轮询是否基于运行特定的标识符进行过滤；Kubernetes 重试是否无法重复产生电子邮件的副作用；租约过期时间是否短于整体清理窗口；回执是否包含消息 ID、运行 ID 和脱敏后的结果；清理程序是否回收了废弃的租约并发出有用的指标；CI 是否在断言不匹配时失败，而不是将其隐藏在另一次重试中。主要收益是枯燥、可预测的电子邮件测试。Kubernetes 可以调度工作，但不应负责理解邮箱所有权。将该契约放入测试工作流中，并为每个租约设置截止日期。
