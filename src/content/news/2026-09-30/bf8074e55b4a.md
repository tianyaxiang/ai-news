# AI code review that follows your team's rules: what each tool actually ingests
# 遵循团队规范的 AI 代码审查：各工具实际摄取的内容解析

"Follows our coding standards" is the phrase teams use when they mean "does not post the same generic nit for the fourth time." It sounds like one feature. It is at least three, and they fail in different ways. The mechanisms are: a rule file the tool reads and treats as review criteria, a per-path instruction that scopes guidance to a directory, and an enforcement rule with a pass or fail attached.
“遵循我们的编码标准”是团队用来表达“不要第四次提出同样的通用琐碎建议”时所用的短语。这听起来像是一个功能，但实际上至少包含三个，且它们在不同方面存在局限。这些机制包括：工具读取并作为审查标准的规则文件、将指导范围限定在特定目录的路径指令，以及带有通过/失败判定的强制执行规则。

A tool can ship one of these and call the result "custom standards." Whether that is enough depends on what your team actually needs, and whether it runs on the edition you are on. That last part matters more than the feature list. On GitLab Self-Managed, Azure DevOps Server and Bitbucket Data Center, hosted rule ingestion is the first thing to disappear.
工具可以仅提供其中一种机制，并将其称为“自定义标准”。这是否足够，取决于你团队的实际需求，以及它是否能在你所使用的版本上运行。最后一点比功能列表本身更重要。在 GitLab 自托管版、Azure DevOps Server 和 Bitbucket Data Center 上，托管规则摄取功能往往是首先被砍掉的部分。

### Three mechanisms that get called "your standards"
### 被称为“你的标准”的三种机制

An ingested rule file is the lowest-effort option. You already have a CLAUDE.md, an AGENTS.md, a .cursorrules, or a docs/coding-standards/ folder in the repo. The reviewer scans for those files and uses their content as review criteria. The upside is that the standards document already exists and both humans and coding agents read it. The downside is that the file is guidance, not a check. The reviewer interprets it, and interpretation is inconsistent across runs.
摄取规则文件是成本最低的选择。你的仓库中可能已经有了 CLAUDE.md、AGENTS.md、.cursorrules 或 docs/coding-standards/ 文件夹。审查工具会扫描这些文件，并将它们的内容作为审查标准。优点是标准文档已经存在，且人类和编码代理都能读取它；缺点是该文件仅作为指导，而非强制检查。审查工具对其进行解读，而这种解读在不同运行之间可能存在不一致。

A per-path instruction is a mapping from a glob to free text. You tell the reviewer that anything under src/controllers/** should be checked for auth, input validation, and direct database calls that bypass the ORM. This is more precise than a global guideline file because the guidance only applies where it belongs, which is the difference between useful and noisy in a monorepo.
路径指令是将 glob 模式映射到自由文本。你可以告诉审查工具，src/controllers/** 下的所有内容都应检查身份验证、输入验证以及绕过 ORM 的直接数据库调用。这比全局指导文件更精确，因为指导仅在适用的地方生效，这在单体仓库（monorepo）中是“有用”与“嘈杂”的区别所在。

An enforcement rule with a verdict is the strictest option. The rule has a severity, a path scope, and it either fires or it does not. This is what teams reach for when the requirement is "the reviewer must block this," and it is the mechanism least likely to be available on every plan. Severity levels and the ability to gate a merge are where vendors draw plan lines.
带有判定的强制执行规则是最严格的选择。该规则具有严重性级别、路径范围，且要么触发，要么不触发。当团队要求“审查工具必须拦截此行为”时，他们会寻求这种机制，这也是最不可能在所有套餐中都提供的机制。严重性级别和合并拦截能力是供应商划分套餐界限的地方。

The practical consequence: if your team's real complaint is that the reviewer misses your conventions, a rule file and per-path instructions handle it. If the complaint is that the reviewer is inconsistent and you need a hard stop, only the third mechanism does that, and it may sit behind a paid tier or a licensed self-hosted deployment.
实际后果是：如果团队真正的抱怨是审查工具遗漏了你们的约定，那么规则文件和路径指令就能解决；如果抱怨的是审查工具不一致且你需要强制拦截，则只有第三种机制能做到，且它可能位于付费层级或授权的自托管部署之后。

### What CodeRabbit ingests, and where it stops
### CodeRabbit 摄取的内容及其局限

CodeRabbit detects guideline files automatically and applies them as review criteria with no configuration. The code guidelines docs list the patterns: **/AGENTS.md, **/.cursorrules, .github/copilot-instructions.md, .github/instructions/*.instructions.md, **/CLAUDE.md, **/.windsurfrules, **/.clinerules/*, **/.rules/*, among others. Matching is case-sensitive, so a file named claude.md is not picked up.
CodeRabbit 会自动检测指导文件，并将其作为审查标准应用，无需配置。代码指南文档列出了这些模式：**/AGENTS.md, **/.cursorrules, .github/copilot-instructions.md, .github/instructions/*.instructions.md, **/CLAUDE.md, **/.windsurfrules, **/.clinerules/*, **/.rules/* 等。匹配是区分大小写的，因此名为 claude.md 的文件不会被识别。

Scoping is directory-based. A CLAUDE.md at the repo root applies to everything; src/backend/.cursorrules applies only under src/backend/. When directory placement does not match the files a guideline should govern, you switch to the object form of filePatterns with an explicit applyTo glob. That is the per-path mechanism, and it is the one that makes a monorepo workable.
作用域基于目录。仓库根目录下的 CLAUDE.md 适用于所有内容；src/backend/.cursorrules 仅适用于 src/backend/ 下。当目录位置与指导文件应覆盖的文件不匹配时，你可以切换到 filePatterns 对象形式，并使用显式的 applyTo glob。这就是路径指令机制，也是让单体仓库变得可行的关键。

Guidelines can also come from another repository, written as repo:path or owner/repo:path. Here the edition split shows up. On GitHub the source and reviewed repos must share an organization, on GitLab they must share a top-level group, and Bitbucket Cloud must share a workspace. The docs mark the Bitbucket entry Cloud Only. Cross-repo guideline reuse is not a path available on Bitbucket Data Center.
指导也可以来自另一个仓库，格式为 repo:path 或 owner/repo:path。这里体现了版本差异：在 GitHub 上，源仓库和被审查仓库必须共享同一个组织；在 GitLab 上必须共享同一个顶级组；在 Bitbucket Cloud 上必须共享同一个工作区。文档标注 Bitbucket 条目为“仅限云端”。跨仓库指导复用在 Bitbucket Data Center 上不可用。

One trap worth calling out because it is easy to hit: adding a guideline filename like CLAUDE.md to path_instructions does not use it as a guideline. It tells the reviewer to review that file as changed code. Use filePatterns.
有一个值得注意的陷阱：将 CLAUDE.md 这样的指导文件名添加到 path_instructions 中并不会将其作为指导使用，而是告诉审查工具将该文件作为已更改的代码进行审查。请使用 filePatterns。

### Qodo's governance layer
### Qodo 的治理层

Qodo routes rule and standards questions to its governance area rather than its review area. The code governance docs describe Review Standards as turn "your organization's engineering conventions into something that can actually be enforced," with rule enforcement as the explicit, checkable form. There is also a REVIEW.md instructions file and rule generation from PR history indexing.
Qodo 将规则和标准问题路由到其治理区域，而不是审查区域。代码治理文档将“审查标准”描述为将“组织的工程约定转化为可实际执行的内容”，并将规则执行作为明确的、可检查的形式。此外还有 REVIEW.md 指令文件以及通过 PR 历史索引生成的规则。

The difference from CodeRabbit's approach is where the configuration lives. CodeRabbit reads files that are already in the repo. Qodo's standards are managed as governance objects in the portal, which suits an org that wants one set of rules across every repository without relying on each repo carrying the right file. It also means the standards are not part of the codebase, so a review of a rule change is not a code review.
与 CodeRabbit 的区别在于配置的位置。CodeRabbit 读取仓库中已有的文件；Qodo 的标准则作为治理对象在门户网站中管理，这适合那些希望在所有仓库中统一一套规则，而不依赖于每个仓库都包含正确文件的组织。这也意味着标准不是代码库的一部分，因此对规则变更的审查不是代码审查。

Both approaches are legitimate and they fail differently. Repo-resident files drift when teams copy them and forget to update. Portal-managed rules drift when the portal is edited and nobody notices. Pick based on which of those two failure modes your team already handles.
两种方法都是合理的，但它们的局限性不同。驻留在仓库中的文件在团队复制并忘记更新时会产生偏差；门户管理的规则在门户被编辑且无人察觉时会产生偏差。请根据你的团队目前更能处理哪种失效模式来做出选择。

### Kodus and rule files
### Kodus 与规则文件

Kodus ships rule following as a first-class path rather than a side feature. Its Kody Rules overview splits rules into file-level and pull-request-level, with each rule carrying a severity of Critical, High, Medium or Low and a path scope using globs. Rules can reference other files with @file:src/services/userService.ts or @repo:team/api-standards to check consistency against a standard outside the reviewed repo, and can call MCP functions during evaluation.
Kodus 将规则遵循作为核心功能而非辅助功能。其 Kody Rules 概览将规则分为文件级和拉取请求级，每条规则都带有严重性（严重、高、中、低）和使用 glob 的路径范围。规则可以通过 @file:src/services/userService.ts 或 @repo:team/api-standards 引用其他文件，以检查与被审查仓库之外的标准的一致性，并可在评估期间调用 MCP 函数。

The distinction that matters for teams already using a coding agent: rules file detection imports the same files CodeRabbit does, plus more, including .sourcegraph/**/*.rule.md, .opencode.json, .aider.conf.yml and docs/coding-standards/**/*. Unlike CodeRabbit's case-sensitive matching, Kodus matches case-insensitively. Nested files are scoped automatically: a services/billing/CLAUDE.md is imported and scoped to services/billing/**. Files it generates rules from are re-synced when a PR closes, and @kody-ignore keeps a file in the repo without it becoming an enforced.
对于已经在使用编码代理的团队来说，重要的区别在于：规则文件检测不仅导入了 CodeRabbit 所支持的文件，还包括 .sourcegraph/**/*.rule.md, .opencode.json, .aider.conf.yml 和 docs/coding-standards/**/*. 等。与 CodeRabbit 的区分大小写匹配不同，Kodus 匹配时不区分大小写。嵌套文件会自动确定作用域：services/billing/CLAUDE.md 会被导入并限定在 services/billing/** 范围内。它生成规则的文件会在 PR 关闭时重新同步，且 @kody-ignore 可以让文件保留在仓库中而不被强制执行。
