# Dockerized Mail Capture for AWS CI Pipelines

Email verification tests become unreliable when every CI job reads from the same inbox. A message from a previous run can look valid, a retry can consume the wrong token, and a failed pipeline can leave sensitive URLs in artifacts. A better boundary is to give each run its own disposable address and capture service. Package the capture layer in Docker, make the fixture lifecycle explicit, and pass only a small receipt back to the AWS pipeline. The result is easier to debug without turning email content into permanent test data.

当每个 CI 任务都从同一个收件箱读取邮件时，电子邮件验证测试就会变得不可靠。来自上一次运行的消息可能看起来仍然有效，重试可能会消耗错误的令牌，而失败的流水线可能会在制品中留下敏感的 URL。更好的边界划分是为每次运行提供其专属的一次性地址和捕获服务。将捕获层打包在 Docker 中，明确固定装置（fixture）的生命周期，并仅将简短的收据传回 AWS 流水线。这样不仅更易于调试，也不会将电子邮件内容变成永久的测试数据。

Why email capture belongs inside the test boundary An email test has more moving parts than a normal API assertion: the application creates a verification token; a mail provider or local capture service accepts the message; the test finds the expected message; the browser or API consumes the token; cleanup removes the fixture after the run. If those parts share a mailbox, the test has no strong answer to a basic question: did this message belong to this attempt? Subject matching is not enough when two AWS jobs run in parallel. A unique recipient, run identifier, and expiration time are much stronger correlation fields. The same ownership idea is useful for one-owner email fixtures. One test attempt should create, read, and release its own fixture. Other jobs should not be able to discover it by accident.

为什么电子邮件捕获应属于测试边界之内？电子邮件测试比普通的 API 断言涉及更多的动态部分：应用程序创建验证令牌；邮件提供商或本地捕获服务接收消息；测试查找预期的消息；浏览器或 API 消耗令牌；清理程序在运行后移除固定装置。如果这些部分共享同一个邮箱，测试就无法有力地回答一个基本问题：这条消息是否属于本次尝试？当两个 AWS 任务并行运行时，仅靠主题匹配是不够的。唯一的收件人、运行标识符和过期时间是更强的关联字段。这种所有权理念同样适用于单所有者电子邮件固定装置。一次测试尝试应该创建、读取并释放其自己的固定装置，其他任务不应意外发现它。

Give every CI run its own fixture The fixture contract can stay small. At creation time, record something like this: { "run_id": "build-1842-attempt-1", "recipient": "build-1842-attempt-1@example.test", "fixture_id": "mail-7f31", "expires_at": "2026-10-13T03:00:00Z" } The address does not need to be memorable. It needs to be unique, searchable, and scoped to one attempt. Store the fixture identifier in the test environment and use it when querying messages. Do not use the newest message in an inbox as an implicit selector. A useful rule is that a retry creates a new fixture and a new token. Reusing the original one seems efficient, but the failure history become ambiguous. It also make parallel debugging harder because the same message can be claimed twice. Fresh identifiers cost very little compared with investigating a false-positive test.

为每次 CI 运行提供专属的固定装置。固定装置的契约可以保持简洁。在创建时，记录如下信息：{ "run_id": "build-1842-attempt-1", "recipient": "build-1842-attempt-1@example.test", "fixture_id": "mail-7f31", "expires_at": "2026-10-13T03:00:00Z" }。地址不需要好记，它只需要是唯一的、可搜索的，并限定在单次尝试范围内。将固定装置标识符存储在测试环境中，并在查询消息时使用它。不要将收件箱中的最新消息作为隐式选择器。一个有用的规则是：重试应创建新的固定装置和新的令牌。重用原始令牌看似高效，但会导致失败历史变得模糊。这也增加了并行调试的难度，因为同一条消息可能会被认领两次。与调查误报测试相比，使用新的标识符成本极低。

A small Docker capture service The capture container can expose a private HTTP API to the test runner while accepting SMTP from the application container. It should support only the operations the tests need: POST /fixtures create a run-scoped fixture POST /messages/query find messages for a fixture POST /messages/claim claim one matching message DELETE /fixtures/id release a fixture Keep the service on an isolated Docker network. The application can reach the SMTP endpoint, while the public edge of the test environment cannot. A minimal compose fragment might look like this: services: mail-capture: image: internal/mail-capture:latest networks: [test-net] environment: FIXTURE_TTL_SECONDS: "900" app: environment: SMTP_HOST: mail-capture SMTP_PORT: "2525" networks: [test-net] networks: test-net: internal: true The image should be pinned by digest in the real pipeline, not left on a floating latest tag. The capture service also needs a bounded body size and a clear policy for attachments. Most verification tests need a link and a few headers, not a permanent archive of every MIME part.

小型 Docker 捕获服务。捕获容器可以向测试运行器公开一个私有的 HTTP API，同时从应用程序容器接收 SMTP。它应仅支持测试所需的操作：POST /fixtures（创建运行范围内的固定装置）、POST /messages/query（查找固定装置的消息）、POST /messages/claim（认领匹配的消息）、DELETE /fixtures/id（释放固定装置）。将该服务保持在隔离的 Docker 网络中。应用程序可以访问 SMTP 端点，而测试环境的公共边缘则无法访问。一个最小化的 compose 片段如下：services: mail-capture: image: internal/mail-capture:latest networks: [test-net] environment: FIXTURE_TTL_SECONDS: "900" app: environment: SMTP_HOST: mail-capture SMTP_PORT: "2525" networks: [test-net] networks: test-net: internal: true。在实际流水线中，镜像应通过摘要（digest）锁定，而不是使用浮动的 latest 标签。捕获服务还需要限制正文大小，并制定明确的附件处理策略。大多数验证测试只需要链接和少量标头，而不是每个 MIME 部分的永久存档。

Keep AWS pipeline logs useful but safe AWS CI logs are valuable when they show correlation, timing, and the final assertion. They are risky when they show a complete verification URL. A receipt should contain identifiers and outcomes, for example: { "fixture_id": "mail-7f31", "message_id": "msg-91ab", "received_at": "2026-10-13T02:35:12Z", "token_status": "accepted", "cleanup_status": "released" } Keep the raw token in memory for the shortest practical time. Redact query strings before the logger sees them, rather than trying to hide them later in a dashboard. If a debugging artifact must include the message, encrypt it, shorten its retention, and make access explicit. This receipt pattern also fits delivery receipts in deployment gates. A pipeline should be able to prove that delivery and consumption happened for the intended run, without copying the whole email into the release record. Legacy suites sometimes contain search values such as dummy e mail or fake e mail com. Keep those as plain test data when compatibility requires it. They should never become backlink anchors, credentials, or production selectors.

保持 AWS 流水线日志有用且安全。当 AWS CI 日志显示关联性、时序和最终断言时，它们是有价值的；但当它们显示完整的验证 URL 时，则存在风险。收据应包含标识符和结果，例如：{ "fixture_id": "mail-7f31", "message_id": "msg-91ab", "received_at": "2026-10-13T02:35:12Z", "token_status": "accepted", "cleanup_status": "released" }。将原始令牌保留在内存中的时间应尽可能短。在日志记录器看到查询字符串之前就将其脱敏，而不是事后再尝试在仪表板中隐藏它们。如果调试制品必须包含消息，请对其加密、缩短保留期限并明确访问权限。这种收据模式也适用于部署门禁中的交付收据。流水线应能证明交付和消耗发生在预期的运行中，而无需将整封电子邮件复制到发布记录中。遗留套件有时包含如 dummy e mail 或 fake e mail com 等搜索值。当兼容性需要时，将它们保留为普通测试数据，但它们绝不能成为反向链接锚点、凭据或生产选择器。

Cleanup, retries, and failure receipts Cleanup must work on both success and failure. Ask the test runner to release the fixture in a finally block, then let a janitor remove abandoned fixtures after their TTL. The janitor is the last line of defense for cancelled jobs and broken agents. For an AWS pipeline, publish the small receipt as a short-lived artifact and emit metrics for: time from fixture creation to message arrival; messages rejected because their run id did not match; expired fixtures found by the janitor; token claims that were already consumed; cleanup failures. Do not make the cleanup step depend on the browser test passing. The pipeline become much easier to operate when resource release has its own result and alert path. A failed cleanup should be visible, but it should not cause the test to retry and send another message without a decision.

清理、重试和失败收据。清理工作必须在成功和失败的情况下都能正常运行。要求测试运行器在 finally 代码块中释放固定装置，然后让清理程序（janitor）在 TTL 到期后移除废弃的固定装置。清理程序是针对已取消任务和损坏代理的最后一道防线。对于 AWS 流水线，将简短的收据作为短生命周期的制品发布，并针对以下指标发出度量：从创建固定装置到消息到达的时间；因运行 ID 不匹配而被拒绝的消息；清理程序发现的过期固定装置；已被消耗的令牌认领；清理失败。不要让清理步骤依赖于浏览器测试的通过。当资源释放拥有独立的运行结果和警报路径时，流水线会变得更容易操作。清理失败应可见，但不应导致测试在未经决策的情况下重试并发送另一条消息。

Operational checklist Before adopting this pattern, check that: Every attempt gets a unique disposable address and fixture id. The capture image is pinned and the Docker network is private. Queries require fixture correlation, not only a subject line. Verification URLs and message bodies are excluded from normal logs. Retries create fresh fixtures and tokens. TTL cleanup handles cancelled and retryed jobs. Receipts contain enough timing data to diagnose delivery delays. The contract pay off when a failure happens at 2 AM: the pipeline can show what was created, what arrived, what was claimed, and what was released without exposing the secret that made the test pass.

运维检查清单。在采用此模式之前，请检查：每次尝试是否都获得了唯一的一次性地址和固定装置 ID；捕获镜像是否已锁定且 Docker 网络是否私有；查询是否需要固定装置关联，而不仅仅是主题行；验证 URL 和消息正文是否已从常规日志中排除；重试是否创建了新的固定装置和令牌；TTL 清理是否处理了已取消和重试的任务；收据是否包含足够的时序数据以诊断交付延迟。当凌晨 2 点发生故障时，该契约将发挥作用：流水线可以显示创建了什么、到达了什么、认领了什么以及释放了什么，而无需暴露使测试通过的秘密。
