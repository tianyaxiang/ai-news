What is clice?# In short, clice is a C/C++ language server written in modern C++, but it’s more than just a language server. It is still built on LLVM/Clang, but unlike clangd and ccls, which are also Clang-based, clice was redesigned from the ground up to fix architectural problems that have gone unsolved in those servers for years. It is written entirely in C++23 and serves as an example of modern C++ best practices in its own right, with all the major modern C++ features coming together remarkably well: Written entirely with C++20 coroutines, using our own libuv-based structured-concurrency async library for intricate asynchronous logic. It is a complex concurrent program running an event loop on the main thread while coordinating both multiple processes (IPC) and multiple threads. Written entirely with C++20 named modules and C++23 import std, and fully self-hosted: module wrappers for third-party libraries are generated automatically by clice modularize, and clice runs smoothly on its own codebase to provide module-aware language services. Uses static reflection built on templates and C++20 concepts for all serialization and deserialization across formats, including TOML, JSON, bincode, blob, and command-line arguments, with Rust-macro-like declarative annotations and zero boilerplate. Data-oriented code design throughout, with almost no virtual functions outside the callback interfaces Clang requires. Makes heavy use of modern C++ APIs like std::format, std::expected, std::ranges, and std::views, steering clear of outdated legacy C++98/11 APIs. A completely hermetic, reproducible build powered by Bazel, compiled with the unified xclang toolchain for a consistent cross-platform cross-compilation workflow. Compiled binaries are heavily optimized (PGO + LTO), and build artifacts depend on nothing beyond system libraries. People are always debating whether modern C++ features like modules are actually ready for real work. clice’s answer is: yes, of course, completely usable! They hold up for complex software like clice, with hundreds of thousands of lines of code. Maybe this is what the modern C++ we have been hoping for looks like. That said, the surrounding ecosystem really is inconvenient enough right now that getting this whole workflow running end to end took a huge amount of effort on my part to track issues and adapt everything.

什么是 clice？简而言之，clice 是一个用现代 C++ 编写的 C/C++ 语言服务器，但它不仅仅是一个语言服务器。它仍然构建在 LLVM/Clang 之上，但与同样基于 Clang 的 clangd 和 ccls 不同，clice 是从零开始重新设计的，旨在解决这些服务器多年来未解决的架构问题。它完全用 C++23 编写，本身就是现代 C++ 最佳实践的典范，所有主要的现代 C++ 特性都结合得非常出色：完全使用 C++20 协程编写，使用我们自己基于 libuv 的结构化并发异步库来处理复杂的异步逻辑。它是一个复杂的并发程序，在主线程上运行事件循环，同时协调多个进程（IPC）和多个线程。完全使用 C++20 命名模块和 C++23 import std 编写，并完全自托管：第三方库的模块包装器由 clice modularize 自动生成，clice 在其自身代码库上运行顺畅，以提供感知模块的语言服务。使用基于模板和 C++20 Concepts 构建的静态反射，用于跨格式的所有序列化和反序列化，包括 TOML、JSON、bincode、blob 和命令行参数，具有类似 Rust 宏的声明式注解且零样板代码。全程采用面向数据的代码设计，除了 Clang 要求的回调接口外，几乎没有虚函数。大量使用 std::format、std::expected、std::ranges 和 std::views 等现代 C++ API，避开了过时的 C++98/11 旧 API。由 Bazel 提供支持的完全封闭、可重复的构建，使用统一的 xclang 工具链编译，以实现一致的跨平台交叉编译工作流。编译后的二进制文件经过深度优化（PGO + LTO），构建产物不依赖于系统库之外的任何东西。人们总是在争论模块等现代 C++ 特性是否真的为实际工作做好了准备。clice 的回答是：是的，当然，完全可用！它们经受住了像 clice 这样拥有数十万行代码的复杂软件的考验。也许这就是我们一直期待的现代 C++ 的样子。话虽如此，目前的周边生态系统确实还不够方便，以至于我花费了巨大的努力来追踪问题并适配所有内容，才使整个工作流端到端地运行起来。

Language Server# Here is an overview of clice’s main features: Multi-process compilation: clice compiles code in a process pool modeled after modern web browsers, whereas clangd uses multithreading. Why multiple processes? Because C++ is simply too complex, and on certain corner cases the compiler can easily crash or leak memory. That is especially true for incomplete code in the middle of editing: a huge downstream user base tests compilers on complete code, while very few people test them on half-written code, where the compiler mostly falls back on best-effort heuristics. In clangd, a compiler crash takes down the whole server and forces a restart. In clice, compilation happens in isolated child processes: losing one worker does not affect the rest of the server, so go-to-definition, highlighting, and other services keep working. It also makes it much easier to manage memory usage and schedule compilation priorities, cutting down on unnecessary resource consumption. Modules and shared caching: clice has full support for C++20 named modules. All you need is a compile_commands.json containing all module files, and clice scans dependencies on its own and lazily builds required modules on demand, regardless of your build system or compiler, with full support for module completion, highlighting, go-to-definition, hover, and more. Built PCHs and PCMs are also cached on local disk for reuse across sessions. By comparison, clangd offers only very limited module support and no persistent cache. Compilation context: clice has full support for non-self-contained files, and more generally for the concept of a compilation context. You can explicitly pick the active context of a file: a specific compile command for a source file, or a specific inclusion site for a header. When you open a non-self-contained file, clice detects its context automatically, so it works out of the box. More broadly, it also supports grouping compile commands into build configurations, letting you switch between, say, debug and release. Better template support: clice implements a DFS pseudo instantiator that infers what many dependent names resolve to without needing concrete template arguments for a full instantiation.
