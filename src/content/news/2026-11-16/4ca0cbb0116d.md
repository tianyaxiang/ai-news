### alive365: An Uptime Monitor That Checks Past the Login Page

主页可能会返回 200 状态码，但实际上没人能登录。简单的正常运行时间检查会将该站点报告为健康。alive365 是我们在 EarthLink Network 构建的正常运行时间监控 SaaS。它会按计划调用您的站点和 API，并通过登录或结账步骤运行真实的浏览器，因此“页面加载但无法使用”之类的故障也会被发现。alive365 尚未开放注册。本文通过我们的开发环境，逐屏展示了它的功能及其适用对象；其中的每个目标都是演示用的。简而言之，alive365 会在外部按计划检查您的站点和 API 是否正常运行。检查分为两种：一种是浏览器检查，可重放最多 50 个步骤的登录或结账流程；另一种是 HTTP 检查，用于调用 URL（可以先进行登录）。一次故障会成为一个事件，列在仪表板的“事件”下。重复的失败会被添加到同一个事件中，而不是开启新的事件，且在连续五次成功后确认恢复。每日报告可以在每天早上发送到电子邮件或 Webhook（例如 Slack）。它适合那些运行自己的网站、商店或 SaaS，且没有专人负责监控的小型团队。如果您想尝试，请联系我们（见第 9 节末尾）。

#### 1. The monitor list and the two kinds of checks
监控列表页面列出了每一项检查：其类型（HTTP 或 BROWSER）、URL 以及运行频率（间隔）。“新建监控”会询问类型。有两种可用：HTTP 请求使用 GET 或 POST 调用 URL，并检查状态码是否为您预期的（例如 200）。将其用于 API 健康端点和应该打开的页面。浏览器旅程驱动真实的浏览器完成流程，并检查其是否到达终点。第 2 节将详细介绍。间隔时间为 1、3、5、10、15、30 或 60 分钟。

#### 2. Browser checks for login and checkout
主页返回 200 并不意味着登录按钮有效或购物车可以打开。浏览器检查则可以做到。您列出客户采取的步骤，alive365 会在真实的浏览器（由 Playwright 驱动的 Chromium）中按顺序运行它们。这些步骤是在“旅程构建器”中构建的。共有六种步骤类型：导航（打开 URL）、输入（填充字段）、点击（按下按钮或链接）、等待（等待设定的时间或直到元素出现）、断言（检查元素是否在页面上）、截图（捕获该点的页面）。一个旅程最多可以有 50 个步骤。如果某个步骤缺少 URL 或选择器，屏幕会显示“旅程无效”且不会继续。密码不会直接进入步骤本身；步骤可以指向存储的密钥，格式为 {{secrets.<name>}}。浏览器仅在检查运行时启动。在此期间没有任何程序在运行。

#### 3. HTTP checks behind a login
会员页面和管理 API 需要登录。HTTP 检查的“身份验证”选项卡会在请求前进行登录。有五个选项：无（不登录）、基本认证（用户名和密码）、Bearer Token（大多数 API 使用的令牌）、API 密钥（在您指定的标头中发送的密钥，例如 X-API-Key）、表单登录（将用户名和密码发布到登录表单，保持会话，然后检查目标页面）。密码和令牌在存储前会被加密，之后屏幕和 API 都不会返回它们。“登录 URL”可以留空。alive365 随后会直接打开目标页面而不进行登录，并将重定向到的页面用作登录页面。每个环境的加密密钥都是独立的，并保存在 AWS SSM 参数存储中。存储的值仅在检查运行时解密。表单登录适用于普通的登录表单。正如屏幕所示，构建为单页应用或受 MFA 保护的站点无法通过这种方式登录，alive365 会建议您改用浏览器检查。

#### 4. What to check, and how often: an online shop
对于小型在线商店，设置可能如下：主页：HTTP 检查，每分钟一次。这是了解站点本身是否宕机的最快方法。订单 API：HTTP 检查，每分钟一次。页面可能在加载，但订单处理功能可能已停止。会员页面：带表单登录的 HTTP 检查，每 5 分钟一次，以确认登录后的页面可以打开。登录到购物车：浏览器检查，每 15 分钟一次，以捕获无效按钮或从未加载的步骤。浏览器检查会启动真实的浏览器并逐步完成页面操作，因此每次运行的时间比 HTTP 检查更长，成本也更高。将短间隔留给 HTTP 检查，并使用浏览器检查以稍长的间隔确认整个流程仍然有效。

#### 5. When something breaks: one incident per outage
某物是否宕机由固定的规则决定，而不是由 AI 决定。相同的结果总是导致相同的决定。默认设置：一次失败会开启一个事件。第一次失败将其标记为警告；连续两次失败将其提升为错误并将监控标记为 DOWN。当事件开启时，更多的失败会被添加到该事件中，而不是开启新的事件。一次故障不会变成几十个事件。在连续五次成功后确认恢复，事件随之关闭。这防止了不稳定的站点反复关闭和重新开启事件。事件列在仪表板的“事件”下，每个事件都有失败和恢复时间的记录。以下是每分钟检查一次的主页在宕机 20 分钟时的默认处理方式：故障后的第一次检查失败，事件作为警告开启。下一次检查也失败。事件提升为错误，监控被标记为 DOWN。在剩下的 20 分钟里，每次失败都被添加到同一个事件中。修复后，连续第五次成功确认了恢复，事件关闭。整个故障作为一个单一事件保留。确认恢复所需的时间取决于间隔：一分钟检查一次大约需要 5 分钟，十分钟检查一次大约需要 50 分钟。我们让 AI 远离这个决定，以便原因总是可以用同样的方式解释。“它连续失败了两次”是您可以原样告诉客户或同事的话。AI 的判断可能会给出不同的答案。
