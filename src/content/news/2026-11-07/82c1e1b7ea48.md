I like using AI for software development. It can help with debugging, architecture, refactoring, documentation, and even building entire features. But there was one thing that kept bothering me: Why does using AI for development have to mean subscribing to another platform?

我喜欢在软件开发中使用人工智能。它可以在调试、架构、重构、文档编写甚至构建完整功能方面提供帮助。但有一件事一直困扰着我：为什么使用人工智能进行开发就非得订阅另一个平台呢？

I wanted something different. I wanted to choose the AI model myself. I wanted to use my own API key. I wanted to keep my projects under my control. And I didn't want another mandatory account, token system, or subscription standing between me and my code. So I decided to build it.

我想要一些不同的东西。我想自己选择人工智能模型。我想使用自己的 API 密钥。我想让我的项目保持在自己的掌控之下。我也不希望在我和我的代码之间横亘着另一个强制性的账户、代币系统或订阅。所以我决定自己开发它。

The idea I started building NullCry as an AI development environment focused on developer control. The concept is simple: You bring your own API key. Instead of forcing developers to purchase AI credits from another platform, NullCry can work with the developer's own API access. That means the developer can choose the provider and model that fits their needs. No NullCry tokens. No mandatory NullCry subscription. No requirement to use one specific AI provider.

我开始构建 NullCry，将其作为一个专注于开发者控制的人工智能开发环境。这个概念很简单：你自带 API 密钥。NullCry 不会强迫开发者从其他平台购买人工智能积分，而是可以使用开发者自己的 API 访问权限。这意味着开发者可以选择适合自己需求的提供商和模型。没有 NullCry 代币，没有强制性的 NullCry 订阅，也没有使用特定人工智能提供商的要求。

But the difficult part wasn't the API Connecting an AI model to a web interface is relatively straightforward. The harder problem is building something that can actually work with a real software project. A real project isn't one text prompt. It can contain: Multiple files, Existing code, Dependencies, Previous changes, Bugs, Large files, Different programming languages, Changes that affect other parts of the project.

但困难的部分不在于 API。将人工智能模型连接到 Web 界面相对简单。更难的问题是构建一个能够真正处理实际软件项目的工具。一个真正的项目不仅仅是一个文本提示。它可能包含：多个文件、现有代码、依赖项、之前的更改、错误、大文件、不同的编程语言，以及会影响项目其他部分的更改。

So I focused heavily on context and project continuity. The goal was to make the AI work with the project rather than treating every request as an isolated conversation.

因此，我非常注重上下文和项目的连续性。我的目标是让人工智能与项目协同工作，而不是将每个请求都视为孤立的对话。

What NullCry is trying to solve The philosophy behind NullCry is: «Your AI. Your Projects. Your Freedom.» Developers should be able to choose their AI provider instead of being locked into a single ecosystem. They should also be able to experiment with different models without rebuilding their entire workflow around a subscription. That's the direction I'm trying to take with NullCry.

NullCry 试图解决的问题：NullCry 背后的理念是：“你的人工智能。你的项目。你的自由。”开发者应该能够选择自己的人工智能提供商，而不是被锁定在单一的生态系统中。他们也应该能够在不围绕订阅重建整个工作流程的情况下，尝试不同的模型。这就是我试图通过 NullCry 实现的方向。

I'm not claiming it's perfect This is still a project I'm developing and improving. There are things I want to make better. There are probably things developers will notice that I haven't considered yet. And that's exactly why I'm sharing it with the developer community. I want honest feedback. If you were designing an AI development environment around BYOK, what would you add? Would you prefer this model over a traditional AI coding subscription? Or do subscriptions provide enough convenience to make the trade-off worthwhile? I'd genuinely like to hear how other developers see it.

我并不声称它已经完美。这仍然是一个我正在开发和改进的项目。有些地方我想做得更好。可能还有一些开发者会注意到而我尚未考虑到的问题。这正是我想与开发者社区分享它的原因。我想要诚实的反馈。如果你要围绕“自带密钥”（BYOK）设计一个人工智能开发环境，你会添加什么？你会比传统的 AI 编码订阅更喜欢这种模式吗？还是说订阅提供的便利性足以让这种权衡变得值得？我真心想听听其他开发者对此的看法。
