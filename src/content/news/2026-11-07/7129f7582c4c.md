# The MustCreate Pattern for Go Tests

I recently discovered a handy way to make Go tests more readable and less repetitive. Suppose I have a constructor that can fail: `func NewUsername(raw string) (Username, error) { ... }` And I have another function that takes a Username as an argument: `func (ds Datastore) ReadUser(username Username) (User, error) { ... }` When I write tests for ReadUser, I call NewUsername with a value I know is valid, but I still have to include a lot of verbose error-checking code to convince the compiler that everything is okay:

我最近发现了一种让 Go 测试更具可读性且减少重复代码的便捷方法。假设我有一个可能会失败的构造函数：`func NewUsername(raw string) (Username, error) { ... }`，并且我有另一个以 Username 作为参数的函数：`func (ds Datastore) ReadUser(username Username) (User, error) { ... }`。当我为 ReadUser 编写测试时，我会用一个已知有效的数值来调用 NewUsername，但我仍然必须包含大量冗长的错误检查代码，以向编译器证明一切正常：

```go
username, err := NewUsername("joe123")
// This is silly because *I* know joe123 is a valid username, so this should
// never happen.
if err != nil {
    t.Fatalf("failed to create username: %v", err)
}
// Perform the test assertion I actually care about.
user, err := store.ReadUser(username)
if got, want := user.Name.String(), "joe123"; got != want {
    t.Errorf("username=%v, want=%v", got, want)
}
```

My old solution: one new helper function per type. Until a few months ago, I avoided the verbose error checking by writing a helper function like MustCreateUsername that wraps NewUsername with the expectation that it never returns a non-nil error value:

我之前的解决方案是：为每种类型编写一个新的辅助函数。直到几个月前，我通过编写像 MustCreateUsername 这样的辅助函数来避免冗长的错误检查，它封装了 NewUsername，并预期它永远不会返回非 nil 的错误值：

```go
user, err := store.ReadUser(MustCreateUsername(t, "joe123"))
if got, want := user.Name.String(), "joe123"; got != want {
    t.Errorf("username=%v, want=%v", got, want)
}
```

The implementation of MustCreateUsername looks how you’d expect:

MustCreateUsername 的实现正如你所预期的那样：

```go
func MustCreateUsername(t testing.TB, raw string) Username {
    t.Helper()
    username, err := NewUsername(raw)
    if err != nil {
        t.Fatalf("invalid username: %s", raw)
    }
}
```

The helper function strategy worked fine, but it scales poorly. Eventually, my repos become littered with MustCreateFoo and MustCreateBar for every type in my app.

这种辅助函数策略运行良好，但扩展性较差。最终，我的代码库中充斥着针对应用中每种类型的 MustCreateFoo 和 MustCreateBar。

New solution: A single, generic MustCreate helper. In 2022, Go 1.18 added support for generics. I like the idea of generics, but I rarely encounter problems where generics are the solution. I recently realized that generics are the better way to solve my sprawling MustCreateX problem. Instead of defining a helper MustCreateX for every type, I defined a single, generic MustCreate test helper, so my test becomes:

新解决方案：一个通用的 MustCreate 辅助函数。2022 年，Go 1.18 增加了对泛型的支持。我喜欢泛型的概念，但我很少遇到必须使用泛型才能解决的问题。最近我意识到，泛型是解决我那泛滥的 MustCreateX 问题的更好方法。我不再为每种类型定义一个 MustCreateX 辅助函数，而是定义了一个单一的、通用的 MustCreate 测试辅助函数，因此我的测试变成了：

```go
user, err := store.ReadUser(testutil.MustCreate(t, NewUsername, "joe123"))
if got, want := user.Name.String(), "joe123"; got != want {
    t.Errorf("username=%v, want=%v", got, want)
}
```

The magic is the generic MustCreate function:

其奥妙在于这个通用的 MustCreate 函数：

```go
func MustCreate[RawInput, CreatedValue any](
    t testing.TB,
    create func(RawInput) (CreatedValue, error),
    rawInput RawInput,
) CreatedValue {
    t.Helper()
    createdValue, err := create(rawInput)
    if err != nil {
        t.Fatalf("failed to create test value: %v", err)
    }
    return createdValue
}
```

I have trouble reasoning about generics, so I’ll walk through the function implementation. I invoke MustCreate like this in my tests: `testutil.MustCreate(t, NewUsername, "joe123")`. The above call is equivalent to this more explicit version: `testutil.MustCreate[string, Username](t, NewUsername, "joe123")`. When I call MustCreate here, RawInput is string (the type of the raw username value), and CreatedValue is Username (the return type). It’s equivalent to an implementation that looks like this:

我对泛型的逻辑理解有些困难，所以我将逐步解析该函数的实现。我在测试中这样调用 MustCreate：`testutil.MustCreate(t, NewUsername, "joe123")`。上述调用等同于这个更明确的版本：`testutil.MustCreate[string, Username](t, NewUsername, "joe123")`。当我在此处调用 MustCreate 时，RawInput 是 string（原始用户名值的类型），而 CreatedValue 是 Username（返回类型）。它等同于如下实现：

```go
func MustCreate(
    t testing.TB,
    create func(string) (Username, error),
    rawInput string,
) CreatedValue {
    t.Helper()
    createdValue, err := create(rawInput)
    if err != nil {
        t.Fatalf("failed to create test value: %v", err)
    }
    return createdValue
}
```

Extending to multi-param constructors. What about constructors that have more than one parameter? `func NewRange(start int, end int) (Range, error) { ... }`. In those cases, I write an additional helper called MustCreate2: `range := testutil.MustCreate2(t, models.NewRange, 0, 5)`. The implementation of MustCreate2 looks just like MustCreate but with an additional type for the second parameter:

扩展到多参数构造函数。如果构造函数有多个参数怎么办？`func NewRange(start int, end int) (Range, error) { ... }`。在这种情况下，我编写了一个名为 MustCreate2 的额外辅助函数：`range := testutil.MustCreate2(t, models.NewRange, 0, 5)`。MustCreate2 的实现看起来与 MustCreate 相同，只是为第二个参数增加了一个类型：

```go
func MustCreate2[RawInput1, RawInput2, CreatedValue any](
    t testing.TB,
    create func(RawInput1, RawInput2) (CreatedValue, error),
    rawInput1 RawInput1,
    rawInput2 RawInput2,
) CreatedValue {
    t.Helper()
    createdValue, err := create(rawInput1, rawInput2)
    if err != nil {
        t.Fatalf("failed to create test value: %v", err)
    }
    return createdValue
}
```

Conclusion. The MustCreate pattern is nothing revolutionary, but it’s a technique that improved my Go tests and reduced some mindless toil from my dev work.

结论。MustCreate 模式并非什么革命性的东西，但它确实改进了我的 Go 测试，并减少了我开发工作中一些机械性的苦差事。
