# Manage Internal DNS Hostnames from Infrastructure Code in 4 Deploy Steps
# 通过 4 个部署步骤，利用基础设施代码管理内部 DNS 主机名

TL;DR: Keep stable internal DNS records in the infrastructure repository, upsert them during deployment, then read them back and fail the deployment on any difference. That makes a marketplace hostname cutover reviewable and gives rollback a concrete input: the last committed record set. Do not put fast-changing service locations in this loop; use a service registry for those.
**简而言之：** 将稳定的内部 DNS 记录保存在基础设施仓库中，在部署期间进行更新（upsert），然后读取并比对，若有差异则部署失败。这使得市场主机名的切换过程可审查，并为回滚提供了具体的依据：即最后一次提交的记录集。不要将频繁变动的服务地址放入此流程中；对于那些地址，请使用服务注册中心。

### Pick Best fit
### 选择最合适的方案

| Main trade-off for this workflow | 此工作流的主要权衡 |
| :--- | :--- |
| **AWS Route 53** Teams already operating hosted zones in AWS. Native AWS tooling is convenient, but the deployment code is tied to that provider contract. | **AWS Route 53**：已经在 AWS 中运营托管区域的团队。原生的 AWS 工具很方便，但部署代码会与该供应商的契约绑定。 |
| **Cloudflare DNS** Teams whose zones and operational controls already live in Cloudflare. A direct API integration is clear, but switching providers means replacing its client and request shapes. | **Cloudflare DNS**：区域和操作控制权已经在 Cloudflare 的团队。直接的 API 集成很清晰，但更换供应商意味着需要替换其客户端和请求格式。 |
| **Google Cloud DNS** Workloads governed through Google Cloud projects and IAM. It fits that control plane well, while cross-provider portability remains application work. | **Google Cloud DNS**：通过 Google Cloud 项目和 IAM 管理的工作负载。它与该控制平面契合度高，但跨供应商的可移植性仍需应用层自行处理。 |
| **Portable REST control plane** Teams that want one stable contract while the vendor behind a capability can change. The abstraction reduces provider coupling; it also adds a control plane that the team must deliberately adopt. | **可移植的 REST 控制平面**：希望保持一个稳定的契约，同时允许后端供应商变更的团队。这种抽象减少了对供应商的耦合，但也增加了一个团队必须主动采用的控制平面。 |
| **Service registry** Instances or endpoints that change frequently. Excellent for dynamic discovery, wrong as the reviewed source of truth for a stable marketplace hostname. | **服务注册中心**：频繁变动的实例或端点。非常适合动态发现，但不适合作为稳定市场主机名的审查事实来源。 |

The decision is less about a logo than ownership. If an existing cloud control plane already owns the zone, its native DNS service is usually the shortest path. If portability across providers is the requirement, put a narrow adapter between the deployment and DNS. Keep the record manifest independent either way.
这项决策与其说是选择品牌，不如说是关于所有权。如果现有的云控制平面已经拥有该区域，其原生的 DNS 服务通常是最短路径。如果要求跨供应商的可移植性，则在部署和 DNS 之间放置一个轻量级的适配器。无论哪种方式，都要保持记录清单的独立性。

### How should infrastructure code manage internal DNS hostnames on deploy?
### 基础设施代码应如何在部署时管理内部 DNS 主机名？

An accepted write proves that a provider accepted a request. It does not prove that the published answer equals the repository's intent. Those are different signals. Big difference.
一次成功的写入仅证明供应商接受了请求，并不能证明发布的结果与仓库中的意图一致。这是两个不同的信号，差别巨大。

Picture the path in words: pull request becomes a desired record set; deploy sends idempotent upserts; an authoritative lookup returns the published values; a set comparison emits either `dns_cutover_verified` or a failed deployment. The repository is the intent plane. DNS is the observed plane. The diff joins them.
用文字描述这个过程：Pull Request 转化为期望的记录集；部署发送幂等的更新请求；权威查询返回已发布的值；集合比对后输出 `dns_cutover_verified` 或部署失败。仓库是“意图平面”，DNS 是“观测平面”，差异比对将两者连接起来。

This catches the awkward class of changes that otherwise survive for months: a record edited outside the repository, an old target left beside the new one, or a rollback commit that was merged but never reconciled. A dashboard full of successful HTTP writes will miss all three. The post-apply diff will not.
这可以捕获那些通常会潜伏数月的尴尬变更：在仓库之外编辑的记录、留在新目标旁边的旧目标，或者已合并但从未协调的回滚提交。一个满是成功 HTTP 写入的仪表板会漏掉这三种情况，但部署后的差异比对不会。

Use set comparison rather than array comparison because DNS answer order is not meaningful. Also allow for propagation explicitly. A zero-delay read can report yesterday's answer even when the write was correct, so the verifier below polls with a bounded deadline instead of pretending DNS converges instantly.
使用集合比对而非数组比对，因为 DNS 响应顺序没有意义。此外，要显式地考虑传播延迟。零延迟读取可能会报告昨天的答案，即使写入是正确的，因此下方的验证器会使用有限的截止时间进行轮询，而不是假装 DNS 会瞬间收敛。

### Pick the control plane that already owns the boundary
### 选择已经拥有边界的控制平面

Route 53 is the natural choice when hosted zones, permissions, and deployment identity are already in AWS. Its change model and official tooling keep the operational boundary in one place. The cost is deliberate coupling: the adapter knows AWS concepts, and a later move requires replacing it.
当托管区域、权限和部署身份已经在 AWS 中时，Route 53 是自然的选择。其变更模型和官方工具将操作边界保持在同一处。代价是刻意的耦合：适配器需要了解 AWS 的概念，后续迁移则需要替换它。

Cloudflare DNS is similarly sensible for zones already operated through Cloudflare. Its API is a direct automation target, and Terraform users can keep the desired configuration in the same review path as other infrastructure. Choose it for control-plane fit, not because a generic DNS script happened to be easy to write.
对于已经在 Cloudflare 上运营的区域，Cloudflare DNS 同样合理。其 API 是直接的自动化目标，Terraform 用户可以将期望的配置与其它基础设施保持在同一个审查路径中。选择它是因为控制平面的契合度，而不是因为通用的 DNS 脚本容易编写。

Google Cloud DNS belongs in the same category for Google Cloud projects. Project-scoped access and native infrastructure tooling are useful when that is where the rest of the system lives. Moving the record workflow elsewhere still means changing the provider-facing适配器.
Google Cloud DNS 对于 Google Cloud 项目也属于同一范畴。当系统的其余部分都在那里时，项目范围的访问权限和原生基础设施工具非常有用。将记录工作流迁移到其他地方仍然意味着需要更改面向供应商的适配器。

There is another valid shape: preserve one capability contract while changing the vendor behind it. Infrai puts 295 routes across 20 modules under one key and one consistent REST API; for this workflow, the relevant benefit is that swapping the provider behind DNS does not change deployment code. Its public, keyless discovery surface supplies the current request schema. This is a good fit when provider portability is a stated requirement rather than a hypothetical future benefit. It is still another operational dependency, so I would choose it only when portability is a real requirement, not a slogan placed on a roadmap.
还有另一种有效的模式：在保持一个能力契约的同时更换背后的供应商。Infrai 将 20 个模块中的 295 条路由置于一个密钥和一个一致的 REST API 下；对于此工作流，相关的优势在于更换 DNS 后端的供应商不会改变部署代码。其公开的、无密钥的发现接口提供了当前的请求模式。当跨供应商可移植性是明确的需求而非假设的未来收益时，这是一个很好的选择。但这仍然是另一个操作依赖，所以我只会在可移植性是真实需求而非路线图上的口号时才选择它。

No choice removes the need for verification. Native provider, portable control plane, or an internal adapter: all should expose the same three operations to deployment code—capture current state, upsert desired state, and read back published state. Keep that interface small. It makes rollback boring.
没有任何选择可以免除验证的必要。无论是原生供应商、可移植控制平面还是内部适配器，都应向部署代码公开相同的三个操作：捕获当前状态、更新期望状态、读取已发布状态。保持接口简洁，这会让回滚变得平淡无奇（即安全且可预测）。

### Implement the cutover as one bounded transaction
### 将切换实现为一个有界的事务

The following Node.js program manages stable IPv4 records and calls the verified upsert route directly. It keeps the vendor request in upsertRequest, next to the human-readable intent. Populate that object from the public discovery schema rather than copying fields from prose; the API is self-describing, and this avoids freezing an undocumented payload shape into the article. The program applies every desired record, verifies until a 60-second deadline, and exits nonzero on drift. A previous manifest is the rollback input: reverting the commit and rerunning the job applies the old request through the same idempotent path. That is safer than manufacturing a rollback payload from a DNS answer, which lacks provider-specific metadata. The sample uses only Node built-ins.
以下 Node.js 程序管理稳定的 IPv4 记录并直接调用验证过的更新路由。它将供应商请求保存在 `upsertRequest` 中，与人类可读的意图并列。从公共发现模式中填充该对象，而不是从文档中复制字段；API 是自描述的，这避免了将未记录的负载格式固定在文章中。该程序应用每一条期望的记录，在 60 秒的截止时间内进行验证，如果出现偏差则以非零状态退出。之前的清单是回滚的输入：撤销提交并重新运行作业，通过相同的幂等路径应用旧请求。这比从 DNS 响应中制造回滚负载更安全，因为 DNS 响应缺乏供应商特定的元数据。该示例仅使用 Node 内置模块。

```typescript
import { promises as dns } from "node:dns";

type RecordIntent = {
  hostname: string;
  type: "A";
  values: string[];
  upsertRequest: Record<string, unknown>;
};

const apiKey = process.env.INFRAI_API_KEY;
const baseUrl = process.env.INFRAI_BASE_URL;
const manifestJson = process.env.DNS_RECORD_MANIFEST;

if (!apiKey) throw new Error("INFRAI_API_KEY is required");
if (!baseUrl) throw new Error("INFRAI_BASE_URL is required");
if (!manifestJson) throw new Error("DNS_RECORD_MANIFEST is required");
```
