What is the difference between how cold and warm sessions receive data? Resident management is handled by `runtime/resident.rs`. It keeps one ACP process alive for each (channel, binding) key, with a maximum of 4 concurrent processes, and kills them after 30 minutes of inactivity. A lease is borrowed for each turn, and what to send is determined solely by `Lease::cold`. If we reduce the branching in `providers/agent_cli.rs`, it looks like this:

冷会话和温会话接收的内容有何不同？驻留管理由 `runtime/resident.rs` 处理。它为每个（频道，绑定）键保留一个 ACP 进程，同时最多存活 4 个，闲置 30 分钟后销毁。每回合都会借用一个租约（Lease），发送什么内容仅由 `Lease::cold` 决定。如果简化 `providers/agent_cli.rs` 中的分支，代码如下：

```rust
let full = if restored && !prompt_warm.trim().is_empty() {
    format!("{system}\n\n{prompt_warm}") // reloaded saved session: framing + new turn
} else if cold || prompt_warm.trim().is_empty() {
    format!("{system}\n\n{prompt}") // new process: framing + full replay
} else {
    prompt_warm.to_string() // warm: the newest user turn, nothing else
};
```

`prompt` 是 `build_prompt` 将整个对话展开为 User:/Assistant: 行的结果。`prompt_warm` 是 `latest_user_turn`，即除了 assistant、system 或 tool 之外的最后一条消息。`resident.rs` 的注释明确规定不要为了优化而改动这个顺序。如果向温进程推送重放，代理会在每回合都收到自己之前的回答作为新的用户输入，导致输入呈指数级增长。从提示词缓存的角度来看，这就是固定前缀原则。系统侧的框架（framing）只在最前面出现一次，之后不再改变。每回合变化的内容全部作为末尾的新用户回合进入。

So where does the channel context go? It is appended after the brief of the latest user turn. `mention_context` fetches the last 30 rows (`channel_rows(..., 30)`) and passes them to `channel_delivery::render` with an upper limit of 12. The processing order is as follows: the mentioned message itself is removed because it is already in the payload. If shown twice, the agent might claim to have answered the echo of the question sent to it. If the session has memory, it removes rows where the watermark ID exists and `created_at` is less than or equal to `last_at`. Among the remaining, it keeps the latest 12 in chronological order. The body is truncated at 600 characters, appending `… [N more characters; channel_history has the full message]`. If it is the first contact, the header is "Recent messages in this channel …"; if there is a watermark, it is "New messages in this channel since you last heard from it …". If there are no new messages, the block is not sent at all.

那么频道上下文放在哪里呢？它被附加在最新用户回合的简报之后。`mention_context` 获取最近 30 行（`channel_rows(..., 30)`），并以 12 为上限传递给 `channel_delivery::render`。处理顺序如下：首先剔除被提及的消息本身，因为它已经在负载中了。如果展示两次，代理可能会说它回答过发给自己的问题回声。如果会话有记忆，则剔除水印 ID 中存在的行，以及 `created_at` 小于等于 `last_at` 的行。在剩余内容中，保留最新的 12 条（按时间顺序）。正文在 600 字符处截断，并附加 `… [N more characters; channel_history has the full message]`。如果是首次接触，标题为 "Recent messages in this channel …"；如果有水印，则为 "New messages in this channel since you last heard from it …"。如果没有新消息，则根本不发送该块。

When does the watermark advance? Only when a run succeeds. When `render` returns the rows shown, `stage()` temporarily hangs them on the run channel, and the run termination path calls `commit()` on success or `discard()` on failure. The comment explains why: a failed run might not have actually shown anything. If you move the watermark ahead of what was seen, that message will never be sent again. The watermark is tied to a single native session. The storage format is `{native, last_at, ids}`. The key is session key/channel/thread, and IDs are stored in `channel-watermarks.json` up to 200 entries. `watermark_for` only returns a value when the native ID matches the process ID currently responding. After recovery, crashes, or "Start fresh," the new process ID differs, so it restarts from a 12-item snapshot instead of a hole. Watermarks are only held by bindings that maintain a session—those that are both `supervised` and `resident`, or cases where a saved session is attached directly. Bindings that start fresh every time receive a snapshot every time. For a process without memory, that is the only correct way.

水印何时推进？仅在运行（run）成功时。当 `render` 返回展示的行时，`stage()` 会将其暂时挂在运行频道上，运行结束路径在成功时调用 `commit()`，失败时调用 `discard()`。注释中说明了原因：失败的运行可能实际上什么都没展示。如果将水印移到已看到的内容之前，该消息将永远不会再发送。水印绑定到一个原生的会话上。存储格式为 `{native, last_at, ids}`。键是会话键/频道/线程，ID 最多存储 200 个，保存在 `channel-watermarks.json` 中。`watermark_for` 仅在 native 与当前响应的进程 ID 相同时才返回值。在恢复、崩溃或“Start fresh”之后，新进程 ID 不同，因此它会从 12 条的快照重新开始，而不是留下空洞。水印仅由维持会话的绑定持有——即那些既是 `supervised` 又是 `resident` 的绑定，或者直接附加已保存会话的情况。每次都重新开始的绑定每次都会收到快照。对于没有记忆的进程，这是唯一正确的方式。

Apple M1에서 전체 실행은 벽시계 1.23초였고, 대부분 토크나이즈 시간이다. 숫자가 말하는 것: 워터마크는 캐시 비율을 안 바꾼다. window도 watermark도 0.94다. 중복된 채널 행은 턴별 서픽스에 있고, 서픽스는 원래 캐시 대상이 아니다. 중복의 비용은 다른 데서 나온다. 웜 턴마다 새 토큰이 766이 아니라 943개로 23% 많다. 게다가 그 중복은 세션 히스토리에 계속 남아서 CLI가 들고 다니는 대화가 빨리 불어난다. 30회 동안 window는 프로바이더에 516k 토큰을 흘렸고 watermark는 417k였다. 뒤의 요청이 매번 그 중복을 캐시에서 다시 읽으니까 차이는 턴마다 벌어지고, 컴팩션도 빨리 온다.

在 Apple M1 上，整个执行过程的挂钟时间为 1.23 秒，大部分是分词时间。数据说明了什么：水印不会改变缓存比例。window 和 watermark 都是 0.94。重复的频道行位于每回合的后缀中，而后缀本身并非缓存目标。重复的成本来自其他方面。每个温回合的新 token 不是 766 个，而是 943 个，多了 23%。此外，这些重复内容会一直留在会话历史中，导致 CLI 携带的对话迅速膨胀。在 30 次提及中，window 向提供者输送了 516k token，而 watermark 为 417k。由于后续请求每次都会从缓存中重新读取这些重复内容，差距会随回合数拉大，压缩（compaction）也会更快到来。

캐시를 결정하는 건 프리픽스다. 매 턴 바뀌는 28토큰짜리 상태 줄 하나를 시스템 프롬프트 앞에 붙였더니 캐시 가능 비율이 0.94에서 0.00이 됐다. 웜 턴 하나가 766이 아니라 14k 넘는 비캐시 토큰이 된다. osFoundry가 로스터·상태·채널 메시지를 프레이밍에 안 넣는 이유가 이거다. 로스터와 프로젝트 활동은 툴(channel_roster, project_activity)로 꺼내게 하고, 채널 메시지는 유저 턴에 둔다. 턴 단위로 보면, 두 번째 멘션부터 window는 매번 약 460토큰의 채널 텍스트를 보내고 그중 420~440은 이미 본 것이다. watermark는 21~44토큰만 보낸다.

决定缓存的是前缀。仅仅在系统提示词前加上一行每回合都会变化的 28 token 的状态行，缓存比例就从 0.94 变成了 0.00。一个温回合不再是 766 个非缓存 token，而是超过 14k 个。这就是 osFoundry 不把花名册（roster）、状态和频道消息放入框架的原因。它让花名册和项目活动通过工具（`channel_roster`, `project_activity`）获取，并将频道消息放在用户回合中。从回合维度看，从第二次提及开始，window 每次发送约 460 token 的频道文本，其中 420~440 个是已经看过的。而 watermark 仅发送 21~44 个 token。

두 가지 더 봤다. 15번째 멘션에서 프로세스가 회수된 경우: 콜드 턴은 처음부터 다시 짠다. 새 프로세스라 캐시가 없고, 네이티브 id가 바뀌어서 스냅샷이 간다. 히스토리가 리셋되니 합계는 watermark 245k, window 290k로 내려간다. watermark 쪽은 옛 프로세스가 봤던 행이 23토큰만큼 다시 간다. 새 프로세스는 그걸 본 적이 없으니 맞는 동작이다. 12개 상한으로 놓치는 것: 두 전략 모두 25개 메시지가 한 번도 안 보였다. 전부 멘션 사이에 12개 넘게 쌓인 구간이다. watermark는 새 것 중 최신 12개를 고르니 이걸 더 나쁘게 만들지 않는다. 헤더가 channel_history를 알려 주고, 이 툴은 before와 thread_root_id로 거슬러 올라가며 기본 30개, 최대 100개까지 읽는다.

我还观察到了两点。第一，在第 15 次提及中进程被回收的情况：冷回合从头开始重构。因为是新进程，没有缓存，且原生 ID 改变，所以发送了快照。由于历史记录重置，总计下降到 watermark 245k，window 290k。在 watermark 侧，旧进程看过的行有 23 token 被再次发送。因为新进程没看过，这是正确的行为。第二，12 个上限导致的遗漏：两种策略都有 25 条消息从未被展示。这些都是提及之间积累超过 12 条消息的区间。watermark 从新消息中挑选最新的 12 条，因此并没有让情况变糟。标题会告知 `channel_history`，该工具通过 `before` 和 `thread_root_id` 向上回溯，默认读取 30 条，最多 100 条。

직접 붙인다면 콜드/웜 판단은 한 곳에서만 하고, 프레이밍과 리플레이는 콜드일 때만 보낸다. 상주 프로세스에 자기 트랜스크립트를 다시 주지 않는다. 로스터, 상태, 브랜치, 채널 메시지처럼 턴마다 바뀌는 건 시스템 프롬프트에 넣지 않는다. 최신 유저 턴이나 툴 뒤에 둔다. 앞에 바뀌는 줄 하나만 있어도 캐시가 통째로 날아간다. 워터마크는 에이전트 핸들이 아니라 프로바이더의 네이티브 세션 id에 묶는다. 프로세스가 바뀌면 구멍 대신 스냅샷이 간다. 워터마크는 run 성공 후에만 옮긴다.

如果自行实现，冷/温判断应仅在一处进行，框架和重放仅在冷启动时发送。不要给驻留进程再次提供它自己的转录内容。像花名册、状态、分支、频道消息这种每回合都会变的内容，不要放入系统提示词中。将它们放在最新用户回合或工具之后。只要前面有一行变化，缓存就会全部失效。水印应绑定到提供者的原生会话 ID，而不是代理句柄。如果进程改变，则发送快照而非空洞。水印仅在运行成功后推进。
