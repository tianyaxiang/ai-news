**Typing Indicators for Marketplace Devices: Is Channel Chatter Worth Keeping?**

**市场设备输入指示器：频道闲聊值得保留吗？**

Use typing indicators only when they change an operator's next action, and keep them outside the delivery path for device status. For a marketplace operations dashboard, online, offline, degraded, and maintenance transitions deserve replay and deduplication. A hint that another operator is composing a note does not. If both compete in one ordered channel, optional chatter can delay the state the dashboard exists to show.

仅在输入指示器会改变操作员的后续行动时才使用它们，并将其保持在设备状态的传输路径之外。对于市场运营仪表板，在线、离线、降级和维护状态的转换值得重放和去重。而“另一位操作员正在撰写备注”的提示则不值得。如果两者在同一个有序频道中竞争，可选的闲聊可能会延迟仪表板本应展示的状态。

TL;DR: give status events durable identity and resumable delivery; give typing activity a short lease, aggressive coalescing, and permission to disappear. Under congestion, reconnect, or rollout trouble, disable the hint first. Silence is an acceptable result for typing activity. A stale device state is not.

简而言之：为状态事件提供持久标识和可恢复的交付；为输入活动提供短期租约、激进的合并策略以及消失的许可。在拥塞、重连或发布故障时，应优先禁用提示。对于输入活动，静默是可以接受的结果，但过时的设备状态则不可接受。

Should typing indicators share a channel, or should we skip them? The failure starts when a team treats every real-time message as equivalent. Imagine a marketplace with sellers' payment terminals, label printers, and pickup scanners on one live operations screen. A terminal changes from online to degraded while three operators are typing into the shared incident note. If the transport, broker subscription, or client queue preserves one global order, a burst of replaceable activity can sit ahead of the status transition.

输入指示器应该共享一个频道，还是我们应该跳过它们？当团队将每一条实时消息视为等同对待时，失败就开始了。想象一个市场，其卖家的支付终端、标签打印机和取货扫描仪都在同一个实时操作屏幕上。当三个操作员正在共享的事件备注中输入内容时，一个终端从在线变为降级。如果传输、代理订阅或客户端队列保持全局顺序，那么一连串可替换的活动可能会排在状态转换之前。

The hint is transient by definition. A late typing=true event may arrive after the author stopped; a replayed one is worse than no hint because it presents expired intent as current activity. Status has the opposite shape. Operators need the newest known state, but reconnecting clients also need a defensible way to detect what they missed. Skipping them entirely is worth considering when the dashboard has no shared editing workflow. There is no operational benefit to broadcasting intent that cannot prevent a collision or change an operator's choice.

提示按定义就是短暂的。一条延迟的“typing=true”事件可能在作者停止输入后才到达；重放的事件比没有提示更糟糕，因为它将过期的意图呈现为当前活动。状态则完全相反。操作员需要最新的已知状态，但重连的客户端也需要一种可靠的方法来检测它们错过了什么。当仪表板没有共享编辑工作流时，完全跳过它们是值得考虑的。广播那些无法防止冲突或改变操作员选择的意图，在运营上没有任何好处。

This is the delivery-guarantee split: Signal Identity Reconnect behavior Congestion policy Device status Stable event ID plus per-device version Resume or fetch a snapshot, then apply newer events Preserve; shed optional work first Typing activity Actor and room, with an expiry Do not replay expired activity Coalesce or drop Do not promise exactly-once display.

这就是交付保证的拆分：信号标识、重连行为、拥塞策略。设备状态：稳定的事件 ID 加每个设备的版本；恢复或获取快照，然后应用更新的事件；保留，优先丢弃可选工作。输入活动：参与者和房间，带有过期时间；不重放过期活动；合并或丢弃；不承诺精确一次显示。

Networks retry, processes restart, and clients reconnect. The practical contract is at-least-once delivery for status combined with idempotent application, while activity is best effort. That contract can be tested. Separate correctness from presence chatter. Use two logical streams even if one physical connection carries both. The status stream owns a cursor or snapshot boundary. The activity stream owns no durable backlog. Separate queue limits and scheduling weights matter more than separate socket URLs: independent URLs still fail together if they feed the same unbounded outbound queue.

网络会重试，进程会重启，客户端会重连。实际的契约是状态的“至少一次”交付结合幂等应用，而活动则是“尽力而为”。该契约是可以测试的。将正确性与存在性闲聊分开。即使一个物理连接承载两者，也要使用两个逻辑流。状态流拥有游标或快照边界。活动流不拥有持久的积压。独立的队列限制和调度权重比独立的 Socket URL 更重要：如果它们馈送到同一个无界的出站队列，独立的 URL 依然会同时失败。

A status event needs enough information for a client to reject duplicates and old writes. A monotonically increasing version scoped to one device is easier to reason about than arrival time; wall clocks can disagree, and arrival order changes across reconnects. The consumer applies version 43 once, ignores another 43, and refuses version 42. On a detected gap, it requests a fresh snapshot rather than guessing intermediate state.

状态事件需要足够的信息供客户端拒绝重复和旧的写入。相对于到达时间，针对单个设备范围的单调递增版本更容易推理；挂钟时间可能不一致，且到达顺序在重连后会改变。消费者应用 43 版本一次，忽略另一个 43，并拒绝 42 版本。在检测到间隙时，它会请求新的快照，而不是猜测中间状态。

Typing activity should act like a lease. active=true sets a local expiry, and another event renews it. The UI clears the indicator when the lease expires, so a missing stop event cannot leave a permanent label. The server should coalesce repeated renewals for the same room and actor. This is a deliberate loss of detail, not a reliability defect.

输入活动应该像租约一样运作。“active=true”设置一个本地过期时间，另一个事件则更新它。当租约过期时，UI 会清除指示器，因此丢失的停止事件不会留下永久的标签。服务器应该为同一个房间和参与者合并重复的更新。这是故意的细节丢失，而不是可靠性缺陷。

Keep persistence outside Accept: acknowledge a durable status only after the new version is stored or otherwise made recoverable. For activity, avoid an acknowledgment loop. Acknowledging every keystroke-shaped renewal turns a disposable UX hint into extra bidirectional load and retry state. One physical transport can still express the split. WebRTC data channels, for example, expose ordered delivery and limited-retransmission choices in the standard. That makes a reliable ordered channel and a separate unordered, no-retry activity channel possible. It does not remove the need for application-level versions, expiry, queue bounds, or reconnect recovery. Those are properties of the message contract.

将持久化保持在 Accept 之外：仅在版本被存储或以其他方式变得可恢复后，才确认持久状态。对于活动，避免确认循环。确认每一次按键式的更新会将一次性的 UX 提示变成额外的双向负载和重试状态。一个物理传输仍然可以表达这种拆分。例如，WebRTC 数据通道在标准中提供了有序交付和有限重传的选择。这使得建立一个可靠的有序频道和一个独立的无序、无重传的活动频道成为可能。但这并不能消除对应用层版本、过期时间、队列边界或重连恢复的需求。这些是消息契约的属性。

Put overload behavior in the runbook. The first alert should not be raw message count. Watch the age of the oldest unsent status event, status queue depth, reconnect recovery time, version-gap rate, and dropped activity renewals. A high activity-drop count can be normal during a busy incident; rising status age is the page. Set explicit bounds. For example, allow at most one pending typing state per actor and room, replacing it when a renewal arrives. Give each client a bounded activity queue. When that queue fills, discard activity entries rather than borrowing capacity reserved for status. If the status queue reaches its own bound, stop pretending the client is healthy: disconnect it with a resumable cursor or force a snapshot refresh, according to the protocol contract. Be careful with one tempting shortcut: prioritizing status inside a single FIFO after enqueue does nothing if activity has already consumed all queue memory.

将过载行为放入运行手册中。第一个警报不应该是原始消息计数。监控最旧未发送状态事件的年龄、状态队列深度、重连恢复时间、版本间隙率以及丢弃的活动更新。在高负载事件期间，较高的活动丢弃计数可能是正常的；状态年龄上升才是触发寻呼的原因。设置明确的边界。例如，每个参与者和房间最多允许一个待处理的输入状态，并在更新到达时替换它。为每个客户端提供一个有界的活动队列。当队列填满时，丢弃活动条目，而不是借用为状态保留的容量。如果状态队列达到其自身边界，停止假装客户端健康：根据协议契约，使用可恢复的游标断开连接或强制刷新快照。小心一个诱人的捷径：如果活动已经消耗了所有队列内存，那么在入队后在单个 FIFO 中优先处理状态是无济于事的。
