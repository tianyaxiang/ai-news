I'm going to be honest with you: the graveyard of AI side projects is vast and well-populated. It's filled with half-finished chatbots, abandoned RAG pipelines, and "revolutionary" apps that never made it past a localhost URL. I know because I've contributed several tombstones myself. But then something clicked. In the last two months, I shipped three AI side projects — not just prototypes, but actual deployed apps with real users. Not thousands, mind you. But real. Strangers were typing into my apps. That's the line between a toy and a product. Here's how I did it, what I learned the hard way, and why I'm probably never going to hand-roll a model deployment again.

老实说：AI 副业项目的坟场既广阔又拥挤。这里堆满了半途而废的聊天机器人、被遗弃的 RAG 流水线，以及那些从未走出本地主机 URL 的“革命性”应用。我之所以知道，是因为我自己也贡献了好几块墓碑。但后来我开窍了。在过去两个月里，我发布了三个 AI 副业项目——它们不仅仅是原型，而是拥有真实用户的已部署应用。虽然没有成千上万，但它们是真实的。陌生人在使用我的应用。这就是玩具与产品之间的界限。以下是我如何做到这一点、我从惨痛教训中学到了什么，以及为什么我可能再也不会手动部署模型了。

The Trap I Kept Falling Into Every AI side project I started before this period followed the same death spiral: Get a brilliant idea at 11 PM. Spend 3 days researching model architectures. Spend 2 weeks building a custom fine-tuning pipeline. Realize I haven't written any actual product code. Get bored, abandon project, repeat. The problem was never the idea. It was that I was treating the AI infrastructure as the project, instead of what the AI does for users. My breakthrough came when I forced myself to adopt a brutal constraint: the model is a commodity, not a differentiator.

我不断陷入的陷阱：在此之前，我启动的每一个 AI 副业项目都遵循同样的死亡螺旋：晚上 11 点冒出一个绝妙想法；花 3 天研究模型架构；花 2 周构建自定义微调流水线；意识到自己还没写任何实际的产品代码；感到厌倦，放弃项目，循环往复。问题从来不在于想法，而在于我把 AI 基础设施当成了项目本身，而不是关注 AI 能为用户做什么。当我也强迫自己接受一个残酷的约束时，我取得了突破：模型是商品，而不是差异化优势。

Project One: The Image Captioning Bot That Actually Got Used. My first successful MVP started with a really annoying problem. My wife and I have thousands of unsorted photos across Google Drive, and we needed to find specific ones. You know, "that picture from the beach trip in 2019" or "the one where the dog is wearing a hat." Building a custom CLIP-based search system sounded fun. I spent a weekend sketching out vector embeddings, thinking about FAISS indexes, and planning a fine-tuning strategy. Then I stopped myself. I realized I could build something good enough with three existing tools: A vision-language model for generating captions, a basic text search, and a folder structure that's already there.

项目一：真正被用起来的图像标注机器人。我的第一个成功 MVP 源于一个非常烦人的问题。我和妻子在 Google Drive 上有数千张未整理的照片，我们需要找到特定的照片。你知道的，比如“2019 年海滩旅行的那张照片”或者“那张狗戴着帽子的照片”。构建一个基于 CLIP 的自定义搜索系统听起来很有趣。我花了一个周末勾勒向量嵌入，思考 FAISS 索引，并规划微调策略。然后我停了下来。我意识到我可以用三个现有的工具构建一个足够好的东西：一个用于生成标注的视觉语言模型、一个基础的文本搜索，以及现有的文件夹结构。

Here's how the core function looks in Python:
```python
from transformers import pipeline
from pathlib import Path
import json

caption_pipeline = pipeline("image-to-text", model="Salesforce/blip-image-captioning-large")

def caption_and_save(image_path, output_file):
    result = caption_pipeline(image_path)
    caption = result[0]["generated_text"]
    with open(output_file, "a") as f:
        f.write(json.dumps({
            "image": str(image_path),
            "caption": caption,
            "folder": str(image_path.parent)
        }) + "\n")
    return caption
```
That's it. That's the core. I ran this over my photo library overnight (took about 4 hours for 2,000 photos on a single GPU — not terrible), and then used a simple grep-style search for captions. My wife actually uses this. She types "dog hat beach" into a simple web UI, and gets results in under a second. It's not fancy. But it works. Lesson one: Ship the boring version first. The version that uses an existing model and does one thing well. You can always add vector search later, but you can't add users later if you never launch.

Project Two: The Email Summarizer Nobody Asked For, But Everyone Uses. With the first project shipping, I got greedy. I had this new idea during a particularly bad week of email overload. I was a dev who got 80+ emails a day — newsletters I never subscribed to, automated GitHub notifications, LinkedIn "connection request accepted" spam. The obvious MVP: an email digest that uses AI to summarize the day's inbox into a morning briefing. My first instinct was to build a full email client integration. OAuth flows, IMAP connections, subscription management. I spent two evenings on that hot mess before I killed it.

项目二：没人要求但每个人都在用的邮件摘要器。随着第一个项目的发布，我变得贪心了。在一周特别糟糕的邮件过载期间，我有了这个新想法。我是一名每天收到 80 多封邮件的开发者——我从未订阅的时事通讯、自动化的 GitHub 通知、LinkedIn“连接请求已接受”的垃圾邮件。显而易见的 MVP 是：一个使用 AI 将当天的收件箱总结为早间简报的邮件摘要工具。我的第一直觉是构建一个完整的电子邮件客户端集成。OAuth 流程、IMAP 连接、订阅管理。我在那个烂摊子上花了两个晚上，然后放弃了。

Lesson two: The second version — the one that actually shipped — was a simple "forward your emails here" system. I set up a special email address that users forward important emails to. A tiny Python script polls it, strips the HTML, and feeds the text to an LLM for summarization.
```javascript
// The simplest "email summarizer" MVP possible
const mailParser = require('mailparser');
const axios = require('axios');

async function handleForwardedEmail(rawEmail) {
  const parsed = await mailParser.simpleParser(rawEmail);
  const summary = await axios.post(process.env.LLM_API_ENDPOINT, {
    messages: [
      { role: "user", content: `Summarize this email in 50 words: ${parsed.text?.slice(0, 5000)}` }
    ]
  });
  // Send summary back to the user
  await sendSummaryBack(parsed.from.value[0].address, summary.data.reply);
}
// Then: poll inbox every 5 minutes, feed emails to handleForwardedEmail()
```
The beauty of this approach? I didn't need to handle OAuth for Gmail. I didn't need a database of users. Users simply create a forward rule. It took me 30 minutes to wire up. In three weeks, 47 people were using it. Not viral, but solid. And the feedback taught me exactly what to improve — which brings me to my third lesson. Lesson three: The product that's easy to abandon is the product users tell you about. When they don't have to install or configure anything, they're more willing to actually try it — and complain about it.

Project Three: The GitHub PR Reviewer That Doesn't Suck. This one was the most technically complex, but also the one that taught me the most about real-world AI constraints. The idea: an automated PR reviewer that catches common issues without being annoying (looking at you, every bot that flags style violations as critical bugs). The key constraint: it needed to work well enough that humans would actually read its comments. If every PR got 15 nitpick comments, nobody would engage. I aimed for one comment per PR at most. I built this using a fairly straightforward chain: Extracted the diff. Stuffed it into a prompt with rules (don't nitpick style, only flag logic errors or security issues). Made the LLM output structured JSON with severity levels. The hardest part wasn't the AI part. It was dealing with API rate limits. This was the project that taught me why infrastructure choices matter more than model choice. The Infrastructure Wake-Up Call. Here's where I'll be straight with you.

项目三：不那么糟糕的 GitHub PR 审查器。这是技术上最复杂的一个，但也让我学到了最多关于现实世界 AI 约束的知识。想法是：一个自动化的 PR 审查器，它能捕捉常见问题而不会让人感到烦恼（说的就是你们，那些把风格违规标记为严重错误的机器人）。关键约束是：它必须足够好用，以至于人类真的会去阅读它的评论。如果每个 PR 都有 15 条吹毛求疵的评论，没人会参与。我的目标是每个 PR 最多一条评论。我使用了一个相当直接的链条来构建它：提取差异；将其放入带有规则的提示词中（不要挑剔风格，只标记逻辑错误或安全问题）；让 LLM 输出带有严重程度级别的结构化 JSON。最难的部分不是 AI 部分，而是处理 API 速率限制。这个项目教会了我为什么基础设施的选择比模型的选择更重要。基础设施的警钟。在这里，我要对你直言不讳。
