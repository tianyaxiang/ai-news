billion-context sits between any agent and its model API, rewriting Anthropic/OpenAI streams with acp-kernel compression. The model decides when and what to compress into high-fidelity summaries — not a hard truncation limit.

billion-context 位于任何代理及其模型 API 之间，通过 acp-kernel 压缩重写 Anthropic/OpenAI 流。由模型决定何时以及将什么内容压缩为高保真摘要 — 而非硬性的截断限制。

Why Long coding sessions blow up context. Each provider charges per token, and once you pass the context window the session degrades or dies. billion-context compresses consumed conversation into layered summaries so you can run a single session for days — billions of tokens through one context window. Unlike a host's built-in summarizer, compression here is incremental, reversible, and prefix-cache friendly: summaries are written in small ranges, can be decompressed on demand, and the cache prefix stays intact.

为什么长编码会话会撑爆上下文。每个提供商都按代币收费，一旦超过上下文窗口，会话就会降级或终止。billion-context 将已消耗的对话压缩为分层摘要，因此你可以运行单次会话数天 — 通过一个上下文窗口处理数十亿代币。与宿主内置的摘要器不同，此处的压缩是增量的、可逆的且对前缀缓存友好：摘要以小范围写入，可按需解压缩，且缓存前缀保持完整。

How it works Context-management tools The proxy injects four context-management tools into the conversation; the model calls them itself as context grows, and the proxy executes compress server-side so folded ranges stay summarized in history until restored: compress — fold a message range into a detailed summary. decompress — restore a compressed range when exact details are needed again. search_context — keyword search over compressed summaries and visible messages. acp_status — context-usage overview plus which ranges are still compressible.

工作原理 上下文管理工具 代理将四个上下文管理工具注入对话；随着上下文增长，模型会自动调用它们，代理在服务器端执行压缩，因此折叠的范围在历史记录中保持摘要状态，直到被恢复：compress — 将消息范围折叠为详细摘要。decompress — 当再次需要确切细节时恢复压缩范围。search_context — 对压缩摘要和可见消息进行关键字搜索。acp_status — 上下文使用概览以及哪些范围仍可压缩。
