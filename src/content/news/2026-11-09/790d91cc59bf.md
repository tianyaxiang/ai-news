Short answer: schedule a small, durable command, then make each cleanup batch idempotent. For a marketplace that sends a weekly digest to active customers, I would separate digest eligibility from retention cleanup: enqueue a cleanup job with an explicit execution time, process bounded batches, and retry only the failed batch with exponential backoff. That keeps latency predictable without turning every weekly digest into a costly, fragile transaction.

简短的回答是：调度一个小型、持久化的命令，然后使每个清理批次都具有幂等性。对于一个向活跃客户发送每周摘要的市场平台，我会将摘要资格与保留清理分离开来：将清理作业加入队列并设置明确的执行时间，处理有界批次，并且仅对失败的批次进行指数退避重试。这样既能保持延迟的可预测性，又不会将每周的摘要变成昂贵且脆弱的事务。

The important boundary is time. A delayed job is a request to try work after a deadline, not a guarantee that the work starts at that exact second. Node.js can coordinate the request, but a process-local timer cannot be the system of record. Keep it durable. What is the best practice for complex delayed data cleanup execution? Assume the marketplace stores customer activity, listing events, and the materialized rows used to build a weekly digest. After the digest is published, a cleanup task removes temporary aggregation data that has passed its retention deadline.

重要的界限是时间。延迟作业是在截止日期之后尝试工作的请求，而不是保证工作在那个确切的秒数开始。Node.js 可以协调该请求，但进程本地的计时器不能作为记录系统。请保持其持久性。对于复杂的延迟数据清理执行，最佳实践是什么？假设市场平台存储了客户活动、列表事件以及用于构建每周摘要的物化行。在摘要发布后，清理任务会删除已超过保留期限的临时聚合数据。

The scheduler records a job such as cleanup_week_2026_42, with a due time, a scope, and a unique key. A worker later claims it, deletes or archives a bounded page, records progress, and schedules the next page if more work remains. That data flow has a useful asymmetry: the digest can be late and still be useful; a cleanup can be retried and still be correct. Treating both as one long-running job loses that advantage. A worker crash, a deploy, or a database lock should affect one small unit of work, not the entire weekly run.

调度程序记录一个作业（例如 cleanup_week_2026_42），包含到期时间、范围和唯一键。随后，工作进程会认领该作业，删除或归档一个有界页面，记录进度，并在仍有工作时调度下一页。这种数据流具有一种有用的不对称性：摘要可以延迟但仍然有用；清理可以重试但仍然正确。将两者视为一个长时间运行的作业会失去这种优势。工作进程崩溃、部署或数据库锁定应该只影响一个小的工作单元，而不是整个每周运行。

Here is the shape I use when prototyping this workflow in a notebook before wiring it into a Node.js worker. The example uses only a generic queue interface, so the policy is visible without binding the design to a queue vendor.

以下是我在将工作流接入 Node.js 工作进程之前，在笔记本中进行原型设计时所使用的结构。该示例仅使用通用的队列接口，因此策略清晰可见，而无需将设计绑定到特定的队列供应商。

```python
from dataclasses import dataclass
from datetime import datetime, timedelta, timezone
from typing import Protocol

class Queue(Protocol):
    def enqueue(self, name: str, payload: dict, run_at: datetime, key: str) -> None: ...

@dataclass(frozen=True)
class CleanupRequest:
    customer_ids: list[str]
    retention_until: datetime
    run_id: str

BATCH_SIZE = 200
MAX_ATTEMPTS = 5

def schedule_cleanup(queue: Queue, request: CleanupRequest, now: datetime) -> None:
    if request.retention_until > now:
        run_at = request.retention_until
    else:
        run_at = now
    for offset in range(0, len(request.customer_ids), BATCH_SIZE):
        batch = request.customer_ids[offset:offset + BATCH_SIZE]
        batch_number = offset // BATCH_SIZE
        queue.enqueue(
            name="marketplace_cleanup_batch",
            payload={
                "run_id": request.run_id,
                "customer_ids": batch,
                "attempt": 0,
                "max_attempts": MAX_ATTEMPTS,
            },
            run_at=run_at,
            key=f"{request.run_id}:batch:{batch_number}",
        )

def retry_at(now: datetime, attempt: int) -> datetime:
    delay_seconds = min(900, 2 ** attempt * 5)
    return now + timedelta(seconds=delay_seconds)
```

In production, the Node.js side should implement the same contract: a durable due time, a deduplication key, a bounded payload, and a worker that can safely receive the same key again. The Python snippet is deliberately boring. That is a feature. The scheduling policy should be testable independently of the queue adapter.

在生产环境中，Node.js 端应实现相同的契约：持久的到期时间、去重键、有界负载，以及能够安全地再次接收相同键的工作进程。这段 Python 代码片段故意写得很平淡，这正是其特性所在。调度策略应该能够独立于队列适配器进行测试。

Which failure does the boundary contain? The first failure is duplicate delivery. A queue may deliver a message again after a worker times out, even if the database operation eventually completed. The cleanup handler therefore needs an idempotency key such as (run_id, batch_number) and a database operation whose repeated application has the same result. A delete constrained by the retention predicate is usually easier to reason about than a handler that assumes the rows still exist.

该边界包含了哪些故障？第一个故障是重复投递。即使数据库操作最终完成，队列也可能在工作进程超时后再次投递消息。因此，清理处理程序需要一个幂等键（如 run_id, batch_number）以及一个重复执行后结果相同的数据库操作。受保留谓词约束的删除操作通常比假设行仍然存在的处理程序更容易推理。

The second is partial progress. A 40,000-row cleanup should not be one transaction held open while the digest pipeline waits. Batches of 200 are an example starting point, not a universal constant. Tune the size against lock duration, row width, index behavior, and the latency budget for other marketplace traffic. Persist a cursor or a stable key range after each successful batch; never infer progress from an in-memory array after a restart.

第二个是部分进度。40,000 行的清理不应作为单个事务在摘要管道等待时保持打开状态。200 行的批次只是一个起始示例，而非通用常量。请根据锁定持续时间、行宽度、索引行为以及其他市场流量的延迟预算来调整批次大小。在每个成功的批次后持久化游标或稳定的键范围；切勿在重启后从内存数组中推断进度。

The third is a moving deadline. If a customer becomes active again while a digest is being prepared, a cleanup rule based on a snapshot can remove data that the next digest expects. Put the retention predicate in the database command, and define whether “active” means an event before the run started or an event before each batch. That decision belongs in the data contract, not in a comment beside a timer.

第三个是移动的截止日期。如果在准备摘要时客户再次变得活跃，基于快照的清理规则可能会删除下一次摘要所期望的数据。将保留谓词放入数据库命令中，并定义“活跃”是指运行开始前的事件，还是每个批次前的事件。该决定属于数据契约，而不是计时器旁边的注释。

A fourth failure is retry amplification. A database outage can make thousands of delayed jobs wake up together and all retry at once. Exponential backoff spreads attempts; jitter prevents workers that failed together from becoming synchronized again. AWS documents exponential backoff as a retry strategy for transient API errors, but the same operational reasoning applies to a cleanup worker: retry transient failures, stop on permanent validation errors, and cap the delay. The retry must stop.

第四个故障是重试放大。数据库中断可能导致数千个延迟作业同时唤醒并立即重试。指数退避可以分散尝试；抖动（jitter）可以防止同时失败的工作进程再次同步。AWS 将指数退避记录为瞬态 API 错误的重试策略，但同样的运维逻辑也适用于清理工作进程：重试瞬态故障，在永久验证错误时停止，并限制延迟。重试必须有终点。

How do latency and cost change the design? For a weekly digest, exact-to-the-second execution is rarely the valuable property. The useful measure is the time between the digest becoming eligible and the cleanup reaching its retention target. A scheduler that wakes every minute may add bounded latency while keeping workers simple. A durable delayed queue may give clearer ownership of due work, but it adds an operational component and another state transition to observe.

延迟和成本如何改变设计？对于每周摘要，精确到秒的执行很少是关键价值。有用的衡量标准是摘要变得符合条件到清理达到其保留目标之间的时间。每分钟唤醒一次的调度程序可能会增加有限的延迟，同时保持工作进程的简单性。持久化的延迟队列可能会提供更清晰的到期工作所有权，但它增加了一个运维组件和另一个需要观察的状态转换。

I would choose the smallest mechanism that preserves the required guarantee:

我会选择能保留所需保证的最小机制：

| Requirement | Appropriate boundary | Reason |
| :--- | :--- | :--- |
| One process, best-effort local work | Process timer | Lowest coordination cost, but work disappears with the process |
| Work must survive deploys and restarts | Durable job record | The database can expose due, claimed, and completed states |
| Large cleanup with independent retries | Queue plus batch worker | Failure and retry stay bounded to a batch |
| Strict deletion audit | Job record plus append-only audit event | Operational |

| 要求 | 合适的边界 | 原因 |
| :--- | :--- | :--- |
| 单进程，尽力而为的本地工作 | 进程计时器 | 协调成本最低，但工作会随进程消失 |
| 工作必须在部署和重启后存活 | 持久化作业记录 | 数据库可以暴露到期、已认领和已完成的状态 |
| 带有独立重试的大规模清理 | 队列加批处理工作进程 | 故障和重试被限制在批次内 |
| 严格的删除审计 | 作业记录加仅追加审计事件 | 运维 |
