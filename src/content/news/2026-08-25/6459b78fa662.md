# AI Agents Don’t Need More Context — They Need Typed Context
# AI 智能体不需要更多上下文，它们需要的是“类型化上下文”

**Agentic AI**
**智能体 AI**

**AI Agents Don’t Need More Context — They Need Typed Context**
**AI 智能体不需要更多上下文，它们需要的是“类型化上下文”**

A lightweight runtime layer that separates instructions, evidence, memory, and tool output before they reach the model.
一个轻量级的运行时层，在指令、证据、记忆和工具输出到达模型之前，将它们进行分离。

***

**TL;DR**
**简而言之**

Some AI agent bugs don’t start with a bad model. They start earlier, when instructions, evidence, memory, and tool output are flattened into ordinary strings before the prompt is built, making their original roles harder to inspect and validate.
一些 AI 智能体的 Bug 并非源于模型本身。它们源于更早的阶段：当指令、证据、记忆和工具输出在构建提示词（Prompt）之前被扁平化为普通的字符串时，其原始角色变得难以检查和验证。

I built a small, zero-dependency Python runtime. I’m calling it a context type system, not because the term is an established industry standard, but because the mechanism behaves like a lightweight type system for context objects, that assigns an explicit type to every piece of context (INSTRUCTION, EVIDENCE, MEMORY, TOOL_OUTPUT) and enforces rules about how that type can change before the context is serialized into a prompt.
我构建了一个小型、零依赖的 Python 运行时。我将其称为“上下文类型系统”，这并非因为该术语是行业标准，而是因为其机制类似于上下文对象的轻量级类型系统：它为每一段上下文（指令、证据、记忆、工具输出）分配一个显式类型，并强制执行规则，规定在上下文被序列化为提示词之前，这些类型如何转换。

The core guarantee: content that enters the system as tool output cannot silently become an instruction. The runtime rejects the operation before the model ever sees it.
其核心保证是：以工具输出形式进入系统的内容，无法悄无声息地变成指令。运行时会在模型看到它之前就拒绝该操作。

***

**The Problem Isn’t That Agents Lack Context**
**问题不在于智能体缺乏上下文**

The standard response to a weird agent output is to throw more context at it. Add another retrieved doc. Insert another paragraph of system instructions. Paste another example. Add another reminder to clarify what the last reminder actually meant.
当智能体输出异常时，标准的应对方式是给它塞入更多上下文。添加另一份检索到的文档，插入一段系统指令，粘贴另一个示例，或者再加一条提醒来澄清上一条提醒的含义。

That instinct comes from a reasonable place. Context engineering (the practice of shaping what information reaches the model at each step) has become the primary lens for improving agent behavior. Andrej Karpathy’s framing of it—that assembling the right context for a task matters far more than tweaking a sentence—reshaped how many teams approach agent design.
这种直觉并非毫无根据。上下文工程（即塑造每一步到达模型的信息的过程）已成为改善智能体行为的主要视角。Andrej Karpathy 对此的定义——为任务组装正确的上下文远比微调句子重要——重塑了许多团队进行智能体设计的方式。

Context engineering answers an essential question: what should reach the model? What it fails to answer is a completely different question: what does the runtime know about what each piece of context actually is?
上下文工程回答了一个核心问题：什么信息应该到达模型？但它未能回答另一个完全不同的问题：运行时本身是否知道每一段上下文究竟是什么？

***

**The "String" Problem**
**“字符串”问题**

Consider what happens during a typical agent execution. Under the hood, your runtime might be managing: System instructions, the immediate user request, retrieved documents from a vector store, conversation history, tool execution outputs, and application state variables.
考虑一下典型的智能体执行过程中发生了什么。在底层，你的运行时可能正在管理：系统指令、即时用户请求、从向量数据库检索的文档、对话历史、工具执行输出以及应用程序状态变量。

By the time all of that hits the LLM, it is usually smashed together into a single, massive string. The moment it becomes a string, critical boundaries vanish: A tool output can read like an active instruction. A remembered historical preference can read like a hard requirement for the current turn. A retrieved reference document can read like an authoritative system command.
当所有这些信息到达大模型时，它们通常被合并成一个巨大的字符串。一旦变成字符串，关键的边界就消失了：工具输出可能被解读为主动指令；记忆中的历史偏好可能被解读为当前轮次的硬性要求；检索到的参考文档可能被解读为权威的系统命令。

This doesn’t require anything unusual to happen. It’s what naturally happens whenever heterogeneous data gets mashed together with a naive `"\n".join(…)` before being handed to a model. The runtime never explicitly typed the data. It just had raw text.
这并不需要发生什么异常情况。只要异构数据在交给模型之前通过简单的 `"\n".join(…)` 强行拼接在一起，这种情况就会自然发生。运行时从未对数据进行显式类型化，它处理的仅仅是原始文本。

***

**The Solution: Strict Type Checking**
**解决方案：严格的类型检查**

What I wanted instead was an execution flow where that same tool result must pass through a strict type-check before it can be used. That is the architecture the rest of this project implements and tests as a small runtime experiment. That was the core gap I set out to test.
我想要的是一种执行流程：同样的工具结果在被使用之前，必须通过严格的类型检查。这正是本项目其余部分作为小型运行时实验所实现和测试的架构。这也是我着手测试的核心缺口。
