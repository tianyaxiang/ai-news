# Put Your Own Logic Inside the Codex Agentic Loop
# 将你自己的逻辑植入 Codex 智能体循环

Most of us customize Codex through prompts. We can describe the task, give instructions, and tell Codex what kind of result we expect. This allows us to control how the agent approaches its work. But sometimes, prompting is not enough. We may want to further customize the execution by running our own logic at different stages of a Codex session. So, how can we do that? The answer is Codex hooks. In this post, we’ll explore the concept of hooks and understand where they fit into the agentic loop. Then, we’ll go through a concrete case study to demonstrate the concept.

我们大多数人通过提示词（Prompts）来定制 Codex。我们可以描述任务、给出指令，并告知 Codex 我们期望的结果类型。这使我们能够控制智能体处理工作的方式。但有时，仅靠提示词是不够的。我们可能希望通过在 Codex 会话的不同阶段运行我们自己的逻辑，来进一步定制执行过程。那么，该如何实现呢？答案就是 Codex 钩子（Hooks）。在本文中，我们将探讨钩子的概念，并了解它们如何融入智能体循环。随后，我们将通过一个具体的案例研究来演示这一概念。

### 1. Understanding Codex hooks
### 1. 理解 Codex 钩子

When Codex works on a task, it goes through an agentic loop. For a new session, the user types in a prompt, Codex analyzes the problem, calls tools, and completes the task. You can think of this whole problem-solving trajectory as a lifecycle, and at different points in this lifecycle, Codex emits events with different event names:
*   **SessionStart**: emitted when a session begins;
*   **PreToolUse**: emitted when Codex is about to call a tool;
*   **PostToolUse**: emitted after the tool finishes;
*   **Stop**: emitted when Codex is ready to finish its response;
*   **SessionEnd**: emitted when the Codex session ends.

当 Codex 处理任务时，它会经历一个智能体循环。对于一个新的会话，用户输入提示词，Codex 分析问题、调用工具并完成任务。你可以将整个问题解决轨迹视为一个生命周期，在这个生命周期的不同节点，Codex 会触发带有不同名称的事件：
*   **SessionStart**：会话开始时触发；
*   **PreToolUse**：Codex 即将调用工具时触发；
*   **PostToolUse**：工具执行完成后触发；
*   **Stop**：Codex 准备结束响应时触发；
*   **SessionEnd**：Codex 会话结束时触发。

A Hook is the mechanism that allows us to attach our own logic to these events. For example, we could use SessionStart hook to load additional context, or PreToolUse hook to inspect a command before it runs, or Stop hook to validate a result. So, what does it mean to attach logic to an event? Suppose we configure a hook for PreToolUse. Whenever Codex is about to call a tool, the hook runs a script. Codex passes information about that tool call to the script as part of the context.

钩子是一种允许我们将自定义逻辑附加到这些事件上的机制。例如，我们可以使用 SessionStart 钩子来加载额外的上下文，使用 PreToolUse 钩子在命令运行前进行检查，或者使用 Stop 钩子来验证结果。那么，将逻辑附加到事件上意味着什么呢？假设我们为 PreToolUse 配置了一个钩子。每当 Codex 即将调用工具时，该钩子就会运行一个脚本。Codex 会将有关该工具调用的信息作为上下文的一部分传递给脚本。

Choosing PreToolUse only identifies a point in the lifecycle. Many different tool calls can occur at that point. As a result, we’d also need a matching rule to let us select the ones we actually care about. For example, we could run the script only when Codex is about to execute a shell command. Therefore, there are three basic choices when configuring a hook:
1. At which point in the lifecycle should it run?
2. Under what conditions should it run at that point?
3. What action should it execute?

选择 PreToolUse 仅仅确定了生命周期中的一个点。在该点可能会发生许多不同的工具调用。因此，我们还需要一个匹配规则来筛选出我们真正关心的调用。例如，我们可以设置仅在 Codex 即将执行 Shell 命令时才运行脚本。因此，配置钩子时有三个基本选择：
1. 它应该在生命周期的哪个点运行？
2. 在该点它应该在什么条件下运行？
3. 它应该执行什么操作？

In Codex, these correspond to the event, matcher, and handler. And this is the basic pattern behind Codex hooks.

在 Codex 中，这些分别对应事件（event）、匹配器（matcher）和处理器（handler）。这就是 Codex 钩子背后的基本模式。

### 2. Case study: Adding a quality gate to deep research
### 2. 案例研究：为深度研究添加质量门禁

In this case study, we build a small deep research workflow with Codex. Specifically, we’ll ask Codex to research recent trends in a given topic. Codex will conduct web searches and identify three important trends from the past 90 days. At the end, it should return a structured research brief. To showcase the hook concept, we’ll add a quality check just before Codex finishes. It’ll verify that the brief contains enough sources and that those sources come from a reasonable variety of domains. If the brief passes, Codex can finish. If it fails, the hook will send the problems back to Codex, and Codex will continue researching within the same run until it satisfies our checks.

在本案例研究中，我们将使用 Codex 构建一个小型深度研究工作流。具体来说，我们将要求 Codex 研究给定主题的近期趋势。Codex 将进行网络搜索，并识别过去 90 天内的三个重要趋势。最后，它应返回一份结构化的研究简报。为了展示钩子概念，我们将在 Codex 结束前添加一个质量检查。它将验证简报是否包含足够的来源，以及这些来源是否来自足够多样的领域。如果简报通过检查，Codex 即可结束；如果失败，钩子会将问题反馈给 Codex，Codex 将在同一运行周期内继续研究，直到满足我们的检查要求。

#### 2.1 Preparing the Research Task
#### 2.1 准备研究任务

We’ll start by preparing a prompt template:
```markdown
# Deep research task
Research **{{TOPIC}}**. Use sources published from **{{WINDOW_START}}** through **{{WINDOW_END}}**, inclusive. Identify the three most important trends in that period and prepare a concise, source-backed brief. Return a concise, source-backed research brief that follows the supplied schema.
```

我们首先准备一个提示词模板：
```markdown
# 深度研究任务
研究 **{{TOPIC}}**。使用从 **{{WINDOW_START}}** 到 **{{WINDOW_END}}**（含）期间发布的来源。识别该期间最重要的三个趋势，并准备一份简洁、有来源支持的简报。返回一份遵循所提供模式的、简洁且有来源支持的研究简报。
```

To ensure structured output, we also prepare a JSON schema. We save this as `schemas/research_brief.schema.json`. Note that this is also the structure our hook expects.

为了确保输出结构化，我们还准备了一个 JSON 模式。我们将其保存为 `schemas/research_brief.schema.json`。请注意，这也是我们的钩子所预期的结构。
