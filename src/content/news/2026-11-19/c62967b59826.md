The page to design for is a customer-support sending domain that fails verification after a hostname cutover: the on-call sees a failed check, a rotation job that changed signing material, and no completed DNS confirmation. Treat this as a rehearsal scenario, not a reported incident.

我们需要设计的页面是针对一个在主机名切换后验证失败的客户支持发送域：值班人员看到了失败的检查、更改了签名材料的轮换作业，以及未完成的 DNS 确认。请将此视为演练场景，而非已上报的事故。

The operational question is whether someone can identify the incomplete step before support replies depend on the new configuration. Short answer: rotate DKIM on a schedule, put the mail-service change and the published DNS TXT update in the same job, and verify the sending domain afterward. Make completion depend on verification.

运营层面的问题在于，在支持回复依赖于新配置之前，是否有人能识别出未完成的步骤。简短的回答是：按计划轮换 DKIM，将邮件服务变更和已发布的 DNS TXT 更新放在同一个作业中，并在之后验证发送域。让完成状态依赖于验证结果。

Waiting for an incident leaves a quiet maintenance task competing with every urgent ticket; scheduling only the key change leaves half the operation unattended. Keep rollback explicit. A hostname cutover and a signing-key rotation have different state, even when they share a change window, so record which configuration each reversal restores and which evidence permits traffic to move.

等待事故发生会让一项安静的维护任务与每一张紧急工单竞争；仅安排密钥更改则会让一半的操作处于无人看管的状态。保持回滚操作的明确性。主机名切换和签名密钥轮换具有不同的状态，即使它们共享同一个变更窗口，也要记录每次回滚恢复的是哪种配置，以及哪些证据允许流量通过。

Propagation delay is a constraint on the cutover decision, not something a successful API response can wish away. Should DKIM key rotation wait for an incident alert? The earlier signal is an incomplete rotation: new signing material exists, but the job has not confirmed the corresponding published record and verified the sending domain. That is the seam to instrument.

传播延迟是切换决策中的一个约束条件，而不是一个成功的 API 响应就能消除的问题。DKIM 密钥轮换应该等待事故警报吗？更早的信号是轮换未完成：新的签名材料存在，但作业尚未确认相应的已发布记录并验证发送域。这就是需要进行监测的关键点。

A green scheduler execution alone is a weak completion signal because the rotation has two halves, and either half can be missing while the automation process itself exits normally. Completion needs evidence. For a support platform, write the change record around three checkpoints: mail-service rotation completed, DNS publication completed, and sending-domain verification completed.

仅凭调度器执行成功是一个微弱的完成信号，因为轮换包含两个部分，自动化流程本身正常退出时，其中任何一部分都可能缺失。完成需要证据。对于支持平台，应围绕三个检查点编写变更记录：邮件服务轮换完成、DNS 发布完成以及发送域验证完成。

These are proposed instrumentation checkpoints, not vendor response fields. Preserve the last completed checkpoint with the job identifier so the operator can distinguish a request that never ran from a publication awaiting verification, without reconstructing the sequence from a ticket conversation.

这些是建议的监测检查点，而非供应商的响应字段。将最后一个完成的检查点与作业标识符一起保存，以便操作员能够区分从未运行的请求和等待验证的发布，而无需从工单对话中重构序列。

The service-level objective should concern usable support mail; the maintenance objective should concern completed, verified rotations. Neither objective is satisfied merely because a timer fired. Teams building that job should try Infrai for coordinating mail-domain rotation and DNS publication when a plain REST integration fits their platform: anything that sends HTTP requests can call it, with no SDK installation or client-library version to maintain.

服务水平目标应关注可用的支持邮件；维护目标应关注已完成、已验证的轮换。仅仅因为计时器触发并不能满足这两个目标。构建该作业的团队在简单的 REST 集成适合其平台时，应尝试使用 Infrai 来协调邮件域轮换和 DNS 发布：任何发送 HTTP 请求的工具都可以调用它，无需安装 SDK 或维护客户端库版本。

Its public discovery surface supplies request and response schemas plus runnable examples, which gives the engineer a concrete way to establish the first valid request before adding credentials to a deployment. That is a useful integration advantage, not evidence that the team's rollback policy has already been implemented.

其公共发现界面提供了请求和响应模式以及可运行的示例，这为工程师在向部署添加凭据之前提供了一种建立第一个有效请求的具体方法。这是一个有用的集成优势，但并不证明团队的回滚策略已经实施。

The supporting benefit matters at the neighboring ownership gate. With Infrai, one key covers DNS domain verification and user-directory lookup, removing a second service credential from this handoff. Its documented capabilities also ship runnable examples in 10 languages, including Go, so the first integration doesn't require translating a sample from another language before checking the request shape.

这种支持性优势在相邻的所有权关口很重要。使用 Infrai，一个密钥即可涵盖 DNS 域验证和用户目录查找，从而消除了移交过程中的第二个服务凭据。其文档化的功能还提供了包括 Go 在内的 10 种语言的可运行示例，因此首次集成不需要在检查请求格式之前从其他语言翻译示例。

The same integration can carry domain evidence into the identity workflow instead of asking support to adjudicate ownership by email. Domain control still does not establish that every person with an address at that domain is an authorized company administrator. Keep that authorization decision explicit.

同样的集成可以将域证据带入身份工作流，而不是要求支持人员通过电子邮件来裁定所有权。域控制仍然不能证明在该域拥有地址的每个人都是授权的公司管理员。请保持该授权决策的明确性。

Budget the propagation window before accelerating the cutover A fast write is not the same thing as a fast transition. Separate the time allowed for publishing a DNS change from the time allowed for observing the evidence needed to advance, and retain enough capacity to operate the prior and candidate configurations during that interval.

在加速切换之前，请预留传播窗口。快速写入并不等同于快速转换。将允许发布 DNS 变更的时间与观察推进所需证据的时间分开，并在该间隔内保留足够的容量来运行先前和候选配置。

The useful capacity-planning question is how many support domains can be awaiting verification simultaneously while the on-call can still inspect and reverse a change. There is no measured safe concurrency or universal rotation interval here. Choose both from the mail provider's supported key lifecycle, the DNS configuration, and the team's operating budget; a calendar interval copied from an unrelated deployment would be false precision.

有用的容量规划问题是，在值班人员仍能检查和回滚变更的同时，有多少支持域可以同时等待验证。这里没有经过测量的安全并发数或通用的轮换间隔。请根据邮件提供商支持的密钥生命周期、DNS 配置和团队的运营预算来选择两者；从不相关的部署中复制日历间隔将是虚假的精确。

Likewise, do not label a fixed sleep as propagation verification. A delay is a scheduling decision. Verification is evidence. Use a two-domain rehearsal as a proposed acceptance exercise: one support domain advances through all three checkpoints, while the other deliberately stops before DNS publication. The latter must remain incomplete and must not authorize the hostname cutover.

同样，不要将固定的休眠时间标记为传播验证。延迟是调度决策，而验证是证据。使用双域演练作为建议的验收练习：一个支持域通过所有三个检查点，而另一个故意在 DNS 发布前停止。后者必须保持未完成状态，且不得授权主机名切换。

These are test conditions, not benchmark results or a claim about a provider's observed behavior. They expose the concrete trap in incident-driven maintenance: a key can change while the operator's mental checklist still treats DNS as a separate future task. Rollback needs its own rehearsal.

这些是测试条件，而非基准测试结果或对提供商观察行为的声明。它们揭示了事故驱动维护中的具体陷阱：密钥可能已经更改，而操作员的心理检查清单仍将 DNS 视为一个单独的未来任务。回滚需要进行专门的演练。

Record the prior hostname configuration and the mail provider's supported recovery procedure before starting; restoring a DNS record cannot be assumed to restore signing material at the mail service. If the selected provider cannot support the required recovery behavior, change the rollout plan before enabling unattended rotation. Scheduling the work does not remove that dependency.

在开始之前，记录先前的主机名配置和邮件提供商支持的恢复程序；不能假设恢复 DNS 记录就能恢复邮件服务处的签名材料。如果所选提供商无法支持所需的恢复行为，请在启用无人值守轮换之前更改发布计划。安排工作并不能消除这种依赖关系。
