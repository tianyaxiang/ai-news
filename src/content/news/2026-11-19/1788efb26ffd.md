# CVE-2026-73504: Plaintext Authentication Token Exposure in cassandra-jdbc-wrapper Debug Logs

CVE-2026-73504：cassandra-jdbc-wrapper 调试日志中的明文身份验证令牌泄露

Vulnerability ID: CVE-2026-73504 CVSS Score: 5.5 Published: 2026-11-19 CVE-2026-73504 (GHSA-jc42-994r-vvwp) is a credential exposure vulnerability in ING Bank's cassandra-jdbc-wrapper (com.ing.data:cassandra-jdbc-wrapper). Resulting from an incomplete remediation of AIKIDO-2024-10565, the log sanitization routines in DriverUtil redact the password property but fail to redact the token property. When DEBUG logging is enabled, connection properties and JDBC URLs containing DataStax Astra DB bearer tokens are written in plaintext to application logs, enabling local users or log aggregation readers to harvest active database credentials.

漏洞 ID：CVE-2026-73504，CVSS 评分：5.5，发布日期：2026-11-19。CVE-2026-73504 (GHSA-jc42-994r-vvwp) 是 ING Bank 的 cassandra-jdbc-wrapper (com.ing.data:cassandra-jdbc-wrapper) 中的凭据泄露漏洞。由于对 AIKIDO-2024-10565 的修复不完整，DriverUtil 中的日志脱敏程序虽然对密码属性进行了屏蔽，但未能屏蔽令牌属性。当启用 DEBUG 日志记录时，包含 DataStax Astra DB 持有者令牌的连接属性和 JDBC URL 会以明文形式写入应用程序日志，从而使本地用户或日志聚合读取器能够获取活动的数据库凭据。

TL;DR An incomplete log redaction routine in cassandra-jdbc-wrapper versions prior to 4.16.4 and 5.0.2 writes plaintext authentication tokens (such as DataStax Astra DB tokens) to application logs when DEBUG logging is active.

简而言之：在 4.16.4 和 5.0.2 版本之前的 cassandra-jdbc-wrapper 中，一个不完整的日志脱敏程序会在启用 DEBUG 日志记录时，将明文身份验证令牌（如 DataStax Astra DB 令牌）写入应用程序日志。

技术细节：CVE / 公告 ID：CVE-2026-73504 / GHSA-jc42-994r-vvwp；弱点类别：CWE-532（将敏感信息插入日志文件）；CVSS v3.1 评分：5.5 中危 (CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N)；攻击向量：本地 / 日志文件及 SIEM 读取权限；受影响的包：com.ing.data:cassandra-jdbc-wrapper (< 4.16.4, 5.0.0 - 5.0.1)；已修复版本：4.16.4 和 5.0.2；漏洞利用 / KEV 状态：无已知公开利用；未列入 CISA KEV。

Affected Systems com.ing.data:cassandra-jdbc-wrapper (Maven / Java) cassandra-jdbc-wrapper (4.x Branch): < 4.16.4 (Fixed in: 4.16.4) cassandra-jdbc-wrapper (5.x Branch): >= 5.0.0, < 5.0.2 (Fixed in: 5.0.2)

受影响系统：com.ing.data:cassandra-jdbc-wrapper (Maven / Java)；cassandra-jdbc-wrapper (4.x 分支)：< 4.16.4（已在 4.16.4 中修复）；cassandra-jdbc-wrapper (5.x 分支)：>= 5.0.0, < 5.0.2（已在 5.0.2 中修复）。

Mitigation Strategies Upgrade cassandra-jdbc-wrapper to a patched release (4.16.4+ or 5.0.2+). Pass sensitive authentication parameters (token, password) via java.util.Properties rather than raw JDBC URL query strings. Restrict logger verbosity for the com.ing.data.cassandra.jdbc namespace to INFO or WARN. Rotate all DataStax Astra DB tokens and database credentials that may have been logged during DEBUG sessions. Apply regex-based log scrubbing in log shipping and SIEM ingestion pipelines.

缓解策略：将 cassandra-jdbc-wrapper 升级到已修复版本（4.16.4+ 或 5.0.2+）。通过 java.util.Properties 而非原始 JDBC URL 查询字符串传递敏感身份验证参数（令牌、密码）。将 com.ing.data.cassandra.jdbc 命名空间的日志记录级别限制为 INFO 或 WARN。轮换所有在 DEBUG 会话期间可能已被记录的 DataStax Astra DB 令牌和数据库凭据。在日志传输和 SIEM 摄取管道中应用基于正则表达式的日志清理。

Remediation Steps: Update com.ing.data:cassandra-jdbc-wrapper to version 4.16.4 (for 4.x users) or 5.0.2 (for 5.x users) in your build configuration. Verify that logback.xml or log4j2.xml configurations set com.ing.data.cassandra.jdbc to INFO or higher in production and staging environments. Search existing application log files and centralized log indices for instances of 'AstraCS:' or 'token='. Revoke and regenerate any exposed authentication tokens via the DataStax Astra console and purge affected log segments.

修复步骤：在构建配置中将 com.ing.data:cassandra-jdbc-wrapper 更新至 4.16.4 版本（针对 4.x 用户）或 5.0.2 版本（针对 5.x 用户）。验证生产和预发布环境中的 logback.xml 或 log4j2.xml 配置是否将 com.ing.data.cassandra.jdbc 设置为 INFO 或更高级别。搜索现有的应用程序日志文件和集中式日志索引，查找 'AstraCS:' 或 'token=' 的实例。通过 DataStax Astra 控制台撤销并重新生成任何已泄露的身份验证令牌，并清除受影响的日志片段。
