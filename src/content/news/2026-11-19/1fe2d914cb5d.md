Short answer: let the cron trigger enqueue a small, repeatable command, then let a queue worker deliver each customer digest. A 15-minute scheduler limit is fine when no individual invocation owns the whole report. The useful guarantee is a recorded handoff, not a heroic timeout.

简短的回答是：让 Cron 触发器将任务加入队列，执行一个小的、可重复的命令，然后由队列工作进程负责发送每位客户的摘要。当没有任何单一调用需要负责整个报告时，15 分钟的调度器限制是可以接受的。真正有用的保证是记录在案的任务交接，而不是试图通过延长超时时间来解决问题。

A small decision matrix for weekly delivery:

针对每周交付的小型决策矩阵：

| Design | What it can prove | Where it fits | Trade-off |
| :--- | :--- | :--- | :--- |
| Cron calls the report directly | The process started | A tiny, read-only task | A timeout can hide partial work |
| Cron enqueues one batch | The batch was handed off | Uniform, short reports | One poison item can delay the batch |
| Cron records a run and enqueues customer jobs | Each customer has a traceable attempt | Active-customer digests | Requires a ledger and reconciliation |

| 设计 | 可证明的内容 | 适用场景 | 权衡 |
| :--- | :--- | :--- | :--- |
| Cron 直接调用报告 | 流程已启动 | 微小的只读任务 | 超时可能掩盖部分未完成的工作 |
| Cron 将一批任务加入队列 | 批次已成功交接 | 统一的短报告 | 单个“毒药”项可能延迟整个批次 |
| Cron 记录运行并为客户加入队列 | 每个客户都有可追踪的尝试 | 活跃客户摘要 | 需要账本和对账机制 |

For a B2B SaaS digest, I use the third row. The trigger writes a run record, creates one message per active customer, and exits. A worker owns data fetching, rendering, and delivery. That split keeps the scheduler's execution window boring and makes the business result inspectable. This is a revenue-per-hour decision. Queue mechanics are undifferentiated plumbing; I want them managed or isolated so one person can spend the week shipping product. The ledger is worth keeping in application code because it answers the question support actually asks: “Did Acme's Monday report send?”

对于 B2B SaaS 摘要，我使用第三种方案。触发器写入运行记录，为每个活跃客户创建一条消息，然后退出。工作进程负责数据获取、渲染和交付。这种拆分使调度器的执行窗口变得简单可控，并使业务结果可审查。这是一个关于每小时产出的决策。队列机制属于无差别的底层设施；我希望它们被托管或隔离，以便一个人就能把一周的时间花在交付产品上。账本值得保留在应用程序代码中，因为它能回答支持团队真正关心的问题：“Acme 周一的报告发送了吗？”

What delivery guarantee does the queue really provide? Most queues provide at-least-once delivery. A message may appear again after a worker has sent the email but before it has acknowledged the message. A FIFO queue can preserve ordering and, with a deduplication window, reduce duplicates, but it cannot make an external email provider exactly-once. AWS describes those FIFO properties and their limits in its queue documentation. So I define two separate facts: enqueued means the scheduler committed a message, and sent means the delivery provider accepted the final payload. A retry changes attempts; it must not create a second business event. The idempotency key joins the scheduled run and customer ID, and the delivery adapter stores that key before acknowledging work.

队列到底提供了什么样的交付保证？大多数队列提供“至少一次”交付。在工作进程发送邮件之后、确认消息之前，消息可能会再次出现。FIFO（先进先出）队列可以保持顺序，并通过去重窗口减少重复，但它无法使外部邮件提供商实现“恰好一次”交付。AWS 在其队列文档中描述了这些 FIFO 属性及其局限性。因此，我定义了两个独立的事实：已入队意味着调度器提交了一条消息，已发送意味着交付提供商接受了最终负载。重试会改变尝试次数，但绝不能创建第二个业务事件。幂等键将计划运行 ID 与客户 ID 关联起来，交付适配器在确认工作之前会存储该键。

There is a catch. A per-customer job is only safe if its inputs are stable enough to replay. Store the report version or a snapshot pointer in the message, rather than serializing a giant report into it. If the worker sees the same key, it returns the prior result. That behavior is more valuable than squeezing another minute out of the cron runtime.

这里有个陷阱。只有当输入足够稳定以支持重放时，针对每个客户的任务才是安全的。应在消息中存储报告版本或快照指针，而不是将庞大的报告序列化到消息中。如果工作进程看到相同的键，它会返回之前的结果。这种行为比从 Cron 运行时中多挤出一分钟时间更有价值。

How should a cron trigger enqueue Node.js work for long-running cleanup reports? Use the trigger as a coordinator, not as the worker. This TypeScript example uses generic interfaces so the same state machine can sit over a hosted queue, a database-backed queue, or a self-managed broker.

Cron 触发器应如何为长时间运行的清理报告安排 Node.js 任务？将触发器用作协调器，而不是工作进程。这个 TypeScript 示例使用了通用接口，因此同一个状态机可以运行在托管队列、数据库支持的队列或自托管代理之上。

```typescript
type DigestJob = { runId: string; customerId: string; snapshotId: string; };

async function scheduleDigest(now: Date): Promise<void> {
  const runId = `weekly:${now.toISOString().slice(0, 10)}`;
  const customers = await customerStore.activeIds();
  await ledger.insertIfAbsent({ runId, status: "enqueuing", total: customers.length });
  for (const customerId of customers) {
    const snapshotId = await reportStore.freezeInputs(customerId, runId);
    await queue.send({ runId, customerId, snapshotId } satisfies DigestJob);
  }
  await ledger.markEnqueued(runId);
}

async function work(job: DigestJob): Promise<void> {
  const key = `${job.runId}:${job.customerId}`;
  if (await ledger.wasSent(key)) return;
  const report = await reportStore.render(job.snapshotId);
  await delivery.sendEmail(job.customerId, report, { idempotencyKey: key });
  await ledger.markSent(key);
}
```

The loop is intentionally plain. In production, enqueue in bounded pages and record the last successful page. A crash after page three should resume at page four, not silently claim that all customers were handled. The worker should renew its lease while rendering, cap retries, and move a repeatedly failing item to a dead-letter queue with the run ID attached. Node.js is a good fit for this coordination because the trigger does little synchronous work. It is not a reason to keep a 40-minute report inside one process. Break expensive cleanup into retryable units, and make each unit observable.

这个循环被刻意写得很简单。在生产环境中，应按分页加入队列并记录最后成功的分页。在第三页之后崩溃应该从第四页恢复，而不是静默地声称所有客户都已处理完毕。工作进程在渲染时应续订租约，限制重试次数，并将反复失败的项目连同运行 ID 一起移至死信队列。Node.js 非常适合这种协调工作，因为触发器几乎不做同步工作。这并不是将 40 分钟的报告保留在单个进程中的理由。将昂贵的清理工作分解为可重试的单元，并使每个单元都可观测。

Where do scheduled jobs fail after the trigger appears healthy? The first failure mode is an apparently successful timeout. The scheduler waits 15 minutes, stops waiting, and the enqueue may already be committed. If an operator retries manually without checking the ledger, two weekly runs enter the queue. A deterministic run ID plus an insert-if-absent constraint turns that ambiguity into a visible state. The second is a worker crash at the worst possible line: after the provider accepted an email, before the queue acknowledgement. The next delivery sees the same idempotency key and records a duplicate attempt without sending again. Test this exact point. It is a five-minute fault injection that exposes a whole class of expensive support tickets.

在触发器看起来正常后，计划任务会在哪里失败？第一种失败模式是看似成功的超时。调度器等待 15 分钟后停止等待，而入队操作可能已经提交。如果操作员在未检查账本的情况下手动重试，队列中就会出现两次每周运行。确定性的运行 ID 加上“如果不存在则插入”的约束，将这种歧义转化为可见的状态。第二种是工作进程在最糟糕的代码行崩溃：在提供商接受邮件之后、队列确认之前。下一次交付会看到相同的幂等键，并记录重复尝试，而不会再次发送。测试这个确切的点。这是一个只需五分钟的故障注入，却能暴露出一大类昂贵的支持工单。

That is the contract. The useful test matrix is wider than a happy-path unit test. Start a run with ten customers, kill the worker after rendering customer four, and let the lease expire. The replay should produce four recorded attempts, no second email for customer four, and six untouched messages. Then pause the delivery provider for twelve minutes and watch backlog age, retry count, and dead-letter movement. Finally, deploy a new message schema while an old worker is still draining; the old worker must reject or ignore fields it does not understand without marking the job sent. These checks cost less than a support incident because they exercise the boundaries where state changes hands. I keep the fixture data small and deterministic, so I can run the scenario locally before a weekly release and compare the ledger rows as plain text. It is not glamorous.
