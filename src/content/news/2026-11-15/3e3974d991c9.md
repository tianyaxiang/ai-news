It starts with one small error in Lovable. You press Try to fix, the error comes back in a new shape, you press it again, and a few rounds later pages that worked yesterday are blank. It's one of the most common ways I see founders lose a day (and a pile of credits). Here's why the loop happens, and the order I use to get out of it without throwing the project away.

一切始于 Lovable 中的一个小错误。你点击“尝试修复”（Try to fix），错误以新的形式卷土重来，你再次点击，几轮之后，昨天还能正常工作的页面却变为空白。这是我见过的创始人浪费一天时间（以及大量积分）最常见的方式之一。以下是循环发生的原因，以及我在不放弃项目的前提下摆脱困境的步骤。

What you might be seeing: Lovable stuck in a loop on the same error; Try to fix keeps failing, or "fixes" it and breaks something else; "Lovable broke my app": a page that worked yesterday is now blank or erroring.

你可能遇到的情况：Lovable 卡在同一个错误的循环中；“尝试修复”不断失败，或者“修复”了问题却导致其他地方损坏；“Lovable 弄坏了我的应用”：昨天还能用的页面现在变为空白或报错。

Why it happens: Blind retries. Pressing Try to fix again and again adds patches on top of patches. Lovable's own docs say repeated blind fixes tend to pile up code that hides the real problem. The AI can't see the real error. Errors on your published site or in your backend logs never reach the editor unless you paste them in. The problem isn't in the code being changed. A Supabase policy, a missing secret or an expired API key fails no matter how many times the screen is rewritten. The prompt asked for too much at once. A broad change touches many files and breaks things far from what you asked for.

发生原因：盲目重试。反复点击“尝试修复”会在补丁之上叠加更多补丁。Lovable 官方文档指出，重复的盲目修复往往会堆积代码，从而掩盖真正的问题。AI 看不到真正的错误。除非你手动粘贴，否则已发布网站或后端日志中的错误永远不会传达到编辑器。问题并不在于正在修改的代码。无论屏幕被重写多少次，Supabase 策略、缺失的密钥或过期的 API 密钥都会导致失败。提示词一次性要求过多。大范围的更改会触及许多文件，并破坏你要求之外的内容。

Find the cause first: Before the next prompt, spend five minutes on this: Write down what is broken, where, what you expected, and what actually happened. Copy the exact error: from the browser console for front-end problems, or from the Supabase logs for backend ones. Ask yourself whether the failing step touches the database, sign-in, payments or an outside API. Those usually fail outside the screen code, so no amount of UI rewriting will fix them.

首先找到原因：在下一次提示之前，花五分钟做这件事：写下哪里坏了、在什么位置、你预期的结果是什么，以及实际发生了什么。复制确切的错误信息：前端问题从浏览器控制台复制，后端问题从 Supabase 日志复制。问问自己，失败的步骤是否涉及数据库、登录、支付或外部 API。这些通常在屏幕代码之外失败，因此无论如何重写 UI 都无法修复它们。

Fix 1: Follow Lovable's recovery order: Lovable documents a quick workflow for exactly this, and it's the order I follow: Use Try to fix once or twice, no more. (Lovable's docs say your account includes 10 free fixes, and each comes back 24 hours after you use it.) Describe the bug precisely. Say what is broken, where, what you expected and what happened, and paste the exact error or attach a screenshot. "Nothing works, fix it" gives the AI nothing to point at. Something like this (an example) does: The Projects page goes blank after I click "New project". Expected: the form opens. Console error: TypeError: Cannot read properties of undefined (reading 'map'). This worked yesterday. Check what changed in the Projects page since then. Switch to Plan mode and ask why before changing more code. For example: "What is the root cause of this error? Show me the relevant code and explain it before proposing a fix." Asking "what have we already tried for this error?" also stops it repeating the same failed fix. If the fixes have tangled the code, restore a working version from version history (or edit a past message and choose Revert and resend). Then tell Lovable what you reverted, so it has the context for the next attempt. Reverting feels like losing work, but it's usually faster than untangling ten layers of patches.

修复方案 1：遵循 Lovable 的恢复顺序：Lovable 针对这种情况记录了一个快速工作流程，这也是我遵循的顺序：使用“尝试修复”一到两次，不要再多。（Lovable 文档称你的账户包含 10 次免费修复，每次使用后 24 小时恢复。）精确描述错误。说明哪里坏了、在什么位置、你预期的结果是什么以及发生了什么，并粘贴确切的错误或附上截图。“什么都不能用了，修一下”这种说法让 AI 无从下手。像这样（示例）才有效：点击“新项目”后，项目页面变为空白。预期：表单打开。控制台错误：TypeError: Cannot read properties of undefined (reading 'map')。这在昨天还能用。检查自那时起项目页面发生了什么变化。切换到“计划模式”（Plan mode），在更改更多代码之前询问原因。例如：“这个错误的根本原因是什么？在提出修复方案之前，请向我展示相关代码并进行解释。”询问“我们之前针对这个错误尝试过什么？”也能防止它重复同样的失败修复。如果修复导致代码混乱，请从版本历史记录中恢复一个可用的版本（或编辑过去的消息并选择“撤销并重新发送”）。然后告诉 Lovable 你撤销了什么，以便它为下一次尝试提供上下文。撤销感觉像是丢失了工作，但通常比解开十层补丁要快得多。

Fix 2: Rebuild the broken piece, not the app: When one component is broken beyond patching, isolate it: Ask for a fresh, minimal version of just that one component, check that it works on its own, then connect it back. For delicate areas like sign-in or payments, set guardrails in the same prompt: ask Lovable to read all the related code first and not to touch unrelated components.

修复方案 2：重建损坏的部分，而不是整个应用：当某个组件损坏到无法修补时，将其隔离：要求提供该组件的全新、最小化版本，检查其是否能独立工作，然后再将其连接回去。对于登录或支付等敏感区域，在同一个提示词中设置护栏：要求 Lovable 先阅读所有相关代码，并且不要触及不相关的组件。

Fix 3: Check the backend directly: If the failing action saves data, signs someone in or calls an outside service, look outside the editor: Read the Supabase logs and the table's row-level security policies for the action that fails. Confirm that the secrets your functions need actually exist in the live project. When the cause is an access rule or a missing secret, rewriting the screen never helps, which is why the loop keeps going.

修复方案 3：直接检查后端：如果失败的操作涉及保存数据、用户登录或调用外部服务，请查看编辑器之外的内容：阅读失败操作对应的 Supabase 日志和表的行级安全策略。确认你的函数所需的密钥确实存在于实时项目中。当原因是访问规则或缺失密钥时，重写屏幕永远无济于事，这就是循环不断持续的原因。

Check the fix worked: The original bug is gone, and the flows around it (sign-in, saving, payments) still work. Run a scan of the published site to catch anything the loop exposed along the way, such as keys in the JavaScript or missing security headers.

检查修复是否有效：原始错误已消失，且其周围的流程（登录、保存、支付）仍然有效。对已发布的网站进行扫描，以捕捉循环过程中暴露出的任何问题，例如 JavaScript 中的密钥或缺失的安全标头。

Stop it coming back: After you solve a hard bug, add the cause and the fix to the project knowledge so Lovable applies it next time. Lovable's docs suggest asking it to summarize the issue and the fix for exactly this. Make one change per prompt and test before the next. Connect the project to GitHub so every working state is saved outside the editor.

防止问题重现：解决一个棘手的错误后，将原因和修复方法添加到项目知识库中，以便 Lovable 下次能应用它。Lovable 的文档建议专门为此要求它总结问题和修复方案。每次提示只做一个更改，并在下一次更改前进行测试。将项目连接到 GitHub，以便每个可用的状态都能保存在编辑器之外。

Quick answers: Will a developer have to throw away my Lovable code? Rarely. Most loops come from a few broken areas, often access rules or one tangled component. Those get fixed and the rest stays. Can I keep building in Lovable afterwards? Yes. If the work goes through GitHub, the project stays editable in Lovable.

快速问答：开发者必须丢弃我的 Lovable 代码吗？很少见。大多数循环源于少数几个损坏的区域，通常是访问规则或某个混乱的组件。修复这些问题后，其余部分保持不变。之后我还能继续在 Lovable 中构建吗？可以。如果工作通过 GitHub 进行，项目在 Lovable 中依然可编辑。
