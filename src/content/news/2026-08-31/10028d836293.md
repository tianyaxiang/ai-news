# Noisy Text in RAG: Typos, OCR, and the Gap Classical Spell-Check Leaves
# RAG 中的噪声文本：拼写错误、OCR 与传统拼写检查的局限

The user types “assurance décénale” and the document says “décennale.” One missing letter, and a literal search finds nothing. Real questions arrive with typos, and real documents have their own; before retrieval can match anything, someone has to fix the spelling on both sides.
用户输入“assurance décénale”，而文档中写的是“décennale”。仅仅少了一个字母，字面搜索就无法匹配任何内容。真实的问题往往带有拼写错误，而真实的文档也同样存在此类问题；在检索能够匹配到任何内容之前，必须有人修复双方的拼写。

This article is a bonus in Enterprise Document Intelligence, a series that builds an enterprise RAG system from four bricks. It tackles noisy text across the pipeline: user typos, fast-typing transcription noise, OCR character errors, what classical spell-check fixes, and what embeddings have to carry.
本文是《企业文档智能》系列的一篇番外篇，该系列旨在通过四个模块构建企业级 RAG 系统。本文探讨了整个流程中的噪声文本问题：用户拼写错误、快速输入导致的转录噪声、OCR 字符错误，以及传统拼写检查能解决的问题和嵌入（embeddings）必须承担的任务。

The same problem shows up on both sides of a pipeline. On the question side, type “wat is teh covarge for fyre damge?” into a chatbot built over a company knowledge base: three typos and a missing letter, and the chatbot returns nothing useful until the question is retyped carefully. On the document side, dump 50,000 customer support tickets into the same pipeline for retrieval: half of them are written in fragments, abbreviations, mixed case, with the same kind of errors, and the pipeline that worked for clean queries against clean documents starts returning noise.
同样的问题出现在流程的两端。在提问端，如果向基于公司知识库构建的聊天机器人输入“wat is teh covarge for fyre damge?”：三个拼写错误和一个漏掉的字母，会导致聊天机器人无法返回任何有用的信息，除非重新仔细输入问题。在文档端，如果将 50,000 条客户支持工单导入同一个检索流程：其中一半工单由片段、缩写、大小写混杂组成，并带有同样的错误，那么原本适用于干净查询和干净文档的流程就会开始返回噪声。

This is the noisy-text problem in enterprise RAG. It looks like a spell-check problem from the outside, but the actual cause splits three ways. The user mistyped a word (a typo). The user typed under pressure on mobile and scrambled boundaries, dropped accents, abbreviated (transcription noise). The document came through OCR and a scanner silently replaced O with 0, broke a fi ligature, split policyholder into policy holder (OCR noise). All three end with the same symptom downstream: a token in the query or in the document does not literally match what it should, even though the meaning is intact.
这就是企业级 RAG 中的噪声文本问题。从表面上看，这似乎是一个拼写检查问题，但其根本原因可分为三类。用户输错了一个词（拼写错误）；用户在移动端匆忙输入，导致边界混乱、漏掉重音符号或使用缩写（转录噪声）；文档经过 OCR 和扫描仪处理，导致 O 被静默替换为 0、fi 连字断开、policyholder 被拆分为 policy holder（OCR 噪声）。这三种情况在下游表现出相同的症状：查询或文档中的某个标记（token）在字面上无法匹配，尽管其含义依然完整。

The classical spell-correction toolbox was built for one of the three. The other two are the ones that hurt enterprise pipelines, and the ones embeddings are quietly built to absorb.
传统的拼写校正工具箱最初是为这三种情况中的一种设计的。而后两种情况正是损害企业流程的元凶，也是嵌入（embeddings）被默默设计用来吸收的问题。

### 1. Forty years of classical spell-correction
### 1. 四十年的传统拼写校正

Before embeddings and LLMs, spell-correction was a solved engineering problem. Five techniques cover most of what ran in production between 1980 and today, all with mature Python libraries (rapidfuzz, jellyfish, symspellpy, pybktree). The next subsections walk through each, then close with the case where this toolbox solves the problem.
在嵌入和大语言模型出现之前，拼写校正是一个已经解决的工程问题。五种技术涵盖了 1980 年至今生产环境中运行的大部分方案，且都有成熟的 Python 库支持（如 rapidfuzz, jellyfish, symspellpy, pybktree）。接下来的小节将逐一介绍这些技术，并总结该工具箱在何种情况下能解决问题。

#### 1.1 Levenshtein distance
#### 1.1 莱文斯坦距离 (Levenshtein distance)

The minimum number of single-character edits (insert, delete, substitute) needed to turn one word into another. The foundation under almost every spell-checker built in the last forty years.
将一个单词转换为另一个单词所需的最少单字符编辑次数（插入、删除、替换）。这是过去四十年中几乎所有拼写检查器的基础。

```python
from rapidfuzz.distance import Levenshtein
Levenshtein.distance("coverage", "cverage") # 1 (delete the second 'o')
Levenshtein.distance("coverage", "covarage") # 1 (insert 'a')
Levenshtein.distance("coverage", "ocverage") # 2 (swap, then move)
```

A misspelled word’s “best correction” is the dictionary entry with the smallest Levenshtein distance, broken by frequency in case of ties. The full algorithm runs in O(n·m) time: fast on a single word, but on a 50,000-word document it means one comparison matrix per word pair, which adds up quickly.
拼写错误单词的“最佳修正”是字典中莱文斯坦距离最小的条目，若距离相同则按频率判定。完整算法的运行时间为 O(n·m)：处理单个单词很快，但对于 50,000 字的文档，这意味着每对单词都要进行一次比较矩阵运算，计算量会迅速累积。

#### 1.2 BK-tree
#### 1.2 BK 树 (BK-tree)

A Levenshtein query against a million-word dictionary is too slow if you compute distance to every entry. The Burkhard-Keller tree (1973) indexes the dictionary so that all words within distance k of a query are reachable in roughly O(log n).
如果对百万词汇量的字典逐一计算莱文斯坦距离，查询速度会太慢。Burkhard-Keller 树（1973 年）通过对字典进行索引，使得查询距离 k 以内的所有单词的时间复杂度约为 O(log n)。

```python
import pybktree
tree = pybktree.BKTree(Levenshtein.distance, ["coverage", "average", "overage", "leverage"])
tree.find("cverage", n=1) # [(1, 'coverage')]
```

This makes aspell and hunspell feel instant. No machine learning, no GPU, just a clever index built on triangle inequality.
这使得 aspell 和 hunspell 的响应速度极快。无需机器学习，无需 GPU，仅仅是基于三角不等式构建的巧妙索引。

#### 1.3 Soundex and Metaphone
#### 1.3 Soundex 和 Metaphone

Phonetic codes. They map words that sound alike to the same key regardless of spelling. Designed in the 1910s for U.S. census name matching, still useful today for surname lookup, drug-name disambiguation, voice-to-text post-processing.
语音编码。它们将发音相似的单词映射到同一个键，而不考虑拼写。这些算法设计于 1910 年代，最初用于美国人口普查的姓名匹配，至今在姓氏查找、药物名称消歧和语音转文字后处理中依然有用。

```python
from jellyfish import soundex, metaphone
soundex("Smith"), soundex("Smyth") # ('S530', 'S530') same key
soundex("Robert"), soundex("Rupert") # ('R163', 'R163') same key
metaphone("through"), metaphone("thru") # ('0R', '0R') same code
```

Phonetic matching catches the kind of variation that Levenshtein misses: a French speaker writing Stéphane as Stefan, an English speaker writing Catherine as Kathryn. The price is that any two unrelated words that happen to sound alike collide.
语音匹配可以捕捉到莱文斯坦距离无法处理的变体：例如法语使用者将 Stéphane 写成 Stefan，英语使用者将 Catherine 写成 Kathryn。代价是任何两个发音巧合相似的无关单词会发生冲突。

#### 1.4 SymSpell
#### 1.4 SymSpell

The modern fast variant. Precomputes all deletes within distance k for every dictionary word and stores them in a hash. Lookup becomes a hash join, sub-millisecond on a 100k-word dictionary on a single CPU core.
现代的高速变体。它预先计算字典中每个单词在距离 k 内的所有删除情况，并将其存储在哈希表中。查找过程变成了哈希连接，在单核 CPU 上处理 10 万词汇量的字典时，响应时间在毫秒级以下。

```python
from symspellpy import SymSpell, Verbosity
sym = SymSpell(max_dictionary_edit_distance=2)
sym.create_dictionary_entry("coverage", count=1000)
sym.create_dictionary_entry("overage", count=50)
suggestions = sym.lookup("covrage", Verbosity.CLOSEST, max_edit_distance=2)
# [SuggestItem(term='coverage', distance=1, count=1000), ...]
```

Frequency breaks ties. The dictionary is best built from the target corpus itself, not a generic word list, so corrections land on terms that appear in the documents the user is searching.
频率用于打破平局。字典最好基于目标语料库本身构建，而不是使用通用的词表，这样修正结果才会落在用户正在搜索的文档中出现的术语上。
