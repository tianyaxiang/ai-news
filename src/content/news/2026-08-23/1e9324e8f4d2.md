The standard advice for taking a RAG system past one document is to build an index: one row per document, one column per field you may want to filter on, then a filter in front of the search. That advice assumes the documents have fields in common. Plenty of folders do not.

将 RAG 系统扩展到单文档之外的标准建议是构建索引：每个文档一行，每个你可能想要过滤的字段一列，然后在搜索前设置一个过滤器。该建议的前提是文档具有共同字段。但许多文件夹并非如此。

Take a research folder: a 492-page catalogue of security controls, a zero-trust architecture spec, an AI risk framework, thirty-one machine-learning papers, and seven commodity market reports. Ask what column they share. There is no client, no amount, no effective date that would mean the same thing across all of them, and no other field a business user could name either.

以一个研究文件夹为例：一份 492 页的安全控制目录、一份零信任架构规范、一个人工智能风险框架、三十一篇机器学习论文以及七份大宗商品市场报告。试问它们共享什么列？没有客户、没有金额、没有在所有文档中含义相同的生效日期，业务用户也无法说出任何其他共享字段。

When there is no shared field, there is no table to build. That reads like a missing piece. It is the opposite. It means the preparation step collapses into two artefacts, and one of them the parser already returns for free. This article works through that case: the two questions that tell it apart from the case that does need an index; the preparation, which is one summary line per file plus each file’s own table of contents, and nothing else; why the summary line has to be written for a router rather than for a reader; the two-level routing that answers a question, and why the nested outline never enters a prompt whole; four ways it breaks, including the point where the flat file list stops scaling.

当没有共享字段时，也就没有表格可建。这看起来像是缺失了一环，但事实恰恰相反。这意味着准备步骤简化为两个产物，其中一个解析器已经免费提供了。本文将探讨这种情况：区分它与需要索引的情况的两个问题；准备工作（即每个文件一行摘要加上其自身的目录，仅此而已）；为什么摘要行必须为路由器而非读者编写；回答问题的两级路由，以及为什么嵌套大纲从不完整进入提示词；它失效的四种方式，包括扁平文件列表停止扩展的临界点。

This article is part of Part IV of Enterprise Document Intelligence, a series that builds an enterprise RAG system from four bricks. Part IV asks what changes when the input is a folder instead of a file, and the answer depends on which kind of folder you have. This one is the kind that needs the least new machinery.

本文是《企业文档智能》第四部分的内容，该系列旨在用四个模块构建企业级 RAG 系统。第四部分探讨了当输入从单个文件变为文件夹时会发生什么变化，答案取决于你拥有哪种类型的文件夹。本文所讨论的正是那种需要最少新架构的类型。

### 1. Which kind of folder do you have
### 1. 你拥有哪种类型的文件夹？

Article 14A (three kinds of corpus, and what building for the wrong one costs) sets out three shapes a collection can take, and says that each one wants a different architecture. This article takes the one where the documents have nothing in common. Before building anything, it is worth being sure that is the case you are in, because the wrong guess costs a lot in either direction.

第 14A 篇文章（三种语料库类型，以及为错误的类型构建系统所付出的代价）列出了集合的三种形态，并指出每种形态都需要不同的架构。本文讨论的是文档之间毫无共同点的情况。在构建任何东西之前，务必确认你所处的情况，因为猜错方向的代价都很高昂。

#### 1.1. Two questions that decide it
#### 1.1. 决定性的两个问题

The first question: do two documents in the folder ever refer to each other? An amendment refers to its master agreement. A renewal refers to last year’s policy. A certificate belongs to a contract. If that happens, the folder has a structure you must model, and this article is not the one you want.

第一个问题：文件夹中的两个文档是否会相互引用？修订案引用主协议，续约引用去年的保单，证书属于合同。如果存在这种情况，说明文件夹具有你必须建模的结构，那么本文不适合你。

The second question: can a business user name a field that every document has, and that means the same thing in each? Client, effective date, premium, policy number. If the answer comes back fast and confidently, the folder is a database nobody has typed yet, and typing it is the job. If both answers are no, there is nothing to put in the columns. You could still extract metadata (file name, page count, creation date), but none of it is a field anyone will filter on. A column that is empty for most rows and means something different in the rest is not a column.

第二个问题：业务用户能否说出一个每个文档都具备且含义相同的字段？例如客户、生效日期、保费、保单号。如果答案迅速且肯定，那么这个文件夹就是一个尚未定义类型的数据库，而定义类型就是你的工作。如果两个问题的答案都是否，那么就没有内容可以放入列中。你仍然可以提取元数据（文件名、页数、创建日期），但这些都不是用户会过滤的字段。对于大多数行都为空，且在其余行中含义不同的列，根本算不上列。

Mixed folders exist, and they are common. A shared drive can hold 5,000 look-alike contracts next to 300 miscellaneous files that belong to nobody. That is not a contradiction, it is two corpora sharing a disk. Split them and run the right architecture on each.

混合文件夹是存在的，而且很常见。共享驱动器中可能存放着 5000 份相似的合同，旁边还有 300 份不属于任何类别的杂项文件。这并不矛盾，这只是两个语料库共享一个磁盘。将它们拆分，并对每个语料库运行正确的架构即可。

#### 1.2. What the other case gets, and this one does not
#### 1.2. 另一种情况能得到什么，而这种情况不能

The homogeneous case (Article 14C, where the business already knows the columns) gets three things this one cannot have. It gets a filter. A question that says "retailer X, currently in force" becomes a SQL clause, and 18,000 rows become three before anything is read. It gets aggregation. "How many policies expire this quarter" is answered by the index itself, with no document opened at all. It gets a shared vocabulary. Every row has a client and a date, so the ontology that maps user words to column values pays off across the whole corpus. None of that transfers here. There is no clause to write, nothing to count, and a vocabulary shared by a control catalogue and a commodity report would be a vocabulary about nothing.

同质化情况（第 14C 篇文章，业务方已知晓列名）拥有本文无法实现的三种功能。首先是过滤器：诸如“零售商 X，当前有效”的问题会转化为 SQL 子句，在读取任何内容前，18,000 行数据就会缩减为三行。其次是聚合：“本季度有多少保单到期”可以直接通过索引回答，无需打开任何文档。最后是共享词汇表：每一行都有客户和日期，因此将用户词汇映射到列值的本体论在整个语料库中都能发挥作用。这些在本文讨论的情况下都无法实现。这里没有可写的子句，没有可统计的内容，而安全控制目录与大宗商品报告之间的共享词汇表将毫无意义。
