# Building a Proper Backend for My LangGraph AI Agent
# 为我的 LangGraph AI Agent 构建一个正式的后端

In the first two articles of this series, I built a stateful LangGraph agent that handles a 15-minute booking process and wrapped it up with a Streamlit UI to improve user experience. The agent handles the entire booking process like a real customer service representative.
在本系列的前两篇文章中，我构建了一个有状态的 LangGraph Agent，用于处理 15 分钟的预订流程，并使用 Streamlit UI 对其进行了封装以改善用户体验。该 Agent 像真正的客户服务代表一样处理整个预订流程。

It’s a LangGraph-based agent that orchestrates the following operations:
这是一个基于 LangGraph 的 Agent，它协调以下操作：

*   Responds to customer queries and understands their needs.
    *   响应客户查询并理解其需求。
*   Calculates the price for the service and informs the customer.
    *   计算服务价格并告知客户。
*   Handles the customer’s acceptance or rejection.
    *   处理客户的接受或拒绝。
*   Proposes optimized time slots.
    *   推荐优化的时间段。
*   Confirms and records the appointment.
    *   确认并记录预约。

The next phase is to build a proper backend and we start by implementing a Postgres database instead of keeping everything in memory. We keep Streamlit as the user interface and replace the in-memory adapters with PostgreSQL. This will also allow us to have multiple fronts (e.g. WhatsApp, Streamlit) that share the same backend. So we are turning this into a proper product that will handle a real business.
下一阶段是构建一个正式的后端，我们首先通过实现 Postgres 数据库来替代内存存储。我们将保留 Streamlit 作为用户界面，并将内存适配器替换为 PostgreSQL。这也将使我们能够拥有共享同一后端的多个前端（例如 WhatsApp、Streamlit）。因此，我们正在将其转变为一个能够处理实际业务的正式产品。

The full source code of this project is available on GitHub at customer-service-agent. Feel free to clone the repo and test it yourself.
该项目的完整源代码可在 GitHub 上的 customer-service-agent 获取。欢迎克隆仓库并自行测试。

### What the database looks like now
### 现在的数据库是什么样的

It’s hard to even call it a database as it’s just two Python objects that lived inside the process: The first one is a LangGraph checkpointer, which is a state persistence layer that saves a snapshot of an agent’s graph state at every step of execution. When the graph is compiled, conversation state is stored in memory.
这甚至很难被称为数据库，因为它只是存在于进程中的两个 Python 对象：第一个是 LangGraph checkpointer，这是一个状态持久化层，用于在执行的每一步保存 Agent 图状态的快照。当图被编译时，对话状态存储在内存中。

`graph.compile(checkpointer=checkpointer or MemorySaver())`

The checkpointer allows the agent resume across turns. If we don’t have it, every customer message would be a new conversation.
Checkpointer 允许 Agent 在多轮对话中恢复状态。如果没有它，每一条客户消息都将是一次新的对话。

The second object is a Python list behind a lock. Confirmed appointments are stored in an in-memory repository that looks like this:
第二个对象是一个受锁保护的 Python 列表。已确认的预约存储在一个内存存储库中，如下所示：

```python
class InMemoryBookingRepository:
    def __init__(self) -> None:
        self._lock = threading.RLock()
        self.technicians = {...} # hardcoded cleaners
        self._bookings: list[Booking] = []

    def list_bookings(self) -> list[Booking]:
        with self._lock:
            return list(self._bookings)

    def create_booking(self, option, details, price) -> Booking:
        # check overlap in Python, then append to self._bookings
        ...
```

The scheduling engine called `list_bookings()` to avoid double-booking. Confirmation called `create_booking()`, which re-checked overlap and appended to the list. This is a very simple structure designed for initial testing and demo purposes. It allows us to test LangGraph routing and logic.
调度引擎调用 `list_bookings()` 以避免重复预订。确认环节调用 `create_booking()`，它会重新检查时间重叠并将其追加到列表中。这是一个非常简单的结构，专为初步测试和演示目的而设计。它使我们能够测试 LangGraph 的路由和逻辑。

### Why we need a proper database
### 为什么我们需要一个正式的数据库

The current “database” relies on in-memory persistence so it fails as soon as we leave a single demo process. When the process restarts, conversation checkpoints and bookings vanish. Since it’s in memory, there is no shared availability. Session A cannot see bookings created by Session B, which means every process has its own calendar.
当前的“数据库”依赖于内存持久化，因此一旦我们离开单个演示进程，它就会失效。当进程重启时，对话检查点和预订信息都会消失。由于它在内存中，因此没有共享的可用性。会话 A 无法看到会话 B 创建的预订，这意味着每个进程都有自己的日历。

Even worse for a booking product is that the agent can offer a slot based on a stale in-memory view, then “confirm” a booking that another session already took. When we use the Streamlit UI, it looked like a product but the storage still behaved like a notebook kernel. Long story short, we need a proper database for our agent to be considered as a product.
对于预订产品来说，更糟糕的是，Agent 可能会基于过时的内存视图提供一个时间段，然后“确认”一个已经被另一个会话占用的预订。当我们使用 Streamlit UI 时，它看起来像一个产品，但存储方式仍然表现得像一个 Notebook 内核。简而言之，我们需要一个正式的数据库，才能将我们的 Agent 视为一个产品。

We will use Postgres, which is a free and open-source relational database system. We need a relational database with bookings and technician information stored in separate (and related) tables.
我们将使用 Postgres，这是一个免费且开源的关系型数据库系统。我们需要一个关系型数据库，将预订信息和技术人员信息存储在独立（且相关联）的表中。

### Postgres implementation
### Postgres 实现

We first create a protocol so that the graph and engines can depend on a stable interface, not on Postgres (or memory) specifically.
我们首先创建一个协议（Protocol），以便图和引擎可以依赖于一个稳定的接口，而不是专门依赖 Postgres（或内存）。

```python
from typing import Protocol

class BookingRepository(Protocol):
    """Persistence interface used by scheduling and confirmation."""
    @property
    def technicians(self) -> dict[str, Technician]:
        """Return technicians keyed by id."""
    def list_bookings(self) -> list[Booking]:
        """Return all confirmed bookings."""
    def create_booking(
        self, option: TimeOption, details: BookingDetails, price: float
    ) -> Booking:
        """Persist a booking after re-checking overlap; raise ValueError if taken."""
```

With this protocol, we just plug `PostgresBookingRepository` or `InMemoryBookingRepository` at startup (depending on using Postgres or in-memory). Then, the nodes can call `list_bookings` and `create_booking` functions.
有了这个协议，我们只需在启动时插入 `PostgresBookingRepository` 或 `InMemoryBookingRepository`（取决于是否使用 Postgres 或内存）。然后，节点就可以调用 `list_bookings` 和 `create_booking` 函数。

When we use `InMemoryBookingRepository`, no database tables are created. Confirmed bookings are kept in a Python list inside the running process, and the same repository methods (`list_bookings`, `create_booking`) still work. They just never touch Postgres. The in-memory mode is ideal for unit tests and quick local demos. It’s important to also mention that, with the in-memory mode, everything disappears when the app restarts.
当我们使用 `InMemoryBookingRepository` 时，不会创建任何数据库表。已确认的预订保存在运行进程内的 Python 列表中，并且相同的存储库方法（`list_bookings`，`create_booking`）仍然有效。它们只是从不触及 Postgres。内存模式非常适合单元测试和快速本地演示。同样重要的是要提到，在内存模式下，当应用程序重启时，所有内容都会消失。

When we use `PostgresBookingRepository`, there is an actual database. Inside the `postgres.py` script, you can see the database schema that consists of two tables, which are `technicians` and `bookings`. You can also see the definition of the `PostgresBookingRepository` class. I won’t copy it here because it’s close to 100 lines of code. We also define the functions `list_bookings` and `create_booking` inside this class.
当我们使用 `PostgresBookingRepository` 时，就有了实际的数据库。在 `postgres.py` 脚本中，你可以看到包含 `technicians` 和 `bookings` 两个表的数据库架构。你还可以看到 `PostgresBookingRepository` 类的定义。我不会在这里复制它，因为它有近 100 行代码。我们还在该类中定义了 `list_bookings` 和 `create_booking` 函数。

At app startup, `create_persistence()` chooses Postgres vs in-memory. When `DATABASE_URL` is set, both the booking repository and LangGraph checkpointer use Postgres. Otherwise both stay in memory. So the repository is either a `PostgresBookingRepository` or `InMemoryBookingRepository` (both satisfy the `BookingRepository` protocol).
在应用程序启动时，`create_persistence()` 会选择 Postgres 或内存模式。当设置了 `DATABASE_URL` 时，预订存储库和 LangGraph checkpointer 都会使用 Postgres。否则，两者都保留在内存中。因此，存储库要么是 `PostgresBookingRepository`，要么是 `InMemoryBookingRepository`（两者都满足 `BookingRepository` 协议）。
