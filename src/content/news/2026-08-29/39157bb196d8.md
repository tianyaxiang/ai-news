# From One Agent to a Team: Understanding Codex Subagents
# 从单一智能体到团队：理解 Codex 子智能体

When we ask Codex to complete a task, we usually think of it as a single agent. But if some tasks are complex enough and involve several distinct types of work, Codex will try to divide the problem into smaller tasks and spawn separate agents to work on them.
当我们要求 Codex 完成一项任务时，通常会将其视为单一智能体。但如果某些任务足够复杂且涉及多种不同类型的工作，Codex 会尝试将问题拆解为更小的任务，并生成独立的智能体来处理它们。

These delegated agents are called subagents. Each subagent works in its own thread and focuses on only one part of the original task. At the same time, the main agent coordinates their work and produces the final response by aggregating the subagents' results.
这些被委派的智能体被称为“子智能体”（subagents）。每个子智能体在各自的线程中工作，仅专注于原始任务的一部分。与此同时，主智能体负责协调它们的工作，并通过汇总子智能体的结果来生成最终响应。

As practitioners, this naturally leads to this question: How can we use subagents deliberately for our own problems? In this post, we’ll explore Codex subagents through a hands-on case study. Along the way, we’ll see how to define and delegate work to specialist agents, inspect their individual threads, and let the main agent combine their findings into a final result.
作为实践者，这自然引出了一个问题：我们如何针对自己的问题有意识地使用子智能体？在本文中，我们将通过一个实践案例来探索 Codex 子智能体。在此过程中，我们将了解如何定义并向专家智能体委派工作、检查它们的独立线程，以及如何让主智能体将它们的发现整合为最终结果。

### 1. Case Study: Planning a Trip with Specialist Agents
### 1. 案例研究：利用专家智能体规划行程

Here, we consider a travel planning task. Suppose we want to plan a four-day solo trip from Zurich. We have a total budget of 1,200 Swiss Francs. Our potential destinations include Lisbon, Prague, and Copenhagen, and we care about convenient travel, museums, and local food.
在此，我们考虑一个旅行规划任务。假设我们要规划一次从苏黎世出发的四天单人旅行，总预算为 1200 瑞士法郎。我们的潜在目的地包括里斯本、布拉格和哥本哈根，我们关注交通便利性、博物馆和当地美食。

For this task, we prepare three specialist agents:
*   Travel logistics agent
*   Budget analyst
*   Experience researcher
针对此任务，我们准备了三个专家智能体：
*   旅行物流智能体
*   预算分析智能体
*   体验研究智能体

Each specialist will evaluate all three destinations from its own perspective. The main agent will then collect their findings, compare the tradeoffs, and recommend one final destination.
每位专家将从各自的角度评估所有三个目的地。随后，主智能体将收集它们的发现，比较权衡，并推荐一个最终目的地。

#### 1.1 Defining the Specialist Agents
#### 1.1 定义专家智能体

We start by defining our specialist agents. Codex allows us to define custom agents for a specific project. We can do this by adding TOML files under `.codex/agents/`:
我们首先定义专家智能体。Codex 允许我们为特定项目定义自定义智能体。我们可以通过在 `.codex/agents/` 下添加 TOML 文件来实现：

```markdown
.codex/
├── config.toml
└── agents/
    ├── travel-logistics.toml
    ├── budget-analyst.toml
    └── experience-researcher.toml
```

Each agent definition requires three fields:
*   `name`: how Codex identifies the agent.
*   `description`: what this agent is.
*   `developer_instructions`: how the agent should behave.
每个智能体定义需要三个字段：
*   `name`：Codex 识别智能体的方式。
*   `description`：该智能体的定义。
*   `developer_instructions`：智能体应如何表现。

Here is the definition for the travel logistics agent:
以下是旅行物流智能体的定义：

```yaml
name = "travel_logistics"
description = "Travel specialist for comparing routes and journey convenience across candidate destinations."
developer_instructions = """Evaluate every destination from a travel-logistics perspective.
Return concise, source-backed findings to the main agent."""
```

For the budget analyst:
对于预算分析智能体：

```yaml
name = "budget_analyst"
description = "Budget specialist for comparing the likely trip cost across candidate destinations."
developer_instructions = """Evaluate every destination from a trip-budget perspective.
Return concise, source-backed findings to the main agent."""
```

And the experience researcher:
以及体验研究智能体：

```yaml
name = "experience_researcher"
description = "Destination specialist for comparing how well each option fits the traveler's stated interests."
developer_instructions = """Evaluate every destination against the traveler's stated interests.
Return concise, source-backed findings to the main agent."""
```

A custom agent can also specify its own model, reasoning effort, sandbox configuration, tools, and skills. If we do not override those settings here, the three specialists will inherit them from the main Codex session.
自定义智能体还可以指定其模型、推理强度、沙盒配置、工具和技能。如果我们不在此处覆盖这些设置，这三个专家智能体将从主 Codex 会话中继承这些配置。

Additionally, we add a small project-level configuration in `.codex/config.toml`:
此外，我们在 `.codex/config.toml` 中添加了一个小的项目级配置：

```yaml
[agents]
max_concurrent_threads_per_session = 3
```

This allows up to three subagent threads to run concurrently.
这允许最多三个子智能体线程同时运行。

#### 1.2 Running the Subagent Workflow
#### 1.2 运行子智能体工作流

Now that the three specialists are available, we can give the main agent our specific task:
现在三个专家智能体已就绪，我们可以向主智能体下达具体任务：

> I am planning a four-day solo leisure trip from Zurich from October 15 to October 18, 2026. My total budget is CHF 1,200. Compare Lisbon, Prague, and Copenhagen. I care about convenient travel, museums, and local food. Use the `travel_logistics`, `budget_analyst`, and `experience_researcher` agents in parallel. Each agent should evaluate all three destinations from its specialty. Wait for all three agents, then recommend one destination and explain the main tradeoffs with source links.
> 我正在规划一次从 2026 年 10 月 15 日到 10 月 18 日从苏黎世出发的四天单人休闲旅行。我的总预算是 1200 瑞士法郎。请比较里斯本、布拉格和哥本哈根。我关注交通便利性、博物馆和当地美食。请并行使用 `travel_logistics`、`budget_analyst` 和 `experience_researcher` 智能体。每个智能体应从其专业角度评估所有三个目的地。等待所有三个智能体完成后，推荐一个目的地，并附上来源链接解释主要的权衡因素。

In the prompt, we explicitly asked the main agent to use our defined specialist agents when solving the task.
在提示词中，我们明确要求主智能体在解决任务时使用我们定义的专家智能体。

To run the case study, we can start Codex from the project directory with web search enabled:
要运行此案例研究，我们可以从项目目录启动启用了网络搜索功能的 Codex：

```bash
codex --search
```

Note that we only need to enable web search for the main session. The three subagents inherit this capability when Codex spawns them.
请注意，我们只需为会话主体启用网络搜索。当 Codex 生成这三个子智能体时，它们会自动继承此功能。

Then, we can submit the prompt. We see that Codex started the three specialist agents in parallel. We can inspect their progress directly from the CLI using:
然后，我们可以提交提示词。我们看到 Codex 并行启动了三个专家智能体。我们可以通过 CLI 直接检查它们的进度：

```bash
/agent
```

This opens the agent-thread view, as each specialist has its own context, tool activity, and eventual result. Once all three agents finish, their findings are returned to the main agent for synthesis.
这将打开智能体线程视图，因为每个专家都有自己的上下文、工具活动和最终结果。一旦所有三个智能体完成工作，它们的发现将被返回给主智能体进行综合。

#### 1.3 Inspecting the Results
#### 1.3 检查结果

Now we can check what they produced. I can see that each subagent returned a recommendation from its own perspective. Very interesting, they did not arrive at the same conclusion: the travel logistics subagent suggests Copenhagen, the budget subagent recommends Prague, while the experience subagent says Lisbon is the best choice.
现在我们可以查看它们的产出。我发现每个子智能体都从各自的角度给出了建议。非常有趣的是，它们得出的结论并不一致：旅行物流子智能体建议去哥本哈根，预算子智能体推荐布拉格，而体验研究子智能体则认为里斯本是最佳选择。

The main agent collected individual responses and recommended Lisbon as the best balance across travel convenience, cost, museums, and local food. So, we can see that the main agent indeed compared the subagents' findings against the original requirements and made an overall judgment, instead of simply repeating one answer or concatenating three reports.
主智能体收集了各方的回复，并推荐里斯本作为在交通便利性、成本、博物馆和当地美食之间取得最佳平衡的选择。因此，我们可以看到主智能体确实根据原始需求对比了子智能体的发现并做出了综合判断，而不是简单地重复其中一个答案或拼接三份报告。
